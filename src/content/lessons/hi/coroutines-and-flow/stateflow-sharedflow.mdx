<KeyIdea>
Cold `Flow` हर collector के लिए चलता है। **Hot** stream एक बार चलता है और सबको भेजता है। `StateFlow`
के पास हमेशा एक मौजूदा value होती है; `SharedFlow` के पास सिर्फ उतना जितना replay set किया हो।
</KeyIdea>

## दोनों, आमने-सामने

| | `StateFlow` | `SharedFlow` |
| --- | --- | --- |
| मौजूदा value | हमेशा होती है | Replay set न हो तो नहीं |
| शुरुआती value | जरूरी | इजाजत नहीं |
| दोहराव | गिरा दिया जाता है | भेज दिया जाता है |
| नए collector को | मौजूदा value तुरंत | सिर्फ `replay` जितनी चीजें |
| किस लिए | Screen की **state** | एक बार होने वाले **events** |

फर्क state और events का है, और गलत चुनाव दो बिलकुल तय bugs पैदा करता है।

```kotlin title="ViewModel.kt" numbered
class ProfileViewModel : ViewModel() {

    private val _state = MutableStateFlow<UiState>(UiState.Loading)
    val state: StateFlow<UiState> = _state.asStateFlow()

    private val _events = MutableSharedFlow<Event>()
    val events: SharedFlow<Event> = _events.asSharedFlow()

    fun load() = viewModelScope.launch {
        _state.value = UiState.Loading
        runCatching { repository.user() }
            .onSuccess { _state.value = UiState.Success(it) }
            .onFailure { _events.emit(Event.ShowError(it.message)) }
    }
}
```

## Cold flow को hot बनाना

```kotlin title="Convert.kt" numbered
val state: StateFlow<List<Item>> = repository
    .itemsFlow()                        // cold — हर collector पर एक database query
    .stateIn(
        scope = viewModelScope,
        started = SharingStarted.WhileSubscribed(5_000),
        initialValue = emptyList(),
    )
```

`WhileSubscribed(5_000)` आखिरी collector के जाने के बाद पाँच second तक ऊपर वाले को जिंदा रखता है। यही
खिड़की phone घुमाने पर query दोबारा चलने से रोकती है।

<Detail summary="StateFlow दोहरी values क्यों गिरा देता है">
`StateFlow` `equals` से मिलाता है और मौजूदा value के बराबर emissions छोड़ देता है। इसी से Compose एक
जैसी state पर दोबारा recompose नहीं करता — और इसीलिए state रखने वाली `data class` जरूरी है: value
बराबरी न हो तो हर update बदलाव जैसा दिखता है।
</Detail>

## Android पर सुरक्षित collect करना

```kotlin title="Collect.kt" numbered
lifecycleScope.launch {
    repeatOnLifecycle(Lifecycle.State.STARTED) {
        viewModel.state.collect { render(it) }
    }
}
```

<Pitfall title="दो जो असली bugs बनाती हैं">
**बिना `repeatOnLifecycle` के सादा `lifecycleScope.launch { collect }`।** App background में चली जाए
तो भी collection चलती रहती है, और ऐसे views update करती है जो किसी को दिख ही नहीं रहे।

**एक बार वाले events के लिए `StateFlow` इस्तेमाल करना।** Navigation, snackbar और toast हर
configuration change पर दोबारा चलेंगे। `SharedFlow` इस्तेमाल कीजिए, या इस्तेमाल हो जाना साफ-साफ model
कीजिए।
</Pitfall>

## अभ्यास

1. `MutableStateFlow` में एक ही value दो बार डालिए और collector के calls गिनिए।
2. वही `MutableSharedFlow` के साथ कीजिए। फर्क समझाइए।
3. `stateIn(...WhileSubscribed(5000))` को `Eagerly` से बदलिए और देखिए ऊपर वाला कब चलता है।
4. `StateFlow` से error दिखाइए, device घुमाइए, और उसे दोबारा आते देखिए। फिर उसे `SharedFlow` पर ले
   जाइए।

## सारांश

| Type | कब |
| --- | --- |
| `Flow` | Cold; हर collector को अपना चलना चाहिए |
| `StateFlow` | हमेशा एक मौजूदा value हो — screen state |
| `SharedFlow` | जो एक बार होता है — navigation, संदेश |
| `stateIn` / `shareIn` | Scope के अंदर cold flow को hot बनाइए |
| `WhileSubscribed(5_000)` | घुमाने पर बचे, पर काम leak न हो |
| `repeatOnLifecycle` | UI न दिखे तो collect करना बंद |
