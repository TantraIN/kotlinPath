<KeyIdea>
Dispatcher एक **thread नीति** है, thread नहीं। `withContext` किसी block को उस पर ले जाता है और नतीजा
वापस भी ले आता है।
</KeyIdea>

## तीन जो आप इस्तेमाल करेंगे

| Dispatcher | पीछे क्या है | किस लिए |
| --- | --- | --- |
| `Dispatchers.Main` | अकेला UI thread | Views छूना, state पढ़ना-लिखना |
| `Dispatchers.IO` | बड़ा लचीला pool | Network, disk, database — जो काम **इंतजार** करता है |
| `Dispatchers.Default` | CPU cores जितना pool | Sorting, parsing, image — जो काम **गिनता** है |

आखिरी दो का फर्क ही असल में मायने रखता है।

`IO` उन कामों के लिए है जो ज्यादातर खाली बैठे रहते हैं, इसलिए वह कई threads तक बढ़ जाता है। `Default`
cores के आस-पास रुक जाता है, क्योंकि cores से ज्यादा threads से गिनती तेज नहीं होती।

## `withContext` — आम तौर पर इसी एक switch की जरूरत है

```kotlin title="Switch.kt" numbered
class Repository(private val api: Api, private val dao: OrderDao) {

    suspend fun user(id: String): User = withContext(Dispatchers.IO) {
        val response = api.fetch(id)      // इंतजार — IO
        dao.insert(response)
        response.toUser()
    }
}
```

```kotlin title="Caller.kt" numbered
viewModelScope.launch {                   // Main पर शुरू
    val user = repository.user("1")       // अंदर IO पर जाता है, वापस आता है
    nameText.text = user.name             // वापस Main पर, सुरक्षित
}
```

<Detail summary="Suspend function को अपना dispatcher खुद क्यों चुनना चाहिए">
अच्छे से लिखा `suspend` function **main-safe** होता है: उसे कहीं से भी बुलाया जा सकता है और बुलाने वाले
को threads के बारे में सोचना नहीं पड़ता। इसका मतलब dispatcher का चुनाव repository के अंदर होना चाहिए,
call site पर नहीं। अगर हर बुलाने वाले को `withContext(Dispatchers.IO)` याद रखना पड़े, तो एक न एक दिन कोई
भूल ही जाएगा।
</Detail>

## आम गलतियाँ

<Pitfall title="दो जो अटकाव या उससे बुरा करती हैं">
**छोटे काम के लिए dispatcher बदलना।** `withContext` की असली कीमत है — एक context switch और शायद
thread बदलना। तीन line के हिसाब को उसमें लपेटना सीधे करने से धीमा है।

**भारी गिनती के लिए `Dispatchers.IO` इस्तेमाल करना।** IO pool cores से कहीं ज्यादा बड़ा हो सकता है। आठ
cores पर साठ threads का JSON parse करना सब कुछ धीमा कर देता है, UI समेत।
</Pitfall>

## अभ्यास

1. एक CPU-भारी loop को कई coroutines के साथ `IO` पर और `Default` पर चलाइए। समय मिलाइए।
2. `withContext(Dispatchers.IO)` के अंदर से एक View छुइए और exception पढ़िए।
3. Repository का एक function main-safe बनाइए, फिर उसे `viewModelScope.launch` से बिना call site पर
   `withContext` लिखे बुलाइए।
4. `withContext` block से पहले, अंदर और बाद में `Thread.currentThread().name` print कीजिए।

## सारांश

| बात | विवरण |
| --- | --- |
| `Main` | सिर्फ UI; यहाँ कोई भी धीमी चीज frames गिराती है |
| `IO` | इंतजार वाला काम; pool cores से कहीं ज्यादा बढ़ता है |
| `Default` | गिनती वाला काम; pool cores के आस-पास रुका |
| `withContext` | एक block के लिए switch, और अपने आप वापस |
| Main-safety | Dispatcher function चुनता है, बुलाने वाला नहीं |
