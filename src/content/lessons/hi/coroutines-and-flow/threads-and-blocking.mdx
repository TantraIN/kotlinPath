Android एक thread — **main thread** — सिर्फ drawing और input के लिए रखता है। 60fps के लिए हर frame
लगभग 16ms में बनना चाहिए।

उस thread पर कोई भी धीमी चीज मतलब जमा हुआ app।

## पहला इलाज: दूसरा thread

```kotlin title="Threads.kt" numbered
fun loadUser() {
    Thread {
        val user = api.fetchUser()          // धीमा, पर अब main पर नहीं
        runOnUiThread { showUser(user) }    // draw करने के लिए वापस आना पड़ता है
    }.start()
}
```

यह चलता है, और इसीलिए 2019 से पहले हर Android app ऐसी ही दिखती थी। इसमें तीन असली दिक्कतें हैं।

| दिक्कत | क्यों मायने रखती है |
| --- | --- |
| Threads महँगे हैं | हर एक का लगभग 1MB stack; हजारों नहीं रख सकते |
| Cancel करने का तरीका नहीं | User screen छोड़ देता है; thread चलता रहता है |
| नतीजा वापस लाना पड़ता है | Main के बाहर View छुएँ तो exception आता है |

## दूसरा इलाज: callbacks, और वे बिगड़ते कहाँ हैं

```kotlin title="Callbacks.kt" numbered
fun loadScreen() {
    api.fetchUser { user ->
        api.fetchOrders(user.id) { orders ->
            api.fetchAddress(user.id) { address ->
                showScreen(user, orders, address)
                // और अब तीनों में error handling भी जोड़िए
            }
        }
    }
}
```

हर कदम ठीक है। एक के अंदर एक रखने पर ऐसा code बनता है जहाँ चलने का क्रम और लिखे हुए का क्रम एक नहीं
रहते।

<Pitfall bare>
ऊपर वाले में error handling जोड़िए और हर स्तर को अपनी अलग failure branch चाहिए। ऐसा कोई `try` है ही
नहीं जो तीनों को लपेट ले, क्योंकि तीनों एक ही stack पर हैं ही नहीं।
</Pitfall>

<Detail summary="बस और threads क्यों न बना लें">
एक thread लगभग एक megabyte stack लेता है और उसे schedule करने में kernel-level context switch लगता
है। दस हजार threads मुमकिन ही नहीं। दस हजार coroutines आम बात है, क्योंकि suspended coroutine बस heap
पर पड़ा एक object है — इंतजार के दौरान वह कोई thread पकड़ता ही नहीं।
</Detail>

## सारांश

| शब्द | मतलब |
| --- | --- |
| Main thread | अकेला thread जिसे draw और input की इजाजत है |
| Blocking | इंतजार के दौरान thread पकड़ना — यही कीमत हटानी है |
| Frame budget | 60fps पर ~16ms, 120fps पर ~8ms |
| ANR | Android का "Application Not Responding" dialog |
| Callback hell | Nested callbacks जहाँ चलने का क्रम पढ़ने के क्रम से अलग हो जाता है |
