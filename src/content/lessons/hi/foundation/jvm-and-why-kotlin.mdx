## यह क्यों ज़रूरी है

कभी न कभी build कुछ ऐसा कहकर fail होगी:

```text no-glossary
Unsupported class file major version 65
> Task :app:compileDebugKotlin FAILED
```

इस message में न Kotlin है, न Android, न आपका code। यह बात कर रहा है **bytecode** और **JDK
versions** की — यानी उसी layer की, जो इस पाठ का विषय है। यह layer दिखने लगे तो ऐसे errors
रहस्य नहीं रहते, एक line का fix बन जाते हैं।

## बीच का रास्ता

पिछले पाठ में दो रास्ते थे: सब कुछ पहले ही compile कर दो, या line by line interpret करो।
Kotlin इन दोनों में से कोई नहीं चुनता।

वह पहले ही compile करता है — लेकिन आपके processor के machine code में नहीं। वह **bytecode**
में compile करता है: एक काल्पनिक computer के लिए instructions। फिर **Java Virtual Machine**
नाम का program उस bytecode को उस असली machine पर चलाता है जहाँ वह install है।

यही पूरा खेल है। भारी काम compiler एक बार कर देता है। जो चीज़ Windows laptop, Linux server
और phone के बीच अलग होती है, उसे JVM सँभालता है।

<Tip bare>
"Write once, run anywhere" का मतलब यही है। Source portable है इसलिए नहीं — बल्कि **compile
की हुई चीज़** portable है इसलिए।
</Tip>

दो नाम बार-बार मिलेंगे:

- **JDK** — Java Development Kit. Tools *और* JVM दोनों। Build करने के लिए चाहिए।
- **JRE** — Java Runtime Environment. सिर्फ़ JVM। चलाने के लिए काफ़ी, build के लिए नहीं।

Android Studio अपने साथ एक JDK लेकर आता है, इसलिए आम तौर पर अलग install नहीं करना पड़ता —
और इसीलिए "यह build कौन सा JDK इस्तेमाल कर रही है?" का जवाब ढूँढ़ना आना चाहिए।

## अंदर की बात: bytecode पढ़ा जा सकता है

Bytecode कोई जादू नहीं है। यह एक साधारण Kotlin function है:

```kotlin title="Adder.kt" numbered runnable
fun add(a: Int, b: Int): Int {
    return a + b
}

fun main() {
    println(add(2, 3))
}
```

Compile होने पर `add` लगभग चार bytecode instructions बन जाता है: पहला argument load करो,
दूसरा load करो, जोड़ो, return करो। JVM इन्हें चलाता है — और जब कोई function काफ़ी बार चल चुका
होता है तो **JIT compiler** उसे असली machine code में बदल देता है, ताकि आगे की calls में
interpretation का काम बचे ही ना।

<Note>
इसीलिए JVM program पहले एक second धीमा और उसके बाद तेज़ लगता है। Android पर यही सोच
**Baseline Profiles** के रूप में आती है, जो runtime को पहले ही बता देती है कि क्या compile
करना है — ताकि आपके user को वह धीमा पहला second दिखे ही नहीं। इनसे दोबारा Phase 12 में
मुलाक़ात होगी।
</Note>

## तो Kotlin ही क्यों, Java क्यों नहीं?

दोनों का bytecode एक ही है। JVM को फ़र्क़ ही पता नहीं चलता। फ़र्क़ सिर्फ़ इतना है कि भाषा आपको
क्या कहने देती है — और क्या लिखने से **रोक** देती है।

एक ही चीज़, दोनों भाषाओं में:

```java title="User.java" numbered
public class User {
    private final String name;
    public User(String name) { this.name = name; }
    public String getName() { return name; }
    // और equals, hashCode, toString हाथ से
}
```

```kotlin title="User.kt" numbered runnable
data class User(val name: String)
```

एक line, और `equals`, `hashCode`, `toString` तथा `copy` साथ में। यह कोई जादू का खेल नहीं है
— value equality ही वह चीज़ है जिसकी वजह से list diffing और Compose recomposition सही चलते
हैं, जो आप Phase 2 में देखेंगे।

## आम ग़लतियाँ

<Pitfall title="दो ग़लतियाँ जो beginners का एक-एक दिन खाती हैं">
**JDK versions मिला देना।** आपकी Gradle build, Kotlin compiler और Android Studio — तीनों का
JDK एक होना चाहिए। `Unsupported class file major version 65` का मतलब है कि कुछ नए JDK से
compile हुआ है और पढ़ने वाला पुराना है। इसे एक ही जगह ठीक कीजिए — project का Java toolchain
— न कि randomly चीज़ें reinstall करके।

**Java से आई value पर भरोसा कर लेना।** Compiler को पता ही नहीं चलता कि Java का method null
लौटा सकता है या नहीं, इसलिए वह उसे *platform type* मानकर पीछे हट जाता है। उस boundary पर
null safety चुपचाप बंद हो जाती है। ऐसी value जैसे ही Kotlin code में आए, उसे तुरंत explicitly
nullable type (`String?`) में डाल दीजिए।
</Pitfall>

## अभ्यास

1. Terminal में `java -version` और `javac -version` चलाइए। दोनों same हैं? JDK और JRE शब्द
   सही जगह इस्तेमाल करके बताइए कि हर एक क्या है।
2. `add(2, 3)` लगभग चार instructions बनता है। अपने शब्दों में लिखिए कि हर instruction शायद
   क्या करता होगा।
3. कोई कहता है "Kotlin, Java से तेज़ है"। इस पाठ के आधार पर समझाइए कि यह बात ऐसे कहना बेमानी
   क्यों है, और वह असल में कहना क्या चाहता होगा।
4. Android साधारण JVM क्यों नहीं भेज सकता? पहले अंदाज़ा लगाइए, फिर अगला पाठ पढ़कर अपना जवाब
   जाँचिए।

## सारांश

| शब्द | यह क्या है | कहाँ मिलेगा |
| --- | --- | --- |
| Bytecode | एक काल्पनिक machine के instructions | `.class` files, build errors |
| JVM | वह program जो bytecode चलाता है | हर `java` command |
| JDK | Tools + JVM, build के लिए ज़रूरी | Gradle toolchain settings |
| JIT | Run time पर hot code को machine code बनाता है | पहला run धीमा, बाद में तेज़ |
| Platform type | Java की वह value जिसका null Kotlin जाँच नहीं सकता | Interop crashes |

अच्छा जवाब दोनों layers अलग करता है: bytecode level पर कुछ नहीं — JVM को वही instructions

class के members ख़ुद बनाता है, और `suspend` functions को bytecode बनने से पहले ही state
machine में बदल देता है।
</Interview>
