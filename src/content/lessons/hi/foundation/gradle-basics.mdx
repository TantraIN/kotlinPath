## यह क्यों ज़रूरी है

हर Android project में कुछ files ऐसी होती हैं जो आपने लिखी नहीं, पढ़ नहीं सकते, और छूने से डरते
हैं। फिर जब कोई tutorial कहता है "यह line build.gradle में डालो", तो आप ग़लत वाली में paste कर
देते हैं, build टूटती है, और सीखने को कुछ मिलता नहीं।

बीस मिनट का ढाँचा यह समस्या हमेशा के लिए ख़त्म कर देता है।

## Gradle एक pipeline है, कोई रहस्य नहीं

Build कड़ियों की एक शृंखला है, जहाँ हर कड़ी एक चीज़ को दूसरी में बदलती है। Gradle का काम है इन
कड़ियों को सही क्रम में चलाना, और जिनके inputs नहीं बदले उन्हें छोड़ देना।

ये steps ही **tasks** हैं। `./gradlew assembleDebug` का मतलब है आप `assembleDebug` नाम का task
माँग रहे हैं; Gradle ख़ुद पता करता है कि वह किस-किस पर निर्भर है और उन्हें भी चला देता है।

```bash title="Terminal" no-glossary
./gradlew tasks              # मैं क्या माँग सकता हूँ?
./gradlew assembleDebug      # debug APK बनाओ
./gradlew installDebug       # बनाओ और device पर भेज दो
./gradlew :app:dependencies  # यह library आई कहाँ से?
```

<Tip bare>
वह एक नियम जो ज़्यादातर confusion ख़त्म कर देता है: **library dependencies module की
`app/build.gradle.kts` में जाती हैं।** Root वाली `build.gradle.kts` सिर्फ़ यह बताती है कि पूरा
project कौन से plugins, किस version में इस्तेमाल कर सकता है।

## एक असली module build file पढ़िए

```kotlin title="app/build.gradle.kts" numbered
plugins {
    alias(libs.plugins.android.application)
    alias(libs.plugins.kotlin.android)
}

android {
    namespace = "com.example.myapp"
    compileSdk = 35

    defaultConfig {
        applicationId = "com.example.myapp"
        minSdk = 24
        targetSdk = 35
        versionCode = 1
        versionName = "1.0"
    }

    buildTypes {
        release {
            isMinifyEnabled = true
            proguardFiles(getDefaultProguardFile("proguard-android-optimize.txt"))
        }
    }
}

dependencies {
    implementation(libs.androidx.core.ktx)
    implementation(libs.androidx.activity.compose)
    testImplementation(libs.junit)
}
```

इसे चार सवालों की तरह पढ़िए:

| Block | किस सवाल का जवाब देता है |
| --- | --- |
| `plugins` | यह module है क्या — app, या library? |
| `android` | कौन से SDK levels, कौन सा package name, कौन से build types? |
| `buildTypes` | Debug और release में फ़र्क़ क्या हो? |
| `dependencies` | इस module को बाहर का कौन सा code चाहिए? |

दो lines पर थोड़ा रुकिए। `namespace` वह package है जिसमें आपकी generated `R` class बनती है।
`applicationId` device पर और Google Play पर आपकी app की स्थायी पहचान है — पहली release के बाद
इसे कभी बदला नहीं जा सकता। आम तौर पर दोनों same होते हैं, पर मतलब दोनों का अलग है।

## Version catalogue

ध्यान दीजिए, `dependencies` में कहीं version number नहीं है। वे एक ही file में रहते हैं:

```toml title="gradle/libs.versions.toml" no-glossary
[versions]
kotlin = "2.1.0"
coreKtx = "1.15.0"

[libraries]
androidx-core-ktx = { module = "androidx.core:core-ktx", version.ref = "coreKtx" }
junit = { module = "junit:junit", version = "4.13.2" }

[plugins]
kotlin-android = { id = "org.jetbrains.kotlin.android", version.ref = "kotlin" }
```

एक जगह version बदलिए, और हर module उसे उठा लेता है। Multi-module project में यही फ़र्क़ है कि
upgrade एक मिनट लेता है या पूरी दोपहर।

## अंदर की बात: पहली build धीमी क्यों होती है

Gradle दो अलग phases में चलता है, और आप किस phase में हैं यह पता होना ज़्यादातर उलझाने वाले
behaviour को समझा देता है।

<Timeline>
  <TimelineItem title="Configuration" meta="हर build पर">
    Gradle हर build file पढ़ता है और task graph बनाता है। Build file के top level पर लिखा कोई भी
    code **अभी** चलता है — उस task के लिए भी जो आपने माँगा ही नहीं। इसीलिए build script में पड़ा
    एक आवारा `println` या file read हर एक build को धीमा कर देता है।
  </TimelineItem>
  <TimelineItem title="Execution" meta="सिर्फ़ जो ज़रूरी है">
    आपने जो माँगा उसके लिए ज़रूरी tasks चलते हैं। जिन tasks के inputs और outputs नहीं बदले, उन्हें
    छोड़ दिया जाता है और `UP-TO-DATE` लिख दिया जाता है।
  </TimelineItem>
</Timeline>

```bash title="Terminal output" no-glossary
> Task :app:preBuild UP-TO-DATE
> Task :app:compileDebugKotlin
> Task :app:dexBuilderDebug
BUILD SUCCESSFUL in 12s
38 actionable tasks: 6 executed, 32 up-to-date
```

आख़िरी line ही काम की है। 32 tasks इसलिए छोड़े गए क्योंकि उनसे जुड़ी कोई चीज़ बदली ही नहीं। यही
Gradle का incremental build है — और इसीलिए `./gradlew clean` आख़िरी रास्ता होना चाहिए, आदत नहीं।

## `implementation` और `api` में फ़र्क़

```kotlin title="app/build.gradle.kts" numbered
dependencies {
    implementation(libs.retrofit)  // [!code highlight]
    api(libs.okhttp)               // [!code highlight]
}
```

`implementation` library को सिर्फ़ इस module तक सीमित रखता है। `api` उसे उन सबको दे देता है जो
इस module पर निर्भर हैं।

लगभग हमेशा `implementation` चुनिए। इसका मतलब है कि उस library को बदलने पर सिर्फ़ यही module
दोबारा compile होगा — बड़े project में यही फ़र्क़ पाँच second और दो मिनट की build के बीच का है।

## आम ग़लतियाँ

<Pitfall title="तीन ग़लतियाँ जो सबसे ज़्यादा समय खाती हैं">
**Dependency को root `build.gradle.kts` में paste कर देना।** वह module की file में जानी चाहिए।
जो error मिलता है — `implementation` का unresolved reference — वह यह कभी नहीं बताता।

**ज़रा सी दिक़्क़त पर तुरंत `clean` मार देना।** वह हर cached output फेंक देता है और अगली build पूरी
दोबारा बनाती है। पहले `./gradlew --stop` या `./gradlew build --rerun-tasks` आज़माइए; `clean`
तभी जब सच में पुराना output शक हो।

**बिना changelog पढ़े library version बढ़ा देना।** Gradle ख़ुशी-ख़ुशी नया version resolve कर देगा जो
behaviour चुपचाप बदल देगा। `./gradlew :app:dependencies` से देखिए कि असल में मिला क्या —
transitive dependencies की वजह से जो version माँगा था ज़रूरी नहीं वही मिले।
</Pitfall>

## अभ्यास

1. `./gradlew tasks` चलाइए और तीन ऐसे tasks ढूँढ़िए जो पहले कभी नहीं देखे। उनके नाम से क्या लगता
   है वे करते क्या हैं?
2. `app/build.gradle.kts` के top level पर `println("configuring")` डालिए। कोई भी task चलाइए और
   देखिए यह कब print होता है। यह कौन से phase में है? अब उसे हटा दीजिए।
3. `./gradlew assembleDebug` लगातार दो बार चलाइए। `actionable tasks` वाली line compare कीजिए।
   फ़र्क़ समझाइए।
4. एक dependency को `implementation` से `api` में बदलिए। दिखने में कुछ नहीं बदलेगा — समझाइए
   क्यों, और कब यह फ़र्क़ पड़ने लगेगा।

## सारांश

| शब्द | एक line |
| --- | --- |
| Task | Build का एक step; जिसे आप असल में बुलाते हैं |
| Wrapper (`./gradlew`) | Gradle version project के अंदर pin करता है |
| Configuration phase | Build files पढ़ता है, task graph बनाता है — हर बार चलता है |
| Execution phase | सिर्फ़ ज़रूरी और पुराने पड़े tasks चलाता है |
| Version catalogue | `libs.versions.toml` — हर version के लिए एक ही जगह |
| `implementation` | Dependency सिर्फ़ इस module तक सीमित |
| `api` | Dependency इस module के consumers तक खुली |

<Interview title="जिन्होंने ship किया है और जिन्होंने सिर्फ़ tutorial देखे हैं, उन्हें अलग करता है">
"`api` के बजाय `implementation` क्यों बेहतर है?"

जवाब correctness का नहीं, build time का है: `api` उस library को हर dependent module के compile
classpath पर डाल देता है, इसलिए उसे बदलने पर बहुत ज़्यादा दोबारा compile होता है। यह भी कहिए कि
इससे आपके अंदर के फ़ैसले module की public surface पर leak हो जाते हैं।
</Interview>
