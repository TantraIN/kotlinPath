<KeyIdea>
तीन औजार, तीन काम: **ktlint** सजाता है, **Detekt** Kotlin की बदबू ढूँढ़ता है, **Lint** Android की
गलतियाँ। इनमें से किसी को चलाने वाली चीज एक ही है — CI में चलना और build नाकाम करना, क्योंकि log में
पड़ी चेतावनी वह चेतावनी है जो भेज दी जाती है।
</KeyIdea>

## कौन क्या करता है

| औजार | क्या पकड़ता है | उदाहरण |
| --- | --- | --- |
| ktlint | सजावट | Imports का क्रम, हाशिया, आखिरी comma |
| Detekt | Kotlin की बदबू | लंबे methods, उलझी शर्तें, `!!`, बिना इस्तेमाल का code |
| Lint | Android का सही होना | गायब permission, गलत API level, leak होता `Context` |

Lint वही है जो असली bugs ढूँढ़ता है, क्योंकि वह Android जानता है: वह बताएगा कि आपने `minSdk` से ऊपर की
कोई API बुलाई, कि अंदरूनी class वाला कोई `Handler` leak करता है, कि आपकी की गई किसी call के लिए
manifest में permission नहीं है, या कि किसी string का अनुवाद गायब है। बाकी दो एकरूपता और उलझन के बारे
में हैं, जो अलग वजहों से मायने रखते हैं।

## इसे मायने रखने लायक बनाना

```kotlin title="build.gradle.kts" numbered
android {
    lint {
        warningsAsErrors = true
        abortOnError = true
        disable += setOf("GradleDependency")       // सोच-समझकर, वजह के साथ
        baseline = file("lint-baseline.xml")
    }
}

detekt {
    config.setFrom("$rootDir/config/detekt.yml")
    baseline = file("detekt-baseline.xml")
    buildUponDefaultConfig = true
}
```

`warningsAsErrors` वह लाइन है जो बर्ताव बदलती है। उससे पहले चेतावनी log में पड़ी वह लाइन है जिसे कोई
नहीं पढ़ता; उसके बाद build नाकाम होता है और वह code merge नहीं होता। कौन से नियम चालू करें, इस पर हर
बहस उसके बाद की बात है।

`disable` तब ठीक है जब वह एक फैसला हो। जो ठीक नहीं वह है ऐसी छूट जो किसी नियम के असहज लगने पर जोड़ दी
गई, बिना यह लिखे कि क्यों — वे जमा होती जाती हैं और आखिर में वह config किसी चीज का ब्योरा रह ही नहीं
जाती।

## ईमानदारी से छूट देना

```kotlin title="Suppress.kt" numbered
// वजह के साथ, जितना सँकरा हो सके उतना
@Suppress("TooGenericExceptionCaught")   // यहाँ SDK सादा Exception फेंकता है
try { sdk.connect() } catch (e: Exception) { report(e) }

// Android Lint, उसी शक्ल में
@SuppressLint("MissingPermission")       // बुलाने वाला जाँच चुका है, PermissionGate देखिए
fun lastLocation(): Location? = client.lastLocation
```

हर छूट को उतनी छोटी चीज तक सीमित कीजिए जितनी को उसकी जरूरत है — किसी एक statement तक, पूरी file तक
नहीं — और वजह लिखिए। File के स्तर वाली `@Suppress` अपनी वजह से ज्यादा जीती है, और बाद में पढ़ने वाला
कोई नहीं बता सकता कि वह अब भी चाहिए या नहीं।

## CI में

```yaml title=".github/workflows/check.yml" numbered
- run: ./gradlew ktlintCheck detekt lintDebug testDebugUnitTest
```

क्रम थोड़ा मायने रखता है: पहले सजावट, क्योंकि वह सबसे तेज है और सबसे साफ नाकाम होती है, फिर धीमी
जाँचें। ktlint चलाता कोई pre-commit hook भी जोड़ने लायक है — मनवाने के लिए नहीं, वह CI की जगह है जहाँ
उसे छोड़ा नहीं जा सकता, बल्कि इसलिए कि imports के क्रम पर किसी को CI की नाकामी न मिले।

<Detail summary="अपनी परंपराओं के लिए Lint का नियम लिखना">
सबसे कीमती नियम आमतौर पर project के अपने होते हैं, क्योंकि वे उस फैसले को लिख देते हैं जिसे आपकी team
को review में बार-बार दोहराना पड़ता है:

```kotlin title="Detekt rule" numbered
class NoHardcodedUiText(config: Config) : Rule(config) {
    override val issue = Issue(
        "NoHardcodedUiText", Severity.Defect,
        "UI text must come from a string resource, so it can be translated.",
        Debt.FIVE_MINS,
    )

    override fun visitStringTemplateExpression(expression: KtStringTemplateExpression) {
        if (expression.isInComposable() && expression.text.length > 3) {
            report(CodeSmell(issue, Entity.from(expression), issue.description))
        }
    }
}
```

तरीका यही है: वह नियम लीजिए जो अभी किसी समीक्षक के सिर में रहता है, और उसे build में ले जाइए। फायदा
सिर्फ एकरूपता नहीं है — फायदा यह है कि reviews उन चीजों पर ध्यान खर्च करना बंद कर देते हैं जिन्हें कोई
मशीन देख सकती है, और उस पर खर्च करने लगते हैं कि code सही है या नहीं।

Android Lint भी इसी तरह अपने checks लेने देता है, और उसका फायदा यह है कि वे code के साथ-साथ resources
और manifest भी देख सकते हैं। दोनों किसी config बदलने से ज्यादा काम हैं और उन दो-तीन परंपराओं के लिए
इसके लायक हैं जिन पर आपकी team सच में बहस करती है।
</Detail>

## आम गलतियाँ

<Pitfall title="पाँच, और पहली बाकी सबको बेमतलब कर देती है">
**ऐसी चेतावनियाँ जो build नाकाम नहीं करतीं।** Log में पड़ी चेतावनी भेज दी जाती है।

**पूरी सफाई पर काम रोक देना।** चार हजार उल्लंघन वह तरीका है जिससे औजार अपनाया नहीं, हटाया जाता है।

**बढ़ती हुई baseline।** उसे सिर्फ घटना चाहिए; बढ़ती हुई वह दर्ज करती है जिसकी आपने परवाह करना छोड़ दिया।

**बिना वजह वाली, पूरी file की छूटें।** वे अपनी वजह से ज्यादा जीती हैं और कोई बता नहीं सकता।

**सिर्फ वे नियम चालू करना जो पहले से पास हैं।** काम के नियम ठीक वही हैं जो छूट जाते हैं।
</Pitfall>

## अभ्यास

1. `warningsAsErrors` चालू कीजिए और गिनिए कि build कितनी देर टूटा रहता है।
2. Detekt की baseline बनाइए, फिर दस उल्लंघन ठीक करके उसे छोटा दोबारा बनाइए।
3. अपने codebase में बिना comment वाली कोई `@Suppress` ढूँढ़िए और तय कीजिए कि वह अब भी चाहिए या नहीं।
4. `lintDebug` चलाइए और Android वाली हर चेतावनी पढ़िए; लिखिए कि कौन सी असली bugs हैं।
5. ऐसी एक परंपरा के लिए अपना नियम लिखिए जिसे आपकी team review में दो बार से ज्यादा समझा चुकी है।

## दोहराव

| चीज | एक लाइन |
| --- | --- |
| ktlint | सजावट |
| Detekt | Kotlin की बदबू और उलझन |
| Lint | Android का सही होना — जो असली bugs ढूँढ़ता है |
| `warningsAsErrors` | वह लाइन जो बर्ताव बदलती है |
| Baseline | बीते को मंजूर कीजिए, नए code को नियमों पर रखिए |
| Baseline का अनुशासन | वह सिर्फ घटती है |
| छूटें | सँकरी, और वजह के साथ |
| CI | मनवाने की जगह; hooks सिर्फ सुविधा हैं |
| अपने नियम | समीक्षक के सिर वाले नियम को build में ले जाइए |
| असली बात | Reviews इस पर ध्यान खर्च करें कि code सही है या नहीं |

<Interview title="एक सवाल, किसी औजार को बिना हटवाए अपनाने का">
"बड़े मौजूदा codebase में स्थिर जाँच आप कैसे लाएँगे?"

Baseline के साथ, पहले ही दिन। किसी पके हुए codebase पर Detekt या Lint चालू करने से हजारों उल्लंघन
निकलते हैं, और किसी भी सुविधा वाले काम से पहले उन सबको ठीक करने का प्रस्ताव वह तरीका है जिससे औजार
अपनाया नहीं, हटाया जाता है। Baseline जो मौजूद है उसे जाना-माना और छूट वाला दर्ज कर लेती है, तो build आज
पास होता है और उस पल नाकाम होता है जब नया code कोई उल्लंघन जोड़े — और जो code अभी लिखा जा रहा है वही
सबसे लंबे समय तक सँभाला जाएगा।

जिन दो चीजों पर मैं अड़ूँगा वे हैं कि उल्लंघन चेतावनी छापने के बजाय build नाकाम करें, क्योंकि जिस
चेतावनी से कोई रुकता नहीं वह भेज दी जाती है, और यह कि baseline सिर्फ घटे — चीजें ठीक होने पर दोबारा
बनी, किसी नई चीज को सोखने के लिए कभी नहीं। जिससे मैं बचूँगा वह है वह लुभावना बीच का रास्ता कि सिर्फ वे
नियम चालू करें जो अभी पास हो रहे हैं, क्योंकि उससे ठीक वे नियम छूट जाते हैं जो कुछ पकड़ते।
</Interview>
