<KeyIdea>
शुरुआत **ऐसे लक्षण से** कीजिए जिसे आप दोबारा पैदा कर सकें, औजारों से नहीं। "तस्वीर खोलने के बाद list
को झटका देने पर वह अटकती है" ऐसा सवाल है जिसका जवाब trace दे सकता है; "ऐप धीमा लगता है" नहीं, और
इसीलिए ज्यादातर profiling बिना कुछ मिले खत्म होती है।
</KeyIdea>

## सही build नापिए

```kotlin title="build.gradle.kts" numbered
buildTypes {
    release { isMinifyEnabled = true }
    create("benchmark") {
        initWith(buildTypes.getByName("release"))
        signingConfig = signingConfigs.getByName("debug")
        isDebuggable = false                       // debuggable होना सब कुछ बदल देता है
        proguardFiles("benchmark-rules.pro")
    }
}
```

Debug वाला build ऐसे धीमा नहीं है कि वह अनुपात में हो — वह अलग तरह से धीमा है। वह R8 छोड़ देता है,
कुछ JIT वाली बेहतरी बंद कर देता है, और Compose का debug build compiler की छोड़ने वाली बेहतरी लगाता ही
नहीं। उससे मिले आँकड़े सच का धीमा रूप नहीं हैं; वे अलग आँकड़े हैं।

तो: release जैसा build नापिए, असली मँझोले device पर, और ऐप को पहले से गरम रखकर — जब तक नापने की चीज
startup ही न हो।

## तीन नजरें, और हर एक किसका जवाब देती है

| नजर | जवाब |
| --- | --- |
| CPU | समय कहाँ गया, हर thread पर, हर frame पर |
| Memory | क्या बना, क्या रुका हुआ है, और किसकी वजह से |
| Network | हर request, उसका नाप, उसका समय, और वह cache से आई या नहीं |
| Energy | कौन wake locks या GPS पकड़े है |

CPU वाली में recording के दो तरीके अलग पहचानने लायक हैं:

- **Sampling** हर कुछ milliseconds पर stack की झलक लेता है। सस्ता, तो जो आप नाप रहे हैं उसे बिगाड़ता
  नहीं — और वह ऐसा function चूक सकता है जो बार-बार पर थोड़ी देर चलता है।
- **Tracing** हर घुसने-निकलने को दर्ज करता है। पूरा, और इतना धीमा कि वह अपने ही बताए समय को बदल देता
  है, जिससे छोटे methods कहीं ज्यादा महँगे दिखते हैं।

Sampling से शुरू कीजिए। Tracing तभी उठाइए जब आप इलाका पहले से जानते हों और आपको ठीक-ठीक गिनती चाहिए।

## अपने trace वाले हिस्से

Profiling का सबसे काम का बदलाव आमतौर पर आपके code में होता है, औजार में नहीं:

```kotlin title="Trace.kt" numbered
import androidx.tracing.trace

suspend fun loadOrders(): List<Order> = trace("loadOrders") {
    val dtos = trace("network") { api.orders() }
    trace("map") { dtos.map(OrderDto::toDomain) }
}
```

`androidx.tracing` वाले हिस्से Perfetto में नाम वाले खानों की तरह दिखते हैं और tracing बंद होने पर
उनकी कीमत लगभग कुछ नहीं। किसी धीमे काम के चरणों को नाम देना "कहीं 800ms" को एक ही बार में "620ms
network में, 90ms mapping" बना देता है, और आमतौर पर पूरी छानबीन यही है।

Compose की अपनी है: composition वाली tracing चालू करने पर दिखता है कि कौन से composables recompose
हुए और कितनी बार, जो उस सवाल का जवाब देती है जो CPU वाली नजर नहीं दे सकती — कि काम धीमा नहीं है, वह
बहुत ज्यादा बार हो रहा है।

<Detail summary="Perfetto, और एक frame पढ़ना">
Android Profiler सुविधाजनक है; Perfetto वह है जो आप तब लेते हैं जब सवाल frames का हो।

हर frame का एक बजट है — 60Hz पर 16.7ms, 120Hz पर 8.3ms — और frame की timeline हर frame को उस बजट के
सामने, रंगों में दिखाती है। मायने यह नहीं रखता कि कोई frame धीमा था बल्कि यह कि **कौन सा हिस्सा** था:
आपका `Choreographer#doFrame` वाला काम, layout, draw, या GPU।

दो तरीके पहचानने लायक हैं:

**आपके काम के शुरू होने से पहले लंबा खाली अंतराल।** Main thread किसी और चीज में लगा था — अक्सर कोई
`Binder` वाला लेन-देन, कोई `SharedPreferences` का पढ़ना, या main thread पर चलती कोई database की query।
इलाज आपके frame को तेज करना नहीं है; इलाज उस दूसरे काम को उस thread से हटाना है।

**हर कुछ frames पर नियमित उछाल।** आमतौर पर garbage collection, जो `HeapTaskDaemon` की हलचल बनकर दिखती
है, और वह उस frame के बजाय किसी गरम रास्ते में हो रही allocation की तरफ इशारा करती है।

`adb shell dumpsys gfxinfo <package> framestats` वही बँटवारा आँकड़ों में देता है, और CI में जहाँ आप
timeline देख नहीं सकते वहाँ आपको यही चाहिए।
</Detail>

## आम गलतियाँ

<Pitfall title="पाँच, और पहली अपने बाद की हर चीज बेकार कर देती है">
**Debug वाले build की profiling।** अलग आँकड़े, धीमे रूप नहीं — खास तौर पर Compose में।

**पहले method tracing।** उसका बोझ उसी के खाते में जाता है जो सबसे ज्यादा बुलाया जाता है, जो भरमाता है।

**दोबारा पैदा न होने वाला लक्षण।** उसके बिना आप बता ही नहीं सकते कि बदलाव से फायदा हुआ या नहीं।

**Trace जो पहले दिखाए उसे ठीक करना।** छूने से पहले देखिए कि वह असली रास्ते पर है भी या नहीं।

**महँगे phone पर नापना।** आपके users के मँझोले device की अड़चन अलग है।
</Pitfall>

## अभ्यास

1. वही काम debug और release वाले builds पर दर्ज कीजिए और आँकड़े मिलाइए।
2. किसी धीमे काम को तीन `trace()` हिस्सों में लपेटिए और देखिए कि समय किसका है।
3. उसी काम का sampling वाला profile और method वाला trace लीजिए और मिलाइए कि दोनों किसे दोषी बताते हैं।
4. कोई Perfetto trace खोलिए और ऐसा एक frame ढूँढ़िए जो अपना बजट चूका, और वजह भी।
5. किसी सुधार से पहले और बाद में `dumpsys gfxinfo` चलाइए और अटके frames का प्रतिशत मिलाइए।

## दोहराव

| चीज | एक लाइन |
| --- | --- |
| शुरुआत | ऐसे लक्षण से जिसे दोबारा पैदा कर सकें |
| Build | Release जैसा; debug के आँकड़े अलग हैं, धीमे नहीं |
| Device | मँझोला, आपके users जैसा |
| Sampling | सस्ता, बिगाड़ता नहीं — सही डिफॉल्ट |
| Method tracing | पूरा, और अपना बोझ गरम बुलाने वालों के खाते में डालता है |
| `trace("name")` | आपके अपने नाम वाले हिस्से, लगभग मुफ्त |
| Composition tracing | "कितनी बार" का जवाब, जो CPU का समय नहीं दे सकता |
| Frame का बजट | 60Hz पर 16.7ms, 120Hz पर 8.3ms |
| Perfetto | Frames के लिए, और यह जानने के लिए कि main thread क्या कर रहा था |
| `gfxinfo framestats` | वही बँटवारा, आँकड़ों में, CI के लिए |

<Interview title="एक सवाल, भरमाते profile का">
"कोई profile किसी धीमी screen के ज्यादातर समय के लिए छोटे mapping वाले function को दोषी बताता है। आप उसे दोबारा लिखेंगे?"

पहले यह देखे बिना नहीं कि वह profile लिया कैसे गया। Instrumented method tracing हर call पर घुसना और
निकलना दर्ज करती है, तो उसका बोझ उसी पर आ बैठता है जो सबसे ज्यादा बुलाया जाता है — दस हजार बार बुलाया
गया दो लाइन का mapper trace पर हावी हो सकता है और असली समय में लगभग कुछ भी खर्च न करे। वहाँ जो आँकड़ा
मैं सच में पढ़ूँगा वह calls की गिनती है, क्योंकि एक screen बनाने के लिए दस हजार calls का आमतौर पर मतलब
है loop के अंदर mapping, या हर emission पर बदले हुए के बजाय पूरी list दोबारा map करना।

मैं sampling वाले profile से दोबारा नापूँगा, जिसकी कीमत calls की गिनती से नहीं बदलती, या उससे बेहतर
चरणों के इर्द-गिर्द अपने `trace()` हिस्सों से — network, mapping, बनाना — क्योंकि वह "कहीं 800ms" को
एक ही बार में बँटवारा बना देता है। और यह सब मैं release जैसे build पर करूँगा, क्योंकि debug के आँकड़े
धीमे रूप नहीं, अलग आँकड़े हैं।
</Interview>
