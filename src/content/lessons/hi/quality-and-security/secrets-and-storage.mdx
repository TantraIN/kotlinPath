<KeyIdea>
APK किसी और के computer पर पड़ी एक zip file है। नाम बदलना, `BuildConfig`, native code और चतुर encoding
— सब मेहनत बढ़ाते हैं और नतीजा कोई नहीं बदलता — तो जिस राज को राज रहना ही है वह **ऐप के साथ भेजा जा ही
नहीं सकता**।
</KeyIdea>

## "छिपाने" से मिलता क्या है

```kotlin title="NotHidden.kt" numbered
// decompile की गई class file में दिखता है
private const val API_SECRET = "sk_live_9f2a..."

// BuildConfig में दिखता है, जो एक आम class है
buildConfigField("String", "API_SECRET", "\"sk_live_9f2a...\"")

// strings.xml में दिखता है, और उससे भी आसानी से
<string name="api_secret">sk_live_9f2a...</string>

// .so में `strings` से दिखता है, और JNI वाली call में हाथ डालने वाले किसी को भी
external fun getSecret(): String
```

हर पंक्ति हमलावर के लिए थोड़ी और मेहनत है और कोई भी दीवार नहीं। `apktool` और `jadx` सेकंड लेते हैं;
NDK वाला रूप `strings` या Frida के साथ कुछ मिनट। अपने आप चलने वाले scanners Play पर ठीक इन्हीं शक्लों
के लिए घूमते हैं, और लीक हुई keys आमतौर पर इसी तरह मिलती हैं — किसी निशाना साधे हमलावर से नहीं, किसी
bot से।

जो फर्क मायने रखता है:

| किस तरह की key | भेजी जा सकती है? |
| --- | --- |
| सार्वजनिक client की पहचान — Maps की key, OAuth client id, Firebase की settings | हाँ; उसे server की तरफ से सीमित कीजिए |
| हस्ताक्षर का राज, निजी API की key, admin का token | कभी नहीं |

पहली किस्म के लिए सीमित करना ही सुरक्षा है: Maps की key को अपने package के नाम और हस्ताक्षर वाले
certificate से बाँध दीजिए, ताकि उसे निकालने से कुछ मिले ही नहीं। दूसरी के लिए वह काम आपके server की
जगह है, और ऐप किसी बाहरी के बजाय आपके endpoint को बुलाता है।

## Keystore, उन राजों के लिए जो device खुद बनाता है

Device जो खुद बनाता है और कभी भेजता नहीं वह अलग दिक्कत है, और Android के पास उसके लिए असली hardware
है:

```kotlin title="Keystore.kt" numbered
val spec = KeyGenParameterSpec.Builder("token_key", PURPOSE_ENCRYPT or PURPOSE_DECRYPT)
    .setBlockModes(BLOCK_MODE_GCM)
    .setEncryptionPaddings(ENCRYPTION_PADDING_NONE)
    .setUserAuthenticationRequired(true)          // सिर्फ biometric या PIN के बाद
    .build()

KeyGenerator.getInstance(KEY_ALGORITHM_AES, "AndroidKeyStore").apply {
    init(spec); generateKey()
}
```

Key की असली सामग्री सुरक्षित hardware से बाहर जाती ही नहीं — आजकल के ज्यादातर devices पर कोई TEE या
अलग सुरक्षा वाली chip — और root किए device से भी निकाली नहीं जा सकती। आपके code को उस key को *इस्तेमाल*
करने को मिलता है, पढ़ने को नहीं।

इसीलिए session का token Keystore की key से encrypt करके रखना सुरक्षित है और API का राज नहीं: Keystore
उस चीज की हिफाजत करता है जो उसी device पर बनी थी, जबकि API का राज APK में आया था और Keystore के देखने
से पहले ही उजागर हो चुका था।

## रखे हुए data की हिफाजत

```kotlin title="Storage.kt" numbered
// Jetpack Security हटाई जा चुकी है; अपनी Keystore की key से encrypt किया DataStore
val encrypted = cipher.doFinal(token.toByteArray())
dataStore.edit { it[TOKEN] = Base64.encodeToString(encrypted, Base64.NO_WRAP) }

// पूरे database के लिए SQLCipher, जिसका passphrase Keystore से आता है
Room.databaseBuilder(context, AppDatabase::class.java, "app.db")
    .openHelperFactory(SupportOpenHelperFactory(passphrase))
    .build()
```

`EncryptedSharedPreferences` और `EncryptedFile` मानक जवाब थे और अब हटाए जा चुके हैं, तो नए code को
सीधे Keystore की key DataStore के साथ लेनी चाहिए, या जहाँ पूरा database चाहिए वहाँ SQLCipher।

खतरे की तस्वीर साफ रखना ठीक रहेगा: `filesDir` वाली ऐप की अपनी storage दूसरे ऐप्स के लिए पहले से ही
पढ़ी नहीं जा सकती, और जिस device पर screen lock है वहाँ platform उसे पहले से ही encrypt करके रखता है।
उसके ऊपर encrypt करना root किए device, backup निकाले जाने, या चुराए हुए खुले phone से बचाता है — असली
खतरे, पर "कोई मेरी file पढ़ सकता है" से कहीं सँकरे।

<Detail summary="Backups, logs और इत्तेफाकन होने वाले रिसाव">
तीन तरीके जिनसे राज बिना किसी के हमला किए निकल जाते हैं।

**Auto Backup।** डिफॉल्ट से Android ऐप का data user के cloud पर सहेजता है, आपकी files समेत। जो
संवेदनशील है उसे बाहर रखिए:

```xml title="AndroidManifest.xml" numbered
<application
    android:dataExtractionRules="@xml/data_extraction_rules"
    android:fullBackupContent="@xml/backup_rules">
```

**Logs।** `Log.d("api", "token=$token")` debuggable build पर `adb` रखने वाले किसी को भी पढ़ा जा सकता
है, और crash की रिपोर्टों तथा analytics की कड़ियों में आगे भी बचा रहता है। Release में logging किसी R8
नियम से हटाइए, और request की body कभी log मत कीजिए।

**Screenshots और हाल वाली सूची।** संवेदनशील data दिखाती screen ऐप बदलने वाली सूची में दिखती है और
पकड़ी जा सकती है। `WindowManager.LayoutParams.FLAG_SECURE` उस activity के लिए दोनों रोक देता है।

तीनों में तरीका एक ही है: राज ठीक से सँभाला गया और फिर ऐसी जगह नकल हो गया जहाँ के नियम अलग हैं। यह
किसी भी decompiler से ज्यादा आम रिसाव है।
</Detail>

## आम गलतियाँ

<Pitfall title="पाँच, और पहली हमलावरों के बजाय bots को मिलती है">
**`BuildConfig` या `strings.xml` में कोई निजी key।** Scanners Play पर ठीक इसी के लिए घूमते हैं।

**NDK को छिपने की जगह मानना।** ढूँढ़ना मुश्किल, और इस्तेमाल के वक्त memory में खुला।

**Client की key सीमित न करना।** अपने package से बँधी Maps की key भेजना सुरक्षित है; बिना बँधी किसी और
का बिल है।

**`google-services.json` या keystore commit कर देना।** सिर्फ मौजूदा files नहीं, इतिहास देखिए।

**Tokens log करना।** वे log की लाइन पढ़े जाने के बहुत बाद तक crash की रिपोर्टों और analytics में बचे
रहते हैं।
</Pitfall>

## अभ्यास

1. अपनी ही release APK पर `jadx` चलाइए और हर वह string ढूँढ़िए जो key जैसी लगती है।
2. जिस `.so` में जड़ा हुआ राज है उस पर `strings` चलाइए।
3. `setUserAuthenticationRequired` वाली Keystore की key बनाइए और पक्का कीजिए कि आप उसे पढ़ नहीं सकते।
4. किसी screen पर `FLAG_SECURE` लगाइए और उसका screenshot लेने की कोशिश कीजिए।
5. अपने backup के नियम देखिए और गिनाइए कि आज कौन सी files cloud पर जातीं।

## दोहराव

| चीज | एक लाइन |
| --- | --- |
| APK | किसी और के computer पर पड़ी एक zip |
| नाम बदलना और NDK | हमलावर के लिए ज्यादा मेहनत; दीवार नहीं |
| Client की पहचान | भेजना ठीक है, अगर server की तरफ से सीमित हो |
| निजी राज | कभी मत भेजिए; वह काम आपके server की जगह है |
| Keystore | Hardware का सहारा; key निकाली नहीं जा सकती |
| यह चलता क्यों है | वह उसकी हिफाजत करता है जो device ने बनाई, जो APK में आई उसकी नहीं |
| `EncryptedSharedPreferences` | हटाई जा चुकी; DataStore के साथ Keystore की key लीजिए |
| SQLCipher | जब पूरा database encrypt करना हो |
| Auto Backup | संवेदनशील files बाहर रखिए, वरना वे cloud पर जाती हैं |
| `FLAG_SECURE` | Screenshots और हाल वाली झलक, दोनों रोकता है |

<Interview title="एक सवाल, जिसका जवाब दो टूक है">
"Android ऐप में API की key सुरक्षित तरीके से कैसे रखेंगे?"

रखेंगे ही नहीं — APK की हर चीज निकाली जा सकती है, और `BuildConfig`, `strings.xml`, नाम बदलना तथा NDK
में फर्क सिर्फ इतना है कि कितनी देर लगती है। NDK वही है जिसे लोग सुरक्षित मानते हैं, और वह है नहीं: वह
string उस binary में है, और उलझाई हुई होने पर भी इस्तेमाल के पल उसे memory में खुला होना ही पड़ता है,
और वहीं hooking वाला framework उसे पढ़ लेता है।

तो मैं keys को किस्म के हिसाब से बाँटूँगा। सार्वजनिक client की पहचान — Maps की key, कोई OAuth client
id — भेजी जा सकती है, क्योंकि सुरक्षा वह पाबंदी है: उसे package के नाम और हस्ताक्षर वाले certificate
से बाँध दीजिए ताकि निकालने से कुछ मिले नहीं। जो सच में राज है वह भेजा ही नहीं जाता; वह खास काम किसी
server पर चला जाता है जिससे ऐप हर user के अपने, रद्द किए जा सकने वाले token से पहचान बताता है।
Keystore अलग दिक्कत के लिए है — उस चीज की हिफाजत, जो device ने बनाई, जैसे कोई session की key — और वह
ठीक इसीलिए चलता है कि वह value APK में आई ही नहीं थी।
</Interview>
