## यह क्यों जरूरी है

Java में compiler `IOException` के लिए टोकता था। Kotlin नहीं टोकता। कोई याद नहीं दिलाएगा कि network
call fail हो सकती है — इसलिए *कहाँ* failure सँभालना है, यह फैसला आपका है, और जान-बूझकर लेना होगा।

## `try` भी एक expression है

```kotlin title="TryExpression.kt" numbered runnable
fun parseAge(text: String): Int {
    return try {
        text.toInt()
    } catch (e: NumberFormatException) {
        -1
    } finally {
        // हमेशा चलता है — cleanup, कभी return value नहीं
    }
}

fun main() {
    println(parseAge("42"))
    println(parseAge("abc"))
}
```

`try` value बनाता है, इसलिए उसके ऊपर `var` declare करने की जरूरत कम ही पड़ती है। `finally` हर रास्ते
पर चलता है, पर उसकी value फेंक दी जाती है — वहाँ cleanup रखिए, नतीजा कभी नहीं।

## अक्सर `try` की जरूरत ही नहीं

```kotlin title="SafeApis.kt" numbered runnable
fun main() {
    println("42".toIntOrNull())      // 42
    println("abc".toIntOrNull())     // null — कोई exception नहीं

    val numbers = listOf(1, 2, 3)
    println(numbers.getOrNull(9))    // null
    println(numbers.firstOrNull { it > 5 })
}
```

जो चीजें अनुमानित रूप से fail हो सकती हैं, उनमें से ज्यादातर का standard library एक `OrNull` जोड़ा
देता है। Failure *अपेक्षित* हो — गलत user input, गायब key — तो nullable API चुनिए। Exceptions
अनपेक्षित के लिए हैं।

<Tip bare>
एक अच्छा नियम: exceptions bugs के लिए हैं और बाहर की दुनिया के fail होने के लिए। ये control flow का
औजार नहीं हैं। Failure आते हुए दिख रही हो तो उसे return type में model कीजिए।
</Tip>

## `Result` और `runCatching`

```kotlin title="Result.kt" numbered runnable
fun loadName(id: Int): Result<String> = runCatching {
    if (id < 0) error("bad id")
    "user-$id"
}

fun main() {
    val ok = loadName(1)
    println(ok.getOrNull())                     // user-1
    println(ok.getOrDefault("unknown"))

    val bad = loadName(-1)
    println(bad.isFailure)                      // true
    println(bad.exceptionOrNull()?.message)     // bad id

    bad.fold(
        onSuccess = { println("got $it") },
        onFailure = { println("failed: ${it.message}") },
    )
}
```

`Result<T>` "या तो value या वह failure जिसने रोका" type में ही ले आता है, इसलिए बुलाने वाला भूल नहीं
सकता कि failure संभव है। `runCatching { }` ऐसे block को लपेटता है जो फेंक सकता है।

<Warning>
`runCatching` **सब कुछ** पकड़ लेता है, `CancellationException` भी। Coroutines में वही exception
cancellation ले जाता है, इसलिए उसे निगल जाने पर cancel हुआ काम चलता रहता है। `suspend` code के अंदर
खास exceptions पकड़िए — Phase 3 इसे ठीक से cover करता है।
</Warning>

## अपने exceptions, और `require`

```kotlin title="Own.kt" numbered runnable
class InsufficientBalance(val shortfall: Int) : Exception("Short by $shortfall")

fun withdraw(balance: Int, amount: Int): Int {
    require(amount > 0) { "amount must be positive" }        // IllegalArgumentException
    check(balance >= amount) { "balance too low" }           // IllegalStateException
    return balance - amount
}

fun main() {
    println(withdraw(500, 200))
    println(runCatching { withdraw(500, 900) }.exceptionOrNull()?.message)
}
```

`require` arguments की रखवाली करता है, `check` state की। दोनों हाथ से लिखे `if` और `throw` से बेहतर
पढ़ते हैं, और दोनों साफ बताते हैं कि गलती किसकी है।

<Pitfall title="दो जो असली समस्या छुपा देती हैं">
**खाली body वाला `catch (e: Exception) { }`।** Failure फिर भी हुई; आपने बस उसे अदृश्य कर दिया। कम से
कम log तो कीजिए। इससे बेहतर, यह तय कीजिए कि इस layer पर सुधार संभव है भी या नहीं।

**गलत layer पर पकड़ना।** जो repository network error निगलकर खाली list दे देता है, वह screen के लिए
"no connection" दिखाना असंभव बना देता है। वहाँ पकड़िए जहाँ आप कुछ कर सकते हैं, और तब तक failure को
type में चलने दीजिए।
</Pitfall>

## अभ्यास

1. `fun parsePort(text: String): Int` लिखिए जो गलत input पर 8080 लौटाए — पहले `try/catch` से, फिर
   `toIntOrNull()` से। कौन सा बेहतर है और क्यों?
2. फेंक सकने वाले function को `runCatching` में लपेटिए और दोनों branches `fold` से सँभालिए।
3. `transfer(from, to, amount)` में `require` और `check` दोनों लगाइए। कौन सी failure कौन सी है, और
   बुलाने वाले के लिए यह फर्क क्यों मायने रखता है?
4. समझाइए कि coroutine के अंदर `runCatching` cancellation कैसे तोड़ सकता है।

## सारांश

| Tool | किस लिए |
| --- | --- |
| `try/catch/finally` | सच में असाधारण failure; यह एक expression है |
| `toIntOrNull`, `getOrNull` | अपेक्षित failure — इन्हें चुनिए |
| `runCatching { }` | फेंकने वाले block को `Result` में लपेटना |
| `Result<T>` | सफलता या failure को type में ले जाना |
| `require` | बुलाने वाले ने गलत चीज दी |
| `check` | Object गलत state में है |
