<KeyIdea>
Play दो अलग किस्म के नियम मनवाता है। **तारीखें** — target API का स्तर — तय हैं, साल भर पहले छापी जाती
हैं, और आपको updates भेजने से रोक देती हैं। **घोषणाएँ** — data safety, permissions का इस्तेमाल — उससे
मिलाकर देखी जाती हैं जो आपका ऐप सच में करता है, और बेमेल महीनों बाद किसी कार्रवाई की शक्ल में सामने आता
है।
</KeyIdea>

## Target API वाली तारीख

```kotlin title="build.gradle.kts" numbered
android {
    compileSdk = 36
    defaultConfig {
        minSdk = 24        // आपका चुनाव: कितना पुराना device आप सँभालते हैं
        targetSdk = 35     // Play का नियम: कितने नए बर्तावों को आपने माना
    }
}
```

`targetSdk` बताता है कि आपने platform के कौन से बर्तावों के हिसाब से खुद को ढाला है — पीछे चलने की
हदें, permissions की व्यवस्था, storage के नियम। Play चाहता है कि वह ताजा release के एक साल के अंदर हो,
और वह तारीख हर अगस्त खिसकती है:

| मोटे तौर पर | शर्त |
| --- | --- |
| हर साल, ~अगस्त | नए ऐप्स और updates को पिछले साल का API स्तर लेना पड़ता है |
| उससे नीचे पड़े मौजूदा ऐप्स | Updates नहीं भेज सकते; लगे रह सकते हैं पर नए devices के नए users को दिखते नहीं |

जो नतीजा लोग चूक जाते हैं वह यह है कि तारीख चूकने पर आपका ऐप हटता नहीं — वह जम जाता है। आप कोई सुधार,
कोई सुरक्षा का पैबंद, कुछ भी नहीं भेज सकते जब तक `targetSdk` न बढ़ाएँ और उस platform की version ने जो
बदला उसे सँभाल न लें। इसीलिए तारीख से एक हफ्ते पहले तक टाला गया वह बदलाव उस काम का सबसे बुरा रूप है।

`minSdk` का नीति से कोई लेना-देना नहीं और वह पूरी तरह आपका फैसला है कि कौन से devices सँभालने हैं। उसे
बढ़ाना users छोड़ता है; घटाना अनुकूलता का काम बढ़ाता है।

## वे घोषणाएँ जिन्हें मेल खाना है

| घोषणा | Play किससे मिलाकर देखता है |
| --- | --- |
| Data safety | आपका ऐप और उसकी SDKs सच में क्या जमा और साझा करती हैं |
| Permissions | कोई संवेदनशील permission किसी मुख्य सुविधा से मेल खाती है या नहीं |
| लक्षित लोग | ऐप बच्चों के लिए बना है या नहीं, जिससे नियम बदल जाते हैं |
| विज्ञापन | ऐप में ads हैं या नहीं, जिससे जगहें बदलती हैं |

**संवेदनशील permissions** को ऐसा घोषित इस्तेमाल चाहिए जो मुख्य सुविधा हो, सुविधाजनक होना नहीं।
`QUERY_ALL_PACKAGES`, सारी files की पहुँच, SMS तथा call log की पहुँच, पीछे वाली location और पक्के
alarms, सबको form चाहिए और ज्यादातर माँगें ठुकरा दी जाती हैं — और यही platform वाले पाठों की बात नीति
बनकर आती है: अगर कोई सँकरी API मौजूद है, तो चौड़ी permission मंजूर नहीं होगी।

**खाता मिटाना** अब जरूरी है: जिस ऐप में खाता बनता है उसे ऐप के अंदर मिटाने का रास्ता और उसके लिए एक web
का URL देना पड़ता है। वह कागजी नहीं, बनाने का काम है, और teams को देर से पकड़ता है।

<Detail summary="कार्रवाई वाली email का मतलब असल में क्या है">
Play की कार्रवाइयों में दर्जे हैं, और आपको कौन सी मिली यह जानना जवाब बदल देता है:

- **चेतावनी** — तारीख वाली नीति की बात। ठीक करके दोबारा भेजिए; अभी कुछ बंद नहीं हुआ।
- **अस्वीकृति** — यही एक build ठुकराया गया। चल रहे रूप पर कोई असर नहीं।
- **हटाया जाना** — Listing खोज और install से गायब। मौजूदा users के पास ऐप रहता है।
- **निलंबन** — ऐप गया और developer का खाता खतरे में।
- **खाता खत्म** — हर ऐप, हमेशा के लिए, और Google नया खाता बनाने नहीं देता।

मायने यह चढ़ाई रखती है: बार-बार के उल्लंघन आपको ऊपर की सीढ़ी पर ले जाते हैं, तो चेतावनी को वैकल्पिक
मानना ही वह तरीका है जिससे कोई team अलग-अलग देखने पर छोटी सी बात के लिए निलंबन तक पहुँच जाती है।

अपील की विधि असली है और जब आपको लगे कि नतीजा गलत है तब लेने लायक है, पर वह सीमित बातचीत वाला एक form
है। मदद ब्योरा करता है: उस SDK का नाम लीजिए, वह code उद्धृत कीजिए, वह screen जोड़िए। "हम ऐसा करते ही
नहीं" वाली आम अपील शायद ही चलती है, क्योंकि समीक्षक उस बर्ताव को देख रहा है जो उसने देखा और उसे उससे
मिलाने के लिए कुछ ठोस चाहिए।
</Detail>

## आम गलतियाँ

<Pitfall title="पाँच, और पहली आपका ऐप जमा देती है">
**`targetSdk` बढ़ाना तारीख तक टालना।** जब तक वह न हो, आप कुछ भी नहीं भेज सकते।

**सिर्फ अपना जमा करना घोषित करना।** Play उस ऐप को परखता है, SDKs समेत।

**सँकरी API होते हुए चौड़ी permission माँगना।** वह घोषणा वाला form उसे बचाएगा नहीं।

**चेतावनी अनदेखी करना।** उल्लंघन चढ़ते हैं; चेतावनी काम करने का सबसे सस्ता मौका है।

**ऐप के अंदर खाता मिटाने का रास्ता न होना।** खातों वाले हर ऐप के लिए जरूरी, और वह बनाने का काम है।
</Pitfall>

## अभ्यास

1. अपना `targetSdk` Play की मौजूदा शर्त से मिलाइए और अगली तारीख लिखिए।
2. हर dependency और वह क्या जमा करती है, गिनाइए; अपने Data safety के form से मिलाइए।
3. अपने manifest में कोई संवेदनशील permission ढूँढ़िए और वह सँकरी API पहचानिए जो आप ले सकते थे।
4. Play की खाता मिटाने वाली शर्त पढ़िए और देखिए कि आपका ऐप उस पर खरा उतरता है या नहीं।
5. `targetSdk` एक बढ़ाइए और जो टूटे उसे ठीक कीजिए, जरूरी बनने से पहले।

## दोहराव

| चीज | एक लाइन |
| --- | --- |
| `targetSdk` | Platform के कौन से बर्तावों को आपने माना |
| वह तारीख | सालाना; चूकने पर updates जमते हैं, ऐप नहीं |
| `minSdk` | आपका फैसला, नीति नहीं |
| Data safety | SDKs को भी ढके, सिर्फ आपका code नहीं |
| संवेदनशील permissions | मुख्य सुविधा वाली दलील चाहिए; सँकरी API जीतती है |
| खाता मिटाना | ऐप में और URL से, दोनों जरूरी; बनाने का काम |
| चेतावनी | एक तारीख, और काम करने का सबसे सस्ता मौका |
| अस्वीकृति | सिर्फ यह build; चल रहा रूप ठीक है |
| हटाया जाना | Store से गायब; मौजूदा users के पास रहता है |
| चढ़ाई | बार-बार के उल्लंघन ऊपर की सीढ़ी पर ले जाते हैं |

<Interview title="एक सवाल, ऐसी घोषणा का जिसके लिए किसी ने code लिखा ही नहीं">
"Data safety का उल्लंघन आप कैसे बचाएँगे?"

अपना code देखने के बजाय dependencies गिनाकर, क्योंकि Play उस ऐप को परखता है और ज्यादातर जमा करना उन
SDKs से आता है जिन्हें किसी ने लिखा ही नहीं। Ads वाली SDK बनावट से ही विज्ञापन की id जमा करती है,
attribution वाली SDK होती ही जमा और साझा करने के लिए है, और Firebase Analytics कई दूसरी Firebase वाली
libraries के साथ अपने आप आती है और तुरंत जमा करना शुरू कर देती है। कोई team अपने लिखे के बारे में पूरी
तरह ईमानदार हो सकती है और फिर भी उसकी घोषणा मेल न खाए।

तो जाँच है हर dependency की सूची, हर एक क्या जमा करना बताती है, और उन सबका जोड़ घोषित करना। उसके साथ मैं
वे शर्तें रखूँगा जो कागज नहीं, बनाने का काम हैं — खातों वाले हर ऐप के लिए ऐप के अंदर खाता मिटाना, और
पहुँच में privacy policy का URL — और किसी भी चेतावनी को काम करने का मौका मानूँगा, क्योंकि उल्लंघन चढ़ते
हैं और चेतावनी उस सीढ़ी की सबसे सस्ती पायदान है।
</Interview>
