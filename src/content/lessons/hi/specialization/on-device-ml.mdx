<KeyIdea>
उपकरण पर ML की लगभग हर गड़बड़ी **तैयारी का बेमेल** है, खराब model नहीं। जो वजन laptop पर अच्छा नाप देते
हैं वही फोन पर बेतुका लौटाते हैं क्योंकि तस्वीर घूमी हुई, अलग नाप की या training से अलग तरह से सामान्य
की हुई पहुँची।
</KeyIdea>

## API के दो स्तर

ML Kit आपको पूरे किए हुए काम देता है — text पहचानना, barcode, चेहरे, मुद्रा, अनुवाद, विषय अलग करना। आप
उसे तस्वीर देते हैं और तयशुदा किस्म के नतीजे पाते हैं। LiteRT, वही runtime जिसे पहले TensorFlow Lite कहते
थे, *आपका* model चलाता है और आपको कच्चे tensors देता है।

ML Kit ही लीजिए, जब तक वह काम उसकी सूची में न हो। कसा हुआ, सँभाला जा रहा, hardware से तेज किया गया model
उस अपने वाले से ज्यादा कीमती है जिसे आपको जिंदा रखना पड़े।

```kotlin title="TextAnalyzer.kt" numbered
class TextAnalyzer(private val onText: (String) -> Unit) : ImageAnalysis.Analyzer {
    private val recognizer = TextRecognition.getClient(TextRecognizerOptions.DEFAULT_OPTIONS)

    @OptIn(ExperimentalGetImage::class)
    override fun analyze(proxy: ImageProxy) {
        val media = proxy.image ?: return proxy.close()
        val input = InputImage.fromMediaImage(media, proxy.imageInfo.rotationDegrees)

        recognizer.process(input)
            .addOnSuccessListener { onText(it.text) }
            .addOnCompleteListener { proxy.close() }          // हमेशा, वरना camera रुक जाएगा
    }
}
```

ज्यादातर खतरा दो लाइनों में है। `proxy.imageInfo.rotationDegrees` वही है जिसे लोग छोड़ देते हैं, और
`addOnCompleteListener` में `proxy.close()` वही है जिसे लोग गलत जगह रखते हैं — जल्दी बंद कीजिए तो आप
दोबारा इस्तेमाल हो चुके buffer को पढ़ते हैं, भूलिए तो कुछ frames बाद camera कुछ देता ही नहीं।

## साथ भेजा हुआ या उतारा हुआ

ML Kit दो तरह से आता है, और यह चुनाव build का ब्योरा नहीं, उत्पाद का असली फैसला है।

| | ऐप के साथ भेजा हुआ | Google Play services से |
| --- | --- | --- |
| ऐप का नाप | हर model के कई MB | लगभग कुछ नहीं |
| पहला इस्तेमाल | तुरंत चलता है | उतरने का इंतजार हो सकता है |
| बिना नेट | हमेशा | उतरने के बाद ही |
| सुधार | आपकी releases के साथ | अपने आप, अलग से |

ज्यादातर projects में साथ न भेजने वाला रास्ता ही चलन है, और उसकी कीमत एक ऐसी हालत है जिसे आपकी UI को
सच में सँभालना पड़ेगा: model अभी है ही नहीं। नई-नवेली install और कमजोर connection पर उपयोगकर्ता यही सबसे
पहले देखता है, तो वहाँ चुपचाप खाली screen नहीं, असली संदेश चाहिए।

<Detail summary="अपने model: नाप, delegates और नापना">
जब ML Kit वह काम नहीं करता, तो आप कोई `.tflite` model भेजते हैं और खुद चलाते हैं।

**Quantisation** पहली घुंडी है। float32 वजनों को int8 में बदलना model को करीब चार गुना छोटा और साफ तौर पर
तेज कर देता है, और थोड़े सहीपन की कीमत लेता है। ज्यादातर वर्गीकरण और पहचान के काम में वह सौदा साफ फायदे
का है; उस नुकसान को मान लेने के बजाय नापिए।

**Delegates** काम को CPU से हटाते हैं। GPU वाला delegate बड़े convolutional models की मदद करता है और छोटे
वालों के लिए CPU से धीमा भी हो सकता है, तैयारी और ढुलाई की कीमत की वजह से। नए उपकरण बनाने वालों के NPU
वाले delegates देते हैं, जो और तेज हैं और हर जगह नहीं हैं — तो delegate चलते वक्त की एक कोशिश होनी चाहिए
जिसके पीछे CPU खड़ा हो, कोई मान्यता नहीं।

**नापना** वहीं teams कोताही करती हैं। तीन अंक मायने रखते हैं, और उनमें से कोई औसत सहीपन नहीं:

- आपके सहारे दिए *सबसे सस्ते* उपकरण पर p95 अनुमान का समय, आपके सबसे अच्छे वाले पर नहीं
- लगातार पाँच मिनट चलने के बाद का समय, जब गर्मी से रफ्तार घटने लगती है
- अनुमान के दौरान memory, क्योंकि जो चोटी 8 GB पर बच जाती है वह 4 GB पर शायद नहीं

**Gemini Nano** सबसे नया विकल्प है — AICore से पहुँचा जाने वाला, उपकरण पर चलता LLM, सार बनाने, दोबारा
लिखने और बखान करने के लिए। वह थोड़े से उपकरणों पर है, तो उसका होना चलते वक्त जाँचना पड़ेगा, और पीछे कोई
असली रास्ता खड़ा रखना पड़ेगा।
</Detail>

## उपकरण पर आखिर क्यों

फोन पर अनुमान तेज है, बिना नेट चलता है, और data को किसी माँग से बाहर रखता है — जो तस्वीरों, कागजों और
आवाज के लिए अक्सर वही वजह है जिससे कोई सुविधा बनने दी जाती है। उसकी हर call की कीमत भी शून्य है, तो वह
ऐसे बढ़ता है जैसे server का कोई endpoint नहीं बढ़ता।

आप जो छोड़ते हैं वह चीजों को ठीक कर पाना है। Server वाला model एक deployment दूर है बेहतर हो जाने से;
साथ भेजा हुआ model तब बदलता है जब लोग ऐप बदलें, और अलग वाला तब जब Google भेजे। आपको उपकरणों की पूरी
कतार भी मिलती है, जहाँ आपका सहारा दिया सबसे धीमा फोन तय करता है कि वह सुविधा तुरंत लगती है या टूटी हुई।

आम हल दोनों का मेल है: आम और तेज मामले के लिए उपकरण पर चलाइए, और कभी-कभार वाले मुश्किल मामले के लिए
server पर लौट जाइए।

## आम गलतियाँ

<Pitfall title="पाँच, और पहली दो ज्यादातर गलत नतीजे हैं">
**`rotationDegrees` छोड़ देना।** Model को टेढ़ा input दिखता है और कुछ काम का नहीं लौटता।

**बेमेल सामान्य करना।** Training `-1..1` की थी, ऐप `0..1` भेजता है; नतीजा पूरे भरोसे से गलत।

**मुख्य धागे पर अनुमान।** हर frame पर दसियों milliseconds, सीधे frame के बजट पर गिरे हुए।

**अलग वाले model को मौजूद मानना।** नई install पर पहली बार कोई model नहीं है और असली संदेश चाहिए।

**अपने सबसे अच्छे फोन पर ठंडा नापना।** ऐसी सुविधा भेज देता है जो सस्ते फोन पर गरम होकर बेकार हो जाती है।
</Pitfall>

## अभ्यास

1. Camera पर text की पहचान `rotationDegrees` के साथ और उसके बिना चलाइए और नतीजे मिलाइए।
2. पूरा होने वाले listener से `proxy.close()` हटाइए और feed जमने से पहले के frames गिनिए।
3. अलग वाला model भेजिए, Play services का data मिटाइए, और वह screen गढ़िए जो उपयोगकर्ता पहले देखता है।
4. किसी float model को int8 में बदलिए और उन्हीं inputs पर नाप, देर और सहीपन नापिए।
5. पाँच मिनट अनुमान चलाइए और उपकरण के गरम होते जाने के साथ देर का नक्शा बनाइए।

## दोहराव

| चीज | एक लाइन |
| --- | --- |
| ML Kit | पूरे किए हुए काम; जहाँ वह काम आता है वहीं लीजिए |
| LiteRT | आपका अपना model, कच्चे tensors, आपकी अपनी तैयारी |
| `rotationDegrees` | Camera के buffer टेढ़े हैं; भेजिए वरना कुछ नहीं मिलेगा |
| `proxy.close()` | हमेशा, पूरा होने वाले listener में, वरना camera रुकता है |
| साथ भेजा हुआ | बड़ा ऐप, पहली बार में ही चलता, बिना नेट हमेशा |
| अलग वाला | छोटा ऐप, उतरना पड़ सकता है, UI की एक हालत चाहिए |
| Quantisation | करीब चार गुना छोटा, तेज, थोड़ा कम सही |
| Delegates | GPU या NPU आजमाइए, हमेशा CPU पर लौटिए |
| नापिए | सबसे सस्ते उपकरण पर p95, और गर्मी से रफ्तार घटने के बाद |
| सौदा | तेजी, निजता, बिना नेट, कीमत — बनाम सुधार पाने की सहूलियत |

<Interview title="Model कहाँ चले, इस पर एक सवाल">
"यह model उपकरण पर चलाएँगे या server पर?"

मैं data और नेट से शुरू करूँगा। अगर input तस्वीरें, आवाज या कागज हैं, तो उपकरण पर होने का मतलब है वह
सामग्री फोन से बाहर जाती ही नहीं, जो अक्सर वही बात है जिससे सुविधा मंजूर होती है, और वह lift के अंदर भी
चलती है और हर call पर कुछ नहीं लेती। Server वाला model सुधारना आसान है — एक deployment और हर उपयोगकर्ता
के पास बेहतर रूप है — और वह हमारे सबसे कमजोर फोन से बँधा नहीं है।

तो मैं तीन बातें पूछूँगा: क्या इसे बिना नेट चलना चाहिए, क्या data नाजुक है, और model कितनी बार बदलेगा?
बार-बार बदलना उसे server की ओर धकेलता है; नाजुक data और बिना नेट का चलना उसे उपकरण की ओर खींचते हैं।
जब दोनों जोर से खींचें, तो ईमानदार जवाब मेल है: आम मामले के लिए उपकरण पर, मुश्किल के लिए server पर। और
जो भी चुनें, मैं p95 की देर अपने सहारा दिए सबसे सस्ते उपकरण पर नापूँगा, अपने सबसे अच्छे वाले पर नहीं,
क्योंकि वही फोन तय करता है कि सुविधा तुरंत लगती है या टूटी हुई।
</Interview>
