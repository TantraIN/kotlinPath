<KeyIdea>
Composable कोई ऐसी चीज नहीं जिसे आप बनाकर फिर बदलते रहें। वह **इस बात का बयान है कि किसी एक
खास state पर screen कैसी दिखती है** — एक function, जिसे वह state बदलते ही runtime दोबारा बुला
लेता है।
</KeyIdea>

## यह क्यों जरूरी है

यह रहा एक badge, जो सिर्फ बिना पढ़े orders पर दिखना चाहिए, imperative तरीके से लिखा हुआ:

```kotlin title="Imperative.kt" numbered
fun bind(order: Order) {
    binding.title.text = order.title
    if (order.isUnread) {
        binding.badge.isVisible = true
    }
}
```

यह code गलत है, और वजह वही है जो `RecyclerView` में मिली थी: इसमें लिखा है कि badge कब दिखाना
है, और यह कहीं नहीं लिखा कि वह कब जाना चाहिए। उस row में अगली बार जो order आएगा उसे एक badge
विरासत में मिल जाएगा जो उसने माँगा ही नहीं था।

Imperative UI के हर bug की शक्ल यही है। आपने एक हालत के लिए screen बदली और दूसरी भूल गए।

## वही चीज, हुक्म देकर नहीं, बयान करके

```kotlin title="Declarative.kt" numbered
@Composable
fun OrderRow(order: Order) {
    Row {
        Text(order.title)
        if (order.isUnread) {
            Badge()
        }
    }
}
```

Badge बंद करने वाली कोई शाखा है ही नहीं, क्योंकि बंद करने के लिए कोई badge है ही नहीं। यह
function बताता है कि इस order के लिए row *है* क्या। `order` बदलेगा तो runtime इसे दोबारा बुलाएगा
और नया जवाब पा लेगा।

<Note>
`@Composable` कोई आम annotation नहीं है। यह बदल देता है कि function क्या कर सकता है और उसे बुला
कौन सकता है: सिर्फ कोई दूसरा `@Composable`। अगला पूरा पाठ इसी पर है कि compiler इसका करता क्या
है।
</Note>

<Detail summary="तो state का क्या हुआ">
State गया नहीं — जगह बदल गई। जिस composable को recompositions के आर-पार कुछ याद रखना है वह
runtime से उसे रखवाता है:

```kotlin title="Preview.kt"
var expanded by remember { mutableStateOf(false) }
```

`mutableStateOf` ऐसी value बनाता है जिस पर runtime नजर रखता है, और `remember` उसे recompositions
के बीच जिंदा रखता है। Composable के अंदर उसे पढ़ना उस composable को उससे जोड़ देता है, तो उसे
बदलने पर ठीक उतनी ही recomposition तय होती है जितनी चाहिए। दो पाठ बाद यही पूरा विषय है; अभी
इतना जान लीजिए कि state का एक मालिक है और वह कोई widget नहीं है।
</Detail>

## आम गलतियाँ

<Pitfall title="तीन जो सीधे view system से चली आती हैं">
**Composable को एक चीज समझना।** न कोई `OrderRow` instance है जिसे रखा जाए, न कोई reference
पकड़ने को, न बाद में उस पर बुलाने को कोई method। बस function है और वह state जो वह पढ़ता है।

**Function के अंदर काम कर देना।** Network call, logging, database में लिखना — composable एक ही
frame में कई बार चल सकता है, इसलिए जिस चीज का असर होता है वह side-effect API से होकर जाएगी,
सीधे body में कभी नहीं।

**क्रम की उम्मीद रखना।** आस-पास के composables के चलने का कोई तय क्रम नहीं है और वे साथ-साथ भी
चल सकते हैं। जो code इस पर टिका है कि एक दूसरे से पहले चलेगा, वह पहले से ही टूटा हुआ है।
</Pitfall>

## अभ्यास

1. ऊपर वाली imperative `bind` लीजिए और वे सारी हालतें लिख डालिए जो वह भूलती है। फिर Compose
   वाला रूप लिखिए और शाखाएँ गिनिए।
2. ऐसा composable लिखिए जो कोई label तभी दिखाए जब कोई boolean सही हो, और वह boolean किसी button
   से चलाइए। गौर कीजिए कि label छुपाने वाला code आपने लिखा ही नहीं।
3. Composable के अंदर एक `println` रखिए और देखिए कि आपके छेड़ने पर वह कितनी बार आता है।
4. ऊपर वाले quiz की गिनती क्यों नहीं चल सकती, यह किसी और को समझाइए। वही समझाना पूरी सोच का
   बदलना है।

## सारांश

| चीज | एक line |
| --- | --- |
| Composable | किसी एक state पर UI का बयान, कोई चीज नहीं |
| छोड़ता है | कुछ लौटाता नहीं; composition में nodes जोड़ता है |
| Recomposition | बदले हुए state को पढ़ने वाले composables दोबारा चलाना |
| सफाई | Body में कोई side effect नहीं — कभी नहीं |
| क्रम | तय नहीं; आस-पास वाले साथ-साथ चल सकते हैं |
| छोड़ देना | Input न बदला हो तो function शायद चले ही नहीं |
| पहचान | Source में जगह, आपका चुना कोई नाम नहीं |

"Declarative UI का यहाँ मतलब असल में है क्या?"

यह कि आप state से screen के बयान तक का एक function लिखते हैं, और दो screens के बीच का बदलाव
कभी नहीं लिखते। जोड़ने लायक line वह नाकामी है जो इससे हट जाती है: imperative का जाना-पहचाना bug
है एक शाखा जो कुछ लगाती है और उसके जोड़ की कोई शाखा नहीं जो उसे हटाए — और declarative बयान में
वह bug लिखा ही नहीं जा सकता।
</Interview>
