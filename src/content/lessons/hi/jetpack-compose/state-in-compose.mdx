<KeyIdea>
`remember` बताता है *यह value recomposition झेलेगी या नहीं*। `mutableStateOf` बताता है *इसे बदलने
से recomposition होगी या नहीं*। `rememberSaveable` बताता है *process मारे जाने पर यह बचेगी या
नहीं*। ये तीन सवाल हैं, एक नहीं।
</KeyIdea>

## यह क्यों जरूरी है

उस रूप से शुरू कीजिए जो साफ तौर पर सही लगता है:

```kotlin title="Broken1.kt"
@Composable
fun Counter() {
    var count = 0                        // हर recomposition पर वापस शून्य
    Button(onClick = { count++ }) { Text("$count") }
}
```

हर recomposition body दोबारा चलाती है, तो `count` फिर से शून्य हो जाता है। इसे ठीक कीजिए तो अगला
रूप सामने आता है:

```kotlin title="Broken2.kt"
@Composable
fun Counter() {
    var count = remember { 0 }           // बचती है, पर कोई नजर नहीं रखता
    Button(onClick = { count++ }) { Text("$count") }
}
```

अब value बनी रहती है, पर उसे बदलने से कुछ recompose नहीं होता, तो screen कभी बदलती ही नहीं।
आपको दोनों गुण चाहिए, और यही जोड़ी आपको दोनों देती है।

```kotlin title="Works.kt" numbered
@Composable
fun Counter() {
    var count by remember { mutableStateOf(0) }
    Button(onClick = { count++ }) { Text("$count") }
}
```

<Note>
`by` के लिए `androidx.compose.runtime.getValue` और `setValue` import करने पड़ते हैं। इनके बिना
delegate compile ही नहीं होता, और Compose के पहले दिन की सबसे आम error यही है।
</Note>

## `rememberSaveable` फिर से एक अलग सवाल है

```kotlin title="Saveable.kt" numbered
@Composable
fun SearchField() {
    var query by rememberSaveable { mutableStateOf("") }
    TextField(value = query, onValueChange = { query = it })
}
```

| क्या झेलता है | `remember` | `rememberSaveable` | `ViewModel` |
| --- | --- | --- | --- |
| Recomposition | हाँ | हाँ | हाँ |
| Rotation | नहीं | हाँ | हाँ |
| System का process मार देना | नहीं | हाँ | सिर्फ `SavedStateHandle` के साथ |
| बड़ा data | ठीक है | नहीं — वह `Bundle` में जाता है | हाँ |

<Warning>
`rememberSaveable` उसी नाप की हद वाले `Bundle` में लिखता है जिसमें `onSaveInstanceState` लिखता
है। वहाँ हजार items की list रखना किसी धीमे device पर आने वाला `TransactionTooLargeException` है।
Id सँभालिए, data दोबारा लाइए।
</Warning>

<Detail summary="ऐसा type सँभालना जिसे Bundle नहीं समझता">
जो चीज खुद `Parcelable` नहीं है उसे `Saver` चाहिए — दो functions की जोड़ी, जो उसे `Bundle` के
मानने लायक रूप में बदलती और वापस लाती है।

```kotlin title="Saver.kt" numbered
data class Selection(val from: Int, val to: Int)

val SelectionSaver = listSaver<Selection, Int>(
    save = { listOf(it.from, it.to) },
    restore = { Selection(it[0], it[1]) },
)

var selection by rememberSaveable(stateSaver = SelectionSaver) {
    mutableStateOf(Selection(0, 0))
}
```

`mapSaver` और `listSaver` लगभग सब कुछ सँभाल लेते हैं। Class आपके अपने हाथ में हो तो उस पर
`@Parcelize` लगाना छोटा रास्ता है।
</Detail>

## Lists वहाँ हैं जहाँ state चुपचाप काम करना बंद कर देता है

```kotlin title="Lists.kt" numbered
// गलत: list वाली चीज कभी बदलती ही नहीं, तो कुछ recompose नहीं होता
val items = remember { mutableListOf<String>() }
items.add("new")

// सही: state समझने वाली list
val items = remember { mutableStateListOf<String>() }
items.add("new")

// यह भी सही: value की जगह नई list रख दीजिए
var items by remember { mutableStateOf(emptyList<String>()) }
items = items + "new"
```

Compose सिर्फ *किसी `State` में लिखा जाना* देखता है, और कुछ नहीं। सादी collection बदलना किसी
state में लिखना नहीं है, तो runtime को खबर ही नहीं होती कि कुछ हुआ।

## आम गलतियाँ

<Pitfall title="चार, जिनसे ज्यादातर state वाले bugs बनते हैं">
**बदलते parameter पर बिना key वाला `remember`।** ऊपर वाला जाना-पहचाना बासी-field bug।

**सादी `List`, `Map` या `Set` बदलना।** किसी state में लिखा ही नहीं गया, तो recomposition भी नहीं
होती। `mutableStateListOf` लीजिए, या पूरी value बदल दीजिए।

**किसी भी बड़ी चीज के लिए `rememberSaveable`।** वह saved-state वाले `Bundle` में सवारी करती है।
इसे ids, text fields, scroll की जगह और झंडों तक ही रखिए।

**जो screen का है उसे composable में रखना।** `ViewModel` के पास वाली state rotation और process
मरना मुफ्त में झेल जाती है और बिना device के test हो सकती है। `remember` उस state के लिए है जो
सच में सिर्फ UI के इस टुकड़े की है।
</Pitfall>

## अभ्यास

1. Counter तीन बार बनाइए — सादा `var`, अकेला `remember`, और दोनों — और चलाने से पहले हर बार नतीजा
   बताइए।
2. किसी parameter के साथ बासी-field वाला bug दोबारा पैदा कीजिए, फिर एक बार key से और एक बार
   दोहरी state हटाकर ठीक कीजिए। तय कीजिए कि आपको कौन सा ज्यादा पसंद है और क्यों।
3. `remember` वाले `TextField` में लिखिए, घुमाइए, और उसे खाली होते देखिए। `rememberSaveable` पर
   जाइए और दोबारा घुमाइए।
4. `remember` के अंदर `mutableListOf` में items जोड़िए और कुछ न होते देखिए। एक शब्द बदलिए और उसे
   चलते देखिए।
5. Saveable field भरी हुई रखकर app को recents से हटाइए, दोबारा खोलिए, और देखिए क्या वापस आया।

## सारांश

| चीज | एक line |
| --- | --- |
| `remember` | Recomposition झेलती है, इससे ज्यादा कुछ नहीं |
| `mutableStateOf` | इसमें लिखना उसके पाठकों की recomposition कराता है |
| दोनों साथ | यहीं की UI state रखने का आम तरीका |
| `by` | Delegate वाला रूप; `getValue` / `setValue` के imports चाहिए |
| `remember(key)` | Key बदलने पर दोबारा निकालता है |
| `rememberSaveable` | `Bundle` के जरिए rotation और process मरना भी झेलती है |
| `Saver` | उन types के लिए जिन्हें `Bundle` नहीं रख सकता |
| `mutableStateListOf` | ऐसी list जिसके बदलाव दिखते हैं |
| `ViewModel` | Screen की state की जगह; `remember` सिर्फ UI वाली state के लिए |

<Interview title="तीन जवाबों वाला सवाल, और तीनों चाहिए">
"`remember` और `rememberSaveable` में फर्क क्या है?"

`remember` value सिर्फ recompositions के आर-पार रखता है; `rememberSaveable` उसे saved instance
state में लिखकर configuration बदलने और process मरने पर भी बचा लेता है। तीसरा हिस्सा इसे पूरा
करता है: इसी वजह से `rememberSaveable` को `Bundle` की नाप की हद विरासत में मिलती है, तो वह ids और
field के text के लिए है, और उससे बड़ी चीज `SavedStateHandle` वाले `ViewModel` की है।
</Interview>
