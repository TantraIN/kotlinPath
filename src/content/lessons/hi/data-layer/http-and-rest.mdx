<KeyIdea>
HTTP एक request है, फिर एक response। इस परत पर ऐप जो कुछ गलत करता है वह इन चार में से एक होता है:
उसने कौन सा **method** चुना, कौन सा **status** अनदेखा किया, कौन से **headers** कभी सेट ही नहीं किए,
या body को क्या मान बैठा। Exchange पढ़ना आ जाए तो network के bugs अटकल रह ही नहीं जाते।
</KeyIdea>

## यह क्यों जरूरी है

Retrofit दस मिनट में किसी interface को चलता हुआ network code बना देता है, और दिक्कत ठीक यही है। जिस
दिन कोई request एक device पर 401 और दूसरे पर 200 लौटाए, या Wi-Fi पर चले और mobile data पर न चले,
उस दिन Retrofit का कितना भी ज्ञान काम नहीं आता — जवाब उस exchange के अंदर होता है।

HTTP request एक शक्ल वाला text है:

```http title="Request" numbered
GET /v1/orders?status=open&limit=20 HTTP/1.1
Host: api.example.com
Authorization: Bearer eyJhbGciOi...
Accept: application/json
```

और response की शक्ल भी वही है, बस आगे एक संख्या लगी होती है:

```http title="Response" numbered
HTTP/1.1 200 OK
Content-Type: application/json
Cache-Control: max-age=60
ETag: "a4f1c9"

{"orders":[{"id":"o_18","total":499}]}
```

वह संख्या, वे headers और वह body — आप जो भी network परत लिखेंगे वह इन्हीं तीन चीजों को सँभाल रही
होगी। Retrofit इन्हें हटाता नहीं; annotations के अंदर सरका देता है।

## Methods, और phone पर जो बात असल में मायने रखती है

REST कामों पर verbs चढ़ाता है, पर phone पर जो फर्क अपनी कीमत वसूल करता है वह create बनाम update
नहीं है। वह यह है कि एक ही request दो बार भेजना सुरक्षित है या नहीं।

| Method | किसलिए | Safe | Idempotent |
| --- | --- | --- | --- |
| `GET` | पढ़ना | हाँ | हाँ |
| `HEAD` | सिर्फ headers पढ़ना | हाँ | हाँ |
| `PUT` | जानी-पहचानी id पर पूरा बदल देना | नहीं | हाँ |
| `DELETE` | हटाना | नहीं | हाँ |
| `PATCH` | थोड़ा-सा बदलना | नहीं | आमतौर पर नहीं |
| `POST` | बनाना, या और कुछ भी | नहीं | नहीं |

**Safe** का मतलब है कि server पर कुछ बदलता ही नहीं। **Idempotent** का मतलब है कि दो बार करने पर
वही हालत बचती है जो एक बार करने पर।

यह इसलिए मायने रखता है कि mobile networks सबसे बुरे तरीके से नाकाम होते हैं: request पहुँच जाती है,
server अपना काम कर देता है, और response लौटते वक्त खो जाता है। Client को timeout दिखता है, और वह
इसे request के कभी न पहुँचने से अलग नहीं बता सकता। `GET` दोबारा भेजने की कोई कीमत नहीं। किसी card
से पैसे काटने वाला `POST` दोबारा भेजने पर पैसे दो बार कटते हैं।

## Status codes, और वह बँटवारा जो आपकी error handling तय करता है

पहला अंक बता देता है कि दिक्कत किसके पास है — और आपकी error handling को भी यही सवाल हल करना है।

जिन्हें नाम से जानना चाहिए:

| Code | मतलब | ऐप को क्या करना चाहिए |
| --- | --- | --- |
| `200` | OK | Body पढ़िए |
| `201` | Created | नई id पढ़िए, अक्सर `Location` header से |
| `204` | No content | काम हो गया, और body है ही नहीं — उसे पढ़ने मत जाइए |
| `304` | Not modified | आपकी रखी हुई copy अब भी ठीक है |
| `400` | Bad request | गलती आपकी; दोबारा भेजने पर वही नाकामी |
| `401` | Unauthenticated | कोई सही पहचान नहीं — token refresh कीजिए |
| `403` | Forbidden | पहचान ठीक है, इजाजत नहीं — refresh करने से कुछ नहीं बदलेगा |
| `404` | Not found | या तो वह चीज नहीं है, या path गलत है |
| `409` | Conflict | आपके नीचे कुछ बदल गया |
| `429` | Too many requests | रुकिए, और `Retry-After` पढ़िए |
| `500` | Server error | गलती आपकी नहीं; दोबारा भेजने से चल सकता है |
| `503` | Unavailable | कुछ देर की बात है; रुककर भेजिए |

`401` और `403` का फर्क वही है जो असली bugs पैदा करता है। दोनों को एक जैसा मानने पर ऐसा ऐप बनता है
जो इजाजत वाली हर error पर token refresh करने चलता है, नाकाम होता है, फिर refresh करता है, और user
को उस screen से लॉग आउट कर देता है जिसे खोलने की उसे बस इजाजत नहीं थी।

<Note>
`4xx` का मतलब है कि जब तक कुछ बदले नहीं, दोबारा भेजना बेकार है; `5xx` और `429` का मतलब है कि रुककर
दोबारा भेजना ठीक है। पूरी retry नीति बस यही एक वाक्य है, और इसीलिए हर नाकामी पर दोबारा भेजने वाला
interceptor उस interceptor से बुरा है जो कभी दोबारा नहीं भेजता।
</Note>

## वे headers जो ऐप सच में सेट करता है

```kotlin title="Headers.kt" numbered
// Retrofit और OkHttp दोनों इन्हें कह सकते हैं; मतलब दोनों जगह वही है
"Content-Type: application/json"          // मैं क्या भेज रहा हूँ
"Accept: application/json"                // मैं वापस क्या पढ़ सकता हूँ
"Authorization: Bearer $token"            // मैं हूँ कौन
"Accept-Language: hi-IN"                  // जवाब किस भाषा में
"If-None-Match: \"a4f1c9\""               // body तभी भेजिए जब बदली हो
```

`Content-Type` और `Accept` उलटी दिशाओं की चीजें हैं और लगातार आपस में उलझती हैं: एक आपकी body के
बारे में है, दूसरा उस response के बारे में जो आपको चाहिए। `415 Unsupported Media Type` लौटाता
server पहले वाली की शिकायत कर रहा है; `406 Not Acceptable` लौटाता server दूसरी की।

<Detail summary="Conditional requests, और 304 जोड़ने लायक क्यों है">
Server एक `ETag` भेजता है — एक छोटी-सी बेमतलब दिखती string, जो उस चीज के ठीक उसी रूप की पहचान है।
Client उसे रख लेता है और अगली request में वापस भेजता है:

```http title="Conditional GET" numbered
GET /v1/orders HTTP/1.1
If-None-Match: "a4f1c9"
```

अगर कुछ नहीं बदला, तो जवाब यह है:

```http title="Response" numbered
HTTP/1.1 304 Not Modified
ETag: "a4f1c9"
```

कोई body नहीं। जिस list को हर तीस सेकंड में पूछा जाता है, उस पर यह ज्यादातर responses को कुछ सौ
किलोबाइट से घटाकर चंद दर्जन bytes कर देता है, और गिने-चुने data पर यह बचत असली होती है।

आगे के phases के लिए बात यह है: अगर server cache वाले headers भेजता है और आपने OkHttp को cache की
जगह दे रखी है, तो यह सब वह खुद कर लेता है। ज्यादातर ऐप वह जगह कभी सेट ही नहीं करते, और हर
न-बदले response की पूरी कीमत चुकाते हैं।
</Detail>

## REST आपसे माँगता क्या है

REST कुछ शर्तों का नाम है, और Android के किसी codebase में उनमें से दो ही दिखती हैं:

**चीजें संज्ञा हैं, और verb method में है।** `POST /v1/orders` एक order बनाता है।
`POST /v1/createOrder` वही call है, बस भेस बदलकर — path एक काम का नाम ले रहा है, तो method अब कोई
जानकारी नहीं ढो रहा और कोई proxy पढ़ने और लिखने में फर्क नहीं कर सकता।

**हर request अपने आप में पूरी है।** Server को आपकी पिछली call याद नहीं रहती, इसीलिए हर request अपना
`Authorization` header खुद लेकर चलती है। यही याद न रखना retry को काम करने लायक बनाता है, और यही
वजह है कि ऐप के पास session नहीं, एक token होता है।

बहुत सारी असली APIs सिर्फ ढीले-ढाले तरीके से RESTful होती हैं। यह ठीक है — आप client हैं, और काम
यह है कि server सच में करता क्या है उसका model बनाइए, यह नहीं कि उसे करना क्या चाहिए था।

## आम गलतियाँ

<Pitfall title="पाँच, जिनकी कीमत एक release होती है">
**हर गैर-2xx को exception मान लेना।** किसी search endpoint पर `404` का मतलब अक्सर "कुछ नहीं मिला"
होता है, जो एक आम हालत है, crash नहीं। हर endpoint के लिए खुद तय कीजिए कि असामान्य क्या है।

**आँख मूँदकर दोबारा भेजना।** `400` पर दोबारा भेजना हर बार नाकाम होगा और बस error में देर कराएगा।
Idempotent न होने वाले `POST` पर दोबारा भेजना पैसे दो बार काट सकता है।

**`Retry-After` अनदेखा करना।** `429` आपको बता देता है कि कितनी देर रुकना है। उसकी जगह अपने अंदाजे
से रुकना ही वह रास्ता है जिससे rate limit एक ban बन जाती है।

**यह मान लेना कि body है।** `204` या `304` की body पढ़ने पर exception आता है, और वह exception JSON
का नाम लेता है, उस status code का नहीं जिसकी वजह से आया — इसीलिए उसमें एक दोपहर चली जाती है।

**Base URL का slash गलत रखना।** Retrofit के base URL का अंत `/` पर होना चाहिए, और endpoint के path
के आगे लगा `/` जोड़ने के बजाय पूरा base path ही बदल देता है। दोनों उस server पर `404` देते हैं जो
बिलकुल ठीक चल रहा है।
</Pitfall>

## अभ्यास

1. `curl -i https://api.github.com/users/torvalds` चलाइए और body से पहले हर header पढ़िए।
2. `curl -i -H 'Accept: application/xml' https://api.github.com/users/torvalds` भेजिए और देखिए कि
   जो request server पूरी नहीं कर सकता उसका वह क्या करता है।
3. किसी response से `ETag` लीजिए और उसे `If-None-Match` बनाकर वापस भेजिए। `304` और खाली body पक्की
   कीजिए।
4. आप जो ऐप इस्तेमाल करते हैं उसकी हर call गिनाइए, और हर एक पर safe, idempotent, या इनमें से कुछ
   नहीं लिखिए। "कुछ नहीं" वाला खाना ही आपकी retry के खतरों की सूची है।
5. लिख लीजिए कि `401`, `403`, `429` और `503` पर आपके ऐप को क्या करना चाहिए। अगर इनमें से दो का जवाब
   एक ही है, तो देखिए कि वह जानबूझकर है या नहीं।

## दोहराव

| चीज | एक लाइन |
| --- | --- |
| HTTP | एक request और एक response, दोनों में headers और चाहें तो body |
| Safe | Server पर कुछ नहीं बदलता |
| Idempotent | दो बार का असर वही जो एक बार का |
| Idempotency key | `POST` को दोबारा भेजने लायक बना देती है |
| `2xx` / `3xx` | काम हुआ / कहीं और देखिए |
| `4xx` / `5xx` | आपकी request / उनका server — यहीं retry का फैसला होता है |
| `401` बनाम `403` | Token refresh कीजिए बनाम रहने ही दीजिए |
| `Content-Type` बनाम `Accept` | मैं क्या भेज रहा हूँ बनाम मुझे क्या चाहिए |
| `ETag` + `If-None-Match` | कुछ न बदले तो `304` और कोई body नहीं |
| REST | Path में संज्ञा, method में verb, server के पास कोई session नहीं |

<Interview title="एक सवाल, जो असल में retries के बारे में है">
"जो network request timeout हो जाए, उसे आप कैसे सँभालेंगे?"

सबसे पहले यह पूछकर कि वह request idempotent है या नहीं, क्योंकि बाकी सब यही तय करता है। `GET` को
बढ़ते हुए अंतराल के साथ बेझिझक दोबारा भेजा जा सकता है। `POST` को नहीं: timeout यह नहीं बताता कि
server ने काम किया या नहीं, तो आँख मूँदकर दोबारा भेजने पर काम दो बार होने का खतरा है। उनके लिए मैं
एक idempotency key भेजूँगा, जो user के हर एक काम पर एक बार बनती है, ताकि server दोबारा आई request
को पहचानकर वही पहला नतीजा लौटा दे। इसके बाद मैं सिर्फ `5xx`, `429` और सच्ची I/O नाकामियों पर दोबारा
भेजूँगा — `4xx` पर कभी नहीं, जहाँ दिक्कत request में ही है और दोबारा भेजना error में देर के अलावा
कुछ नहीं करता — और जब server `Retry-After` भेजे तो उसे मानूँगा।
