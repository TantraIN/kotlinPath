<KeyIdea>
हर test **रफ्तार** और **भरोसे** के बीच सौदा करता है। Unit test milliseconds में चलता है और एक फैसला
साबित करता है; UI test एक मिनट लेता है और साबित करता है कि पूरी चीज चलती है। पिरामिड कहता है कि
ज्यादातर tests वहाँ रखिए जहाँ वे सस्ते हैं, और महँगे वालों को उसी के लिए बचाइए जो सिर्फ वे साबित कर
सकते हैं।
</KeyIdea>

बताता है कि *कुछ* टूटा — शायद emulator।

## जाँचना असल में क्या है

काम का सवाल यह नहीं है कि "हमारा coverage कितना है" बल्कि यह कि **पिछले पाँच bugs को पकड़ता कौन**।
Android ऐप में उसका जवाब आमतौर पर वही छोटी सूची होती है:

- **शाखाओं वाला तर्क।** जिसमें भी `when`, कोई हद, या कोई error वाला रास्ता हो। Network वाले पाठ का
  दोबारा भेजने वाला फैसला — `5xx` दोबारा जाता है, `400` नहीं — status code का सादा function है, और
  उसका unit test तीन लाइनों का है।
- **बदलना।** DTO से domain, domain से UI की state. यहीं नाम बदली हुई कोई field चुपचाप `null` बन जाती
  है।
- **State निकालना।** इस घटना और इस मौजूदा हालत को देखते हुए, अगली हालत क्या है।
- **जो एक बार गलत हो चुका।** Bug के बाद लिखा test वही है जिसके अपनी कीमत वसूलने की सबसे ज्यादा
  संभावना है।

और जो आमतौर पर जाँचने लायक नहीं: getters, `data class` की बराबरी, ऐसा code जो सिर्फ किसी और को call
आगे बढ़ाता है, और framework का बर्ताव। जो test यह जाँचे कि Room row सहेजता है वह Room को जाँच रहा है।

## जहाँ चल जाए, mocks नहीं नकली चीजें

```kotlin title="FakeRepository.kt" numbered
class FakeOrderRepository : OrderRepository {
    var result: Outcome<List<Order>> = Outcome.Success(emptyList())
    private val orders = MutableStateFlow<List<Order>>(emptyList())

    override fun observeOrders(): Flow<List<Order>> = orders
    override suspend fun refresh(): Outcome<Unit> = result.map {}
    fun emit(new: List<Order>) { orders.value = new }        // test इसी को चलाता है
}
```

नकली चीज एक चलता हुआ implementation है जिसका अंदरूनी हिस्सा आसान कर दिया गया है। उसका असली बर्ताव है
— कुछ रखिए और वह वापस मिलता है — तो test कामों की एक कड़ी की तरह पढ़ा जाता है, न कि नकली बनाई गई calls
की सूची की तरह।

Mocks तब सही हैं जब आपको किसी *लेन-देन* पर दावा करना हो: कि token refresh की कोशिश ठीक एक बार हुई, कि
analytics चला। बाकी हर चीज के लिए नकली चीज ऐसे tests बनाती है जो code दोबारा सजाने पर भी बचते हैं,
क्योंकि वे बताते हैं कि code करता क्या है, न कि किन methods को बुलाता है।

<Detail summary="बर्ताव जाँचना, बनावट नहीं">
कोई test suite बोझ बनने के जिस रास्ते सबसे ज्यादा जाती है वह है बनावट पर दावा करना:

```kotlin title="Brittle.kt" numbered
verify(exactly = 1) { repository.fetchOrders() }          // cache जोड़ते ही टूटता है
verify { mapper.toDomain(any()) }                          // mapper अंदर ले जाते ही टूटता है
assertEquals(3, viewModel.internalCache.size)              // निजी बारीकी जाँच रहा है
```

इनमें से हर एक तब नाकाम होता है जब code बिना अपना काम बदले दोबारा सजाया जाता है — तो हर refactor उन
tests को सुधारने की एक दोपहर बन जाता है जिन्होंने कभी कोई bug नहीं पकड़ा। Suite सुरक्षा जाल होना छोड़कर
अड़चन बन जाती है, और आमतौर पर नतीजा यह होता है कि लोग उस पर भरोसा करना छोड़ देते हैं।

वही इरादा, बर्ताव की तरह लिखा हुआ:

```kotlin title="Durable.kt" numbered
repository.result = Outcome.Failure(DataError.Network.Offline)
viewModel.refresh()
assertEquals(UiText.Res(R.string.offline), viewModel.state.value.error)
```

वह test तब भी पास होता है जब cache हो या न हो, mapper अंदर हो या बाहर, repository दोबारा लिखा गया हो
— और ठीक तब नाकाम होता है जब user को गलत चीज दिखती। मोटा नियम: उस पर दावा कीजिए जो class से बाहर
निकलता है, उस पर नहीं जो उसके अंदर होता है।
</Detail>

## आम गलतियाँ

<Pitfall title="पाँच, जिनसे ऐसी suite बनती है जिस पर कोई भरोसा नहीं करता">
**Coverage के आँकड़े के पीछे भागना।** वह नापता है कि कौन सी लाइनें चलीं, यह नहीं कि ऐप चलता है।

**Framework को जाँचना।** यह दावा करना कि Room row सहेजता है, या कि `data class` बराबर निकलता है।

**नतीजों के बजाय calls जाँचना।** Refactor पर test टूटता है और कोई bug पकड़ता नहीं।

**जिसे unit test साबित कर सकता था उसके लिए UI test।** Milliseconds के बजाय मिनट, और गैर-भरोसेमंद।

**जोड़ों पर कोई test न होना।** सब कुछ unit tested, और यह साबित करने वाला कुछ नहीं कि हिस्से जुड़ते हैं।
</Pitfall>

## अभ्यास

1. पिछले पाँच bugs गिनाइए जो आपने ठीक किए और लिखिए कि हर एक को कौन सा स्तर पकड़ता।
2. किसी error वाले type पर लिखे `when` की हर शाखा का unit test लिखिए।
3. किसी एक test में mock की जगह नकली चीज रखिए और देखिए कि test छोटा होता है या नहीं।
4. ऐसा test ढूँढ़िए जो किसी निजी method का नाम बदलने पर टूट जाए, और उसे बर्ताव के हिसाब से दोबारा
   लिखिए।
5. एक सादा test लिखिए जो ऐप चलाकर देखे कि पहली screen बनती है।

## दोहराव

| चीज | एक लाइन |
| --- | --- |
| सौदा | हर स्तर पर, रफ्तार बनाम भरोसा |
| Unit | Milliseconds, एक फैसला, सिर्फ JVM |
| Integration | सेकंड, असली साथी, साबित करता है कि हिस्से बैठते हैं |
| UI | मिनट, असली device, साबित करता है कि user पूरा कर सकता है |
| सवाल | पिछले पाँच bugs को पकड़ता कौन |
| जाँचने लायक | शाखाएँ, बदलना, state निकालना, पुराने bugs |
| जाँचने लायक नहीं | Getters, `data class` की बराबरी, framework का बर्ताव |
| नकली चीज | चलता हुआ implementation, आसान अंदरूनी हिस्से के साथ |
| Mock | यह दावा करने के लिए कि कोई लेन-देन हुआ |
| Coverage | जो चला उसका नक्शा, चलने का सबूत नहीं |

<Interview title="एक सवाल, जिसका गलत जवाब कोई आँकड़ा है">
"किसी project का test coverage कितना होना चाहिए?"

मैं कोई आँकड़ा निशाना नहीं बनाऊँगा, क्योंकि coverage नापता है कि कौन सी लाइनें चलीं, यह नहीं कि ऐप
चलता है — कोई suite नब्बे प्रतिशत पर हो सकती है और फिर भी ऐसी release छूट सकती है जिसमें कोई screen
लदती ही नहीं, अगर हर test ने अपनी चीज सीधे बनाई और किसी ने असली object का graph जोड़ा ही नहीं।

मैं असल में यह चाहता हूँ कि जिन चीजों के टूटने की सबसे ज्यादा संभावना है वे उस सबसे सस्ते स्तर पर
जाँची जाएँ जो उन्हें साबित कर सके। शाखाओं वाला तर्क, बदलना और state निकालना unit tests हैं, क्योंकि
वे अपने input के सादे functions हैं और milliseconds में चलते हैं। जिसमें भी असली SQL या असली JSON है
वह integration test है, क्योंकि कोई नकली चीज मुझे यह नहीं बता सकती कि मेरी query सही है। और पूरे
सफरों के लिए मैं गिने-चुने UI tests रखता हूँ, क्योंकि वे धीमे हैं और मेरे code से बेमतलब वजहों से
नाकाम होते हैं — पर वही इकलौती चीज हैं जो साबित करती है कि हिस्से आपस में जुड़ते हैं।
</Interview>
