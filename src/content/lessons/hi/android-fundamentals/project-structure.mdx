<KeyIdea>
Module का code एक folder में नहीं होता। हर build के लिए Gradle कई **source sets** जोड़कर एक
बनाता है, और जोड़ने के नियम code के लिए अलग हैं, resources के लिए अलग।
</KeyIdea>

## यह क्यों जरूरी है

आपका पहला project पूरा भरा हुआ आता है। कहीं यह नहीं लिखा कि कौन से folders आपके हैं, कौन से
Gradle दोबारा बनाता है, और कौन से हटाना safe है।

तो लोग files गलत जगह रखते हैं, generated output commit कर देते हैं, और duplicate class वाली
एक error में घंटों निकल जाते हैं — जबकि एक line का नियम उसे समझा देता।

**Module** वह इकाई है जिसे Gradle compile करता है। शुरू में एक module ही आम बात है; और modules
जोड़ने की वजह build speed और साफ हदें होती हैं, जो Phase 11 में आएगा।

## `src/` के अंदर: source sets

```text title="app/src/" no-glossary
main/
  AndroidManifest.xml
  java/com/example/myapp/     <- Kotlin भी यहीं रहता है
  res/                        <- compile होने वाले resources
  assets/                     <- कच्ची files, जैसी की वैसी
debug/
  res/values/strings.xml      <- main को दबा देता है, सिर्फ debug builds में
```

| Source set | कहाँ जाता है | आम इस्तेमाल |
| --- | --- | --- |
| `main` | हर build में | लगभग सब कुछ जो आप लिखते हैं |
| `debug` / `release` | सिर्फ उसी build type में | अलग server URL, सिर्फ debug वाली screen |
| `test` | JVM test चलने पर | Unit tests, बिना Android framework |
| `androidTest` | Device test चलने पर | UI tests, जिन्हें असली `Context` चाहिए |

## अंदर की बात: build असल में merge क्या करता है

<Timeline>
  <TimelineItem title="Manifests" meta="merge होते हैं">
    आपका manifest, हर library का manifest, और build type का manifest — तीनों मिलकर एक बनते हैं।
    टकराने वाले attributes तब तक error हैं जब तक आप साफ-साफ हल न कर दें।
  </TimelineItem>
  <TimelineItem title="Resources" meta="merge, ज्यादा खास वाला जीतता है">
    Build type flavour से जीतता है, flavour `main` से, और आपका module अपनी libraries से। एक ही
    नाम मतलब override, duplicate नहीं।
  </TimelineItem>
  <TimelineItem title="Kotlin और Java" meta="जुड़ते हैं">
    उस variant के सारे source sets एक ही compile path पर आ जाते हैं। दो में एक ही class नाम
    error है, override नहीं।
  </TimelineItem>
  <TimelineItem title="R class" meta="generated">
    हर resource का नाम आपके `namespace` के नीचे एक constant बन जाता है। इसीलिए layout का नाम
    बदलने पर compile टूटता है, runtime पर नहीं।
  </TimelineItem>
</Timeline>

<Detail summary="Library के resources चुपचाप आपकी app क्यों बदल सकते हैं">
Library के resources आपके साथ merge होते हैं, और बराबरी में आपका module जीतता है। तो जो library
`colors.xml` में `primary` भेजती है, वह आपके `primary` से हार जाएगी — चुपचाप, बिना किसी warning
के।

इसीलिए library लिखने वाले हर नाम के आगे कुछ लगाते हैं (`mtrl_`, `abc_`), और इसीलिए किसी shared
module में `title` या `background` जैसा छोटा resource नाम आगे चलकर टकराने वाला नाम मानकर चलिए।
</Detail>

## आम गलतियाँ

<Pitfall title="तीन जो सच में समय खाती हैं">
**`src/debug` से `src/main` वाली class के दबने की उम्मीद।** वे जुड़ते हैं, तो duplicate class
error मिलती है। Class को *दोनों* build type source sets में रखिए और `main` में कहीं नहीं, या
उसकी जगह `BuildConfig` field इस्तेमाल कीजिए।

**`build/` commit कर देना।** वह हर build पर दोबारा बनता है और बहुत बड़ा होता है। उसकी जगह
`.gitignore` है, `.gradle/` और `local.properties` के साथ।

**Generated file को edit करना।** `build/` के नीचे जो भी है — `R` class समेत — अगली build पर
दोबारा लिख दिया जाता है। बदलना हो तो वह input बदलिए जिससे वह बना।
</Pitfall>

## अभ्यास

1. `src/debug/res/values/strings.xml` जोड़िए जिसमें `app_name` `main` से अलग हो। दोनों build
   types install कीजिए और launcher का नाम पढ़िए।
2. अब वही एक Kotlin file के साथ कीजिए जो `main` और `debug` दोनों में एक ही class declare करे।
   Error पढ़िए, फिर दो अलग तरीकों से ठीक कीजिए।
3. एक छोटी JSON file `assets/` में रखिए और वही data `res/raw/` में। दोनों को code से खोलिए और
   नाम गलत लिखने पर क्या होता है, यह मिलाइए।
4. `./gradlew :app:dependencies` चलाइए और एक ऐसी library ढूँढ़िए जिसके resources आपके साथ merge
   होते हैं।

## सारांश

| चीज | एक line |
| --- | --- |
| Module | वह इकाई जिसे Gradle compile करता है; `app/` आपका पहला |
| Source set | किसी खास build के लिए code और resources वाला folder |
| `main` | हर variant में जाता है |
| Code merging | जुड़ता है — एक जैसे class नाम error हैं |
| Resource merging | दबता है — ज्यादा खास source set जीतता है |
| `res/` बनाम `assets/` | Compile और index, बनाम कच्ची copy |
| `build/` | Generated; न छेड़िए, न commit कीजिए |

बताता है कि आप source set वाले नियम से सच में टकरा चुके हैं।
