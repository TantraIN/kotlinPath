<KeyIdea>
Kotlin में class को तब तक बढ़ाया नहीं जा सकता जब तक आप `open` न लिखें। Inheritance एक सोच-समझकर लिया
फैसला है, गलती से मिला हुआ default नहीं।
</KeyIdea>

```kotlin title="Payment.kt" numbered runnable
open class Payment(val amount: Int) {
    open fun fee(): Int = 0
    fun receipt(): String = "Paid $amount, fee ${fee()}"
}

class Card(amount: Int) : Payment(amount) {
    override fun fee(): Int = amount / 50
}

class Upi(amount: Int) : Payment(amount) {
    override fun fee(): Int = 0
}

fun main() {
    val payments = listOf(Payment(100), Card(500), Upi(500))
    payments.forEach { println(it.receipt()) }
}
```

ध्यान दीजिए कि `receipt()` `open` नहीं है, फिर भी वह `fee()` को बुलाता है जो `open` है। एक method
पक्का है, दूसरा एक खाली जगह है जिसे subclasses भरती हैं। पूरा idea यही है।

## तीन keywords, हर एक का एक नियम

| Keyword | मतलब |
| --- | --- |
| Class पर `open` | इस class को बढ़ाया जा सकता है |
| Member पर `open` | इस member को बदला जा सकता है |
| `override` | यह member ऊपर वाले `open` member की जगह लेता है |
| `final override` | जगह लेता है, और सिलसिला यहीं रोक देता है |
| `super.x()` | जिसे मैंने अभी बदला, वही वाला चलाओ |

<Detail summary="Kotlin ने classes default से बंद क्यों कीं, Java ने क्यों नहीं">
Java में हर class बढ़ाई जा सकती थी जब तक `final` न लिखें, इसलिए library लिखने वाले को हर खतरनाक
subclass पहले से सोचकर रोकनी पड़ती थी। असल में कोई नहीं रोकता था, और fragile base class की समस्या
आती थी: superclass का एक method बदलिए और ऐसी subclasses टूट जाएँ जिनके होने का पता भी न हो। Kotlin
ने default उल्टा कर दिया। अब वही चीज बढ़ाई जा सकती है जिसके बारे में लिखने वाले ने सोचा हो।
</Detail>

## `super` — पुराना behaviour रखकर उसमें जोड़ना

```kotlin title="Super.kt" numbered runnable
open class Logger {
    open fun log(message: String) = println("LOG: $message")
}

class TimestampLogger : Logger() {
    override fun log(message: String) {
        super.log("[12:04] $message")     // दोबारा लिखिए मत, इस्तेमाल कीजिए
    }
}

fun main() = TimestampLogger().log("saved")
```

## आम गलतियाँ

<Pitfall title="दो जो असली bugs बनाती हैं">
**Constructor या `init` से `open` method बुलाना।** Subclass की अपनी properties तब तक assign हुई ही
नहीं होतीं, इसलिए override आधे-अधूरे state पर चलता है और `null` या `0` पढ़ता है। Construction के
दौरान overridable method कभी मत बुलाइए।

**Code बाँटने के लिए inheritance इस्तेमाल करना।** अगर `Card` और `Upi` को सिर्फ एक ही helper चाहिए,
तो वह `is-a` रिश्ता नहीं है — वह एक साझा function है। Inheritance subclass को base के हर आने वाले
बदलाव से बाँध देता है। Composition बेहतर है, या default वाला interface।
</Pitfall>

## अभ्यास

1. एक `Wallet` payment जोड़िए जिसकी fee सीधी 5 हो। देखिए कि `receipt()` उसे बिना `Payment` छुए उठा
   लेता है।
2. `Card` में `fee()` को `final override` कीजिए, फिर `Card` को बढ़ाकर उसे दोबारा override करने की
   कोशिश कीजिए। Compiler की गलती पढ़िए।
3. `Payment` के `init` में एक `println` डालिए जो `fee()` बुलाए, फिर `Card` बनाइए। जो number मिला उसे
   समझाइए।
4. पूरे ढाँचे को ऐसे लिखिए कि `fee()` open class की जगह interface से आए। पाँचवाँ payment type जोड़ने
   पर कौन सा version ज्यादा आराम से झेलता है?

## सारांश

| स्थिति | क्या उठाएँ |
| --- | --- |
| Subtypes state और behaviour दोनों बाँटें | `open class` + `override` |
| Subtypes सिर्फ behaviour बाँटें | Default वाला interface |
| Reuse चाहिए, `is-a` नहीं | Composition — दूसरे object को रखिए |
| Subtypes का set तय और पता हो | `sealed` — आगे के lesson में |
