<KeyIdea>
`data` बराबरी का मतलब **एक जैसी values** कर देता है, **एक ही object** नहीं। बस इसी एक बदलाव की वजह
से data class को `Set`, `Map` key या Compose state में रखना सुरक्षित है।
</KeyIdea>

## यह कौन सी समस्या हल करता है

```kotlin title="Equality.kt" numbered runnable
class PlainUser(val id: Int)
data class DataUser(val id: Int)

fun main() {
    println(PlainUser(1) == PlainUser(1))   // false — अलग objects
    println(DataUser(1) == DataUser(1))     // true  — एक जैसी values
}
```

बिलकुल एक जैसे contents वाले दो `PlainUser` बराबर नहीं होते, क्योंकि default `equals` references
मिलाता है। किसी id, price या screen state के लिए यह लगभग कभी नहीं चाहिए।

## Keyword बनाता क्या है

| बना हुआ | करता क्या है |
| --- | --- |
| `equals` / `hashCode` | **Primary constructor** की properties मिलाता और hash करता है |
| `toString` | `DataUser@4f3a` की जगह `DataUser(id=1)` |
| `copy(...)` | कुछ fields बदले हुए नया object |
| `component1()`… | Destructuring चालू करता है |

```kotlin title="Copy.kt" numbered runnable
data class Order(val id: String, val qty: Int, val paid: Boolean = false)

fun main() {
    val order = Order("A1", 2)
    val settled = order.copy(paid = true)     // बाकी सब जैसा था वैसा

    println(order)
    println(settled)

    val (id, qty) = settled                   // destructuring
    println("$id x$qty")
}
```

<Detail summary="copy() दिखने से ज्यादा जरूरी क्यों है">
Compose और coroutine `StateFlow` में state को बदला नहीं जाता, उसकी जगह नई value रखी जाती है —
सुनने वाले को सिर्फ *नई* value दिखती है। `copy()` उस नई value को एक पढ़ने लायक line बना देता है,
वरना हर न-बदला field दोबारा लिखना पड़ता।
</Detail>

## वह नियम जिसपर सब फिसलते हैं

सिर्फ **primary constructor** की properties गिनती हैं।

```kotlin title="Trap.kt" numbered runnable
data class Note(val title: String) {
    var body: String = ""        // body में — equals को दिखता ही नहीं
}

fun main() {
    val a = Note("Shopping").apply { body = "milk" }
    val b = Note("Shopping").apply { body = "eggs" }
    println(a == b)              // true, अलग body होने के बावजूद
}
```

<Pitfall title="दो जो असली bugs बनाती हैं">
**Body में लिखी properties को** `equals`, `hashCode`, `toString` और `copy` — चारों अनदेखा कर देते
हैं। अगर कोई value object की पहचान का हिस्सा है, तो उसकी जगह primary constructor है।

**`var` वाली data class को `Map` key या `Set` में डालना।** Bucket में रखने के बाद उसे बदलने से उसका
`hashCode` बदल जाता है, और collection उसे ढूँढ ही नहीं पाता। Data class की properties `val` रखिए।
</Pitfall>

## अभ्यास

1. `Order` को body में एक `discount` property दीजिए, सिर्फ उसमें अलग दो orders बनाइए, और देखिए कि
   वे बराबर निकलते हैं। फिर उसे constructor में ले जाकर दोबारा चलाइए।
2. `var` वाली एक data class `mutableSetOf` में डालिए, property बदलिए, फिर उसी object से `contains`
   बुलाइए। नतीजा समझाइए।
3. `copy()` से एक छोटा "order lifecycle" बनाइए — placed, paid, shipped — बिना किसी object को बदले।
4. Orders की list पर `for` loop के अंदर `Order` को destructure कीजिए।

## सारांश

| चीज | बात |
| --- | --- |
| `equals` / `hashCode` | सिर्फ primary constructor की properties |
| `toString` | पढ़ने लायक, property नामों के साथ |
| `copy(...)` | बदली हुई state बनाने का सही तरीका |
| Destructuring | `val (a, b) = obj`, क्रम से — order मायने रखता है |
| Properties `val` रखिए | बदलने वाली key hash collections तोड़ देती है |
