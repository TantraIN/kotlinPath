<KeyIdea>
Enum का हर constant असल में **नाम वाला singleton object** है। इसीलिए वह properties रख सकता है,
interface implement कर सकता है, और फिर भी `==` से मिलाया जा सकता है।
</KeyIdea>

## सिर्फ नामों की list से ज्यादा

```kotlin title="Status.kt" numbered runnable
enum class Status(val label: String, val retryable: Boolean) {
    PENDING("Waiting", true),
    SHIPPED("On the way", false),
    FAILED("Failed", true);

    fun canRetry() = retryable
}

fun main() {
    Status.entries.forEach { println("${it.name}: ${it.label} (${it.canRetry()})") }
    println(Status.valueOf("SHIPPED").label)
    println(Status.PENDING.ordinal)      // 0
}
```

हर constant के पास वही fields हैं। यही एक जैसा होना `sealed` से फर्क है।

## हर constant का अपना behaviour

```kotlin title="Ops.kt" numbered runnable
enum class Op {
    ADD { override fun apply(a: Int, b: Int) = a + b },
    TIMES { override fun apply(a: Int, b: Int) = a * b };

    abstract fun apply(a: Int, b: Int): Int
}

fun main() = Op.entries.forEach { println("${it.name}: ${it.apply(3, 4)}") }
```

<Detail summary="`values()` नहीं, `entries` इस्तेमाल कीजिए">
`values()` हर call पर नई array बनाता है, इसलिए उसे loop या Compose recomposition के अंदर बुलाने से
चुपचाप कचरा बनता रहता है। `entries` (Kotlin 1.9+) एक साझी immutable list लौटाता है। नए code में
पुराना रूप चुनने की कोई वजह नहीं।
</Detail>

## Enum और sealed में से चुनना

| सवाल | हाँ तो |
| --- | --- |
| क्या सारे cases वही fields रखते हैं? | `enum` |
| क्या किसी एक case को ऐसा data चाहिए जो बाकियों को नहीं? | `sealed` |
| क्या एक case के कई instances चाहिए? | `sealed` |
| क्या `valueOf`, `ordinal` या `entries` चाहिए? | `enum` |
| क्या यह screen state या operation result है? | लगभग हमेशा `sealed` |

## आम गलतियाँ

<Pitfall title="दो जो production में काटती हैं">
**`ordinal` को save करना।** Database में `2` लिखकर उसे `SHIPPED` पढ़ना उस दिन टूटेगा जिस दिन कोई बीच
में एक constant घुसा देगा। `name` save कीजिए, या अपना खुद का `val code: Int`।

**Enum पर `when` में `else`।** वही जाल जो sealed के साथ था: नया constant जोड़ना compile error होना
चाहिए, और `else` उसे चुपचाप निगल जाता है। हर constant लिखिए, या जहाँ ठीक बैठे वहाँ `entries.forEach`
इस्तेमाल कीजिए।
</Pitfall>

## अभ्यास

1. `Status` में `CANCELLED` constant जोड़िए और हर वह `when` ढूँढिए जो compile होना बंद हो गया। यही
   खूबी काम कर रही है।
2. `Status` को एक `companion object` दीजिए जिसमें `fromCode(code: Int)` हो और अनजान code पर `null`
   लौटे।
3. Enum से interface implement कीजिए — `Status` को `label` के हिसाब से `Comparable` बनाइए।
4. वही तीन statuses sealed interface से model कीजिए जहाँ `FAILED` एक `reason` रखता हो। API response
   के लिए कौन सा version बेहतर बैठता है?

## सारांश

| चीज | बात |
| --- | --- |
| हर constant | साझा singleton — `==` और `===` दोनों सुरक्षित |
| Properties | हर constant के लिए वही fields |
| हर constant की अपनी body | चलती है, `abstract` member के जरिए |
| `entries` | `values()` से बेहतर — कोई allocation नहीं |
| कभी save मत कीजिए | `ordinal`; `name` या अपना code save कीजिए |
