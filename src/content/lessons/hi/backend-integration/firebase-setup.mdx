<KeyIdea>
Firebase की SDKs अंदर का code साझा करती हैं और versions के अलग होने पर उलझाने वाले तरीकों से टूटती
हैं। **BoM** इसीलिए है कि आप एक version बताएँ और हर Firebase वाली library उसी के पीछे चले — और इसीलिए
आप Firebase की dependencies बिना version के लिखते हैं।
</KeyIdea>

## तैयारी

```kotlin title="app/build.gradle.kts" numbered
plugins {
    id("com.google.gms.google-services")
}

dependencies {
    implementation(platform("com.google.firebase:firebase-bom:33.7.0"))   // इकलौता version

    implementation("com.google.firebase:firebase-auth")                   // कोई version नहीं
    implementation("com.google.firebase:firebase-firestore")
    implementation("com.google.firebase:firebase-analytics")
}
```

`platform(...)` ही BoM को चलाता है: वह कोई library जोड़ने के बजाय आपस में चलने वाले versions का समूह
बताता है। उसके बाद हर Firebase वाली dependency वही version लेती है जो वह BoM बताता है।

किसी एक library का version हाथ से बाँध देना पूरी बात हरा देता है — नए BoM के साथ
`firebase-auth:22.1.0` आपको ठीक वही बेमेल देता है जिसे रोकने के लिए BoM है, और नाकामी आमतौर पर build
की error नहीं बल्कि चलते वक्त का `NoSuchMethodError` होती है।

`google-services` वाला plugin build के वक्त `google-services.json` पढ़कर उसे उन resources में बदल देता
है जिन्हें SDKs शुरू होते वक्त पढ़ती हैं। तो वह file build का input है, चलते वक्त लादी जाने वाली चीज
नहीं।

## `google-services.json` राज नहीं है

उसमें आपके project की id, एक API की key, और वे package के नाम हैं जो आपने दर्ज किए। लोग आमतौर पर आदतन
उसे `.gitignore` में डाल देते हैं, और वह आदत गलत है: उससे नए लोगों का जुड़ना दुखदायी और CI मुश्किल हो
जाती है, और सुरक्षा का कोई फायदा नहीं, क्योंकि वह file हर APK के अंदर वैसे भी जाती है।

Firebase के project की हिफाजत उस file के छिपे होने से नहीं होती:

| हिफाजत | वह करती क्या है |
| --- | --- |
| Security rules | तय करते हैं कि हर document कौन पढ़ और लिख सकता है |
| API key की पाबंदियाँ | Key को आपके package और हस्ताक्षर वाले certificate से बाँधती हैं |
| App Check | गवाही देता है कि request आपके असली ऐप से आई है |

बिना पाबंदी वाली key और ढीले rules खुले पड़े हैं, चाहे वह file commit हो या न हो। बँधी हुई key और सख्त
rules सुरक्षित हैं, चाहे वह file सार्वजनिक ही क्यों न हो।

## माहौल

बनाने और production के लिए एक ही Firebase project तैयारी की सबसे आम गलती है, क्योंकि जाँच वाला data और
असली users का data एक ही database में पहुँच जाते हैं। दो projects और दो config की files लीजिए:

```kotlin title="Flavours" numbered
android {
    flavorDimensions += "env"
    productFlavors {
        create("dev")  { applicationIdSuffix = ".dev" }
        create("prod") { }
    }
}
```

```text title="Layout" numbered
app/src/dev/google-services.json     <- बनाने वाला Firebase project
app/src/prod/google-services.json    <- production वाला
```

Plugin उसी flavour से मेल खाती file उठाता है। `applicationIdSuffix` उतना ही मायने रखता है: उससे दोनों
builds एक ही device पर रह सकते हैं, और इसका मतलब यह भी है कि dev वाला build इत्तेफाकन production के
push notifications के लिए दर्ज नहीं हो सकता।

<Detail summary="अभी क्या जोड़ें, और किसका इंतजार करें">
दो SDKs पहले ही दिन जोड़ने लायक हैं, जरूरत पड़ने से पहले।

**Crashlytics**, क्योंकि वह सिर्फ उन्हीं crashes की खबर देता है जो उसके लगने के बाद हों। पहली ऐसी crash
की रिपोर्ट देखकर उसे जोड़ना, जिसे आप दोबारा पैदा नहीं कर पा रहे, महीना भर देर है।

**Remote Config**, क्योंकि बिना release किसी सुविधा को बंद करने की व्यवस्था वही है। इस्तेमाल करने तक
उसकी कोई कीमत नहीं, और जिस दिन जरूरत पड़ती है उसी दिन आप उतनी तेजी से भेज नहीं सकते।

जिससे सँभलना है वह है **Analytics**, जो कई दूसरी SDKs के साथ डिफॉल्ट से जुड़ जाती है और तुरंत जमा करना
शुरू कर देती है। उसके नतीजे हैं जिन्हें आपको विरासत में लेने के बजाय सोच-समझकर तय करना चाहिए: privacy
policy की जिम्मेदारी, Play की Data Safety वाली घोषणा जो आपके सच में जमा किए से मेल खानी चाहिए, और जहाँ
लागू हो वहाँ GDPR की सहमति। User के मानने तक `setAnalyticsCollectionEnabled(false)` ईमानदार डिफॉल्ट है,
और Play पर data जमा करना गलत बताना असली अस्वीकृति की वजह है।
</Detail>

## आम गलतियाँ

<Pitfall title="पाँच, और पहली build वक्त नहीं, चलते वक्त टूटती है">
**किसी एक Firebase library का version बाँधना।** BoM ठीक उसी बेमेल को रोकने के लिए है।

**`google-services.json` को राज मानना।** वह APK में जाती है; उसकी जगह rules और key सँभालिए।

**Dev और prod के लिए एक project।** जाँच वाला data असली database में उतरता है।

**पहली रहस्यमय crash के बाद Crashlytics जोड़ना।** वह सिर्फ अपने लगने के बाद वाली crashes देखता है।

**Analytics का जमा करना विरासत में लेना।** उसे Play पर बताइए, और जहाँ जरूरी हो वहाँ सहमति लीजिए।
</Pitfall>

## अभ्यास

1. BoM के साथ किसी एक Firebase library को पुराने version पर बाँधिए और चलते वक्त की नाकामी ढूँढ़िए।
2. अलग config की files के साथ dev और prod वाले flavours बनाइए और पक्का कीजिए कि दोनों साथ लगते हैं।
3. अपनी ही release APK से `google-services.json` की values निकालिए।
4. Firestore के rules खोलिए और देखिए कि वे अब भी test वाली हालत में तो नहीं हैं।
5. अपनी API की key को package और हस्ताक्षर वाले certificate से बाँधिए, फिर उसे `curl` से आजमाइए।

## दोहराव

| चीज | एक लाइन |
| --- | --- |
| BoM | एक version; हर Firebase library उसी के पीछे |
| `platform(...)` | Versions बताता है, library जोड़ता नहीं |
| एक library बाँधना | वही बेमेल दोबारा बना देता है जिसे BoM रोकता है |
| `google-services.json` | Build का input, और राज नहीं |
| असली हिफाजत | Security rules, key की पाबंदियाँ, App Check |
| Service account वाली JSON | असली राज; सिर्फ server की तरफ |
| दो projects | Dev और prod, हर flavour की अपनी config के साथ |
| `applicationIdSuffix` | एक ही device पर दोनों; push के tokens आपस में नहीं उलझते |
| Crashlytics | जरूरत पड़ने से पहले जोड़िए |
| Analytics | उसे बताइए, और जहाँ जरूरी हो वहाँ सहमति लीजिए |

<Interview title="एक सवाल, जो चीज और खतरे को अलग करता है">
"क्या `google-services.json` version control में commit होनी चाहिए?"

लगभग हर मामले में हाँ। वह build का input है जिसे `google-services` वाला plugin resources में बदल देता
है, और उसका सामान हर APK के अंदर जाता है — तो कोई भी उसे किसी छपे हुए build से एक मिनट में निकाल सकता
है। उसे gitignore करना नए लोगों के जुड़ने और CI को मुश्किल बनाता है और बचाता कुछ नहीं।

जिस खतरे से उसे अक्सर उलझाया जाता है वह असली है, पर वह कहीं और रहता है: कि Firestore के security rules
सच में पढ़ना-लिखना सीमित करते हैं या नहीं, क्योंकि test वाली हालत में छोड़े गए rules उस file में पड़ी
project की id को ही सब कुछ पढ़ने के लिए काफी बना देते हैं; कि API की key package के नाम और हस्ताक्षर
वाले certificate से बँधी है या नहीं; और कि App Check चालू है या नहीं ताकि जो requests असली ऐप से नहीं
आईं वे ठुकरा दी जाएँ। जो file सच में कभी commit नहीं होनी चाहिए वह service account वाली JSON है — उसमें
निजी key होती है और वह server की जगह है, ऐप में कभी नहीं।
</Interview>
