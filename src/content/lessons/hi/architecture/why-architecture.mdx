<KeyIdea>
Architecture इसलिए है कि **कोई बदलाव कितनी दूर तक जाता है, उसे बाँधा जा सके**। अच्छी तरह जमा हुआ
codebase वह नहीं जो सुथरा दिखे; वह है जिसमें date का format बदलने पर सिर्फ date का format बदलता है
और कुछ नहीं।
</KeyIdea>

## यह क्यों जरूरी है

यह रही वह screen जो सबको मिली है, दबाकर छोटी की हुई:

```kotlin title="OrderActivity.kt" numbered
class OrderActivity : AppCompatActivity() {

    private val client = OkHttpClient()

    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)

        Thread {
            val json = client.newCall(Request.Builder().url(URL).build())
                .execute().body!!.string()
            val orders = JSONArray(json).let { array ->
                (0 until array.length()).map { parseOrder(array.getJSONObject(it)) }
            }
            val open = orders.filter { it.status != "DELIVERED" }
                .sortedByDescending { it.placedAt }

            runOnUiThread {
                binding.total.text = "₹" + open.sumOf { it.amount } / 100
                adapter.submitList(open)
            }
        }.start()
    }
}
```

यह चलता है। दिक्कत यह है कि इसे बदलने की कीमत क्या है।

| आपको क्या करना है | क्या बदलना पड़ेगा | दोबारा क्या जाँचना पड़ेगा |
| --- | --- | --- |
| Currency का format बदलना | `OrderActivity` | पूरी screen, किसी device पर |
| Orders offline रखना | `OrderActivity` | पूरी screen |
| वही list किसी widget पर दिखाना | सब कुछ copy करना | दोनों copies, हमेशा |
| "कौन से orders खुले हैं" वाला नियम जाँचना | जाँच ही नहीं सकते | — |

इनमें से हर एक वही एक नाकामी है: बिना आपस में मतलब वाले फैसले एक ही जगह आ बैठे।

नियम तीर है, नाम नहीं। **निर्भरता एक ही तरफ जाती है।** `ViewModel` को repository का पता हो सकता
है; repository को कभी पता नहीं चलना चाहिए कि कोई `ViewModel` है भी। जैसे ही कोई तीर वापस मुड़ता है,
एक चक्कर बन जाता है, और चक्कर का मतलब है कि दोनों में से किसी को अकेले न समझा जा सकता है न बदला जा
सकता है।

<Note>
Domain का सादा Kotlin होना सिर्फ सफाई के लिए नहीं है। इसका मतलब है कि "order तब तक खुला है जब तक
पहुँचा नहीं" वाला नियम आपके laptop पर milliseconds में जाँचा जा सकता है, बिना किसी emulator के, और
कोई widget, कोई Wear app या कोई server उसे दोबारा इस्तेमाल कर सकता है।
</Note>

## Architecture मुफ्त नहीं है

<Detail summary="इसकी कीमत क्या है, और कब छोड़ देना चाहिए">
आपकी जोड़ी हुई हर सरहद एक घुमाव है: खोलने को एक और file, पढ़ने को एक और interface, button और
network call के बीच एक और पड़ाव। जिस screen पर तीन जमी हुई lines दिखती हैं, वहाँ इस कीमत से कुछ
नहीं मिलता।

ढाँचे की तरफ तब जाइए जब इनमें से कम से कम एक सच हो:

- यह code एक से ज्यादा लोग बदलते हैं।
- वही नियम एक से ज्यादा जगह चाहिए।
- वह logic बिना device के जाँचने लायक है।
- वह screen आज के design से ज्यादा जिएगी।

जिस prototype को आप हफ्ते भर में फेंक देंगे वह एक ही file में रहे। उस पर चार परतें लगाना अनुशासन
नहीं, रस्म है, और इससे वह prototype बदलने में धीमा हो जाता है — जबकि वह बना ही इसीलिए था।
</Detail>

## आम गलतियाँ

<Pitfall title="तीन जो architecture जैसी दिखती हैं और हैं नहीं">
**सरहदों की जगह folders।** `data/`, `domain/` और `ui/` बना देना और फिर `ViewModel` में ही
`Retrofit` बनाना कुछ नहीं बदलता। मायने तीर रखते हैं, रास्ते नहीं।

**दूसरा मामला आने से पहले ही abstract कर देना।** ठीक एक implementation वाला interface, जो इसलिए
लिखा गया कि शायद कभी दूसरा आए, वह file है जिसे सबको पढ़ना पड़ता है और फायदा किसी को नहीं होता।

**हर method के लिए एक class।** ऐसा `UseCase` जो repository का एक method बुलाकर उसी को लौटा देता है
वह एक पड़ाव जोड़ता है और कोई फैसला नहीं। जब कोई नियम रखने को हो तब जोड़िए; उससे पहले नहीं।
</Pitfall>

## अभ्यास

1. ऊपर वाली `OrderActivity` लीजिए और वे सारी वजहें लिखिए जिनसे वह बदल सकती है। वजहों को समूहों में
   बाँटिए — हर समूह वह class है जो आपके पास नहीं है।
2. उसमें वह एक नियम ढूँढ़िए जो सच में कारोबार का नियम है, और उसे एक सादे Kotlin function में ले
   जाइए। उस function का test बिना emulator के लिखिए।
3. अपनी किसी मौजूदा screen में निर्भरता के तीर खींचिए। कोई तीर उल्टा जाता हुआ ढूँढ़िए।
4. अपने project में ठीक एक implementation वाला कोई interface ढूँढ़िए और पूछिए कि उससे मिलता क्या
   है।

## सारांश

| चीज | एक line |
| --- | --- |
| Architecture | बदलाव कितनी दूर तक जाए, यह बाँधती है |
| Coupling | एक चीज दूसरी पर कितनी टिकी है — कम रखिए |
| Cohesion | एक चीज कितनी एक ही काम की है — ज्यादा रखिए |
| Test न हो पाना | शिकायत है; वजह आमतौर पर अपनी dependencies खुद बनाना |
| परतें | UI, presentation, domain, data |
| निर्भरता का नियम | तीर एक ही तरफ; चक्कर का मतलब कोई भी पक्ष अकेला नहीं खड़ा |
| Domain | सादा Kotlin, तो नियम milliseconds में चलते हैं और कहीं भी जाते हैं |
| कीमत | घुमाव — तभी चुकाइए जब ऊपर वाली कोई बात सच हो |
