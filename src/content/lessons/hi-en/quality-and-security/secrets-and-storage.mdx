<KeyIdea>
APK kisi aur ke computer par padi ek zip file hai. Naam badalna, `BuildConfig`, native code aur chatur
encoding — sab mehnat badhate hain aur anjaam koi nahi badalta — to jis raaz ko raaz rehna hi hai wo
**app ke saath bheja ja hi nahi sakta**.
</KeyIdea>

## "Chhupane" se milta kya hai

```kotlin title="NotHidden.kt" numbered
// decompile ki gayi class file mein dikhta hai
private const val API_SECRET = "sk_live_9f2a..."

// BuildConfig mein dikhta hai, jo ek aam class hai
buildConfigField("String", "API_SECRET", "\"sk_live_9f2a...\"")

// strings.xml mein dikhta hai, aur usse bhi aasani se
<string name="api_secret">sk_live_9f2a...</string>

// .so mein `strings` se dikhta hai, aur JNI wali call mein haath daalne wale kisi ko bhi
external fun getSecret(): String
```

Har pankti hamlawar ke liye thodi aur mehnat hai aur koi bhi deewar nahi. `apktool` aur `jadx` second
lete hain; NDK wala roop `strings` ya Frida ke saath kuch minute. Apne aap chalne wale scanners Play par
theek inhin shaklon ke liye ghoomte hain, aur leak hui keys aam taur par isi tarah milti hain — kisi
nishana saadhe hamlawar se nahi, kisi bot se.

Jo farak maayne rakhta hai:

| Kis tarah ki key | Bheji ja sakti hai? |
| --- | --- |
| Sarvajanik client ki pehchan — Maps ki key, OAuth client id, Firebase ki settings | Haan; use server ki taraf se seemit kijiye |
| Hastakshar ka raaz, niji API ki key, admin ka token | Kabhi nahi |

Pehli kism ke liye seemit karna hi suraksha hai: Maps ki key ko apne package ke naam aur hastakshar wale
certificate se baandh dijiye, taki use nikalne se kuch mile hi nahi. Doosri ke liye wo kaam aapke server
ki jagah hai, aur app kisi bahari ke bajaye aapke endpoint ko bulata hai.

## Keystore, un raazon ke liye jo device khud banata hai

Device jo khud banata hai aur kabhi bhejta nahi wo alag mushkil hai, aur Android ke paas uske liye asli
hardware hai:

```kotlin title="Keystore.kt" numbered
val spec = KeyGenParameterSpec.Builder("token_key", PURPOSE_ENCRYPT or PURPOSE_DECRYPT)
    .setBlockModes(BLOCK_MODE_GCM)
    .setEncryptionPaddings(ENCRYPTION_PADDING_NONE)
    .setUserAuthenticationRequired(true)          // sirf biometric ya PIN ke baad
    .build()

KeyGenerator.getInstance(KEY_ALGORITHM_AES, "AndroidKeyStore").apply {
    init(spec); generateKey()
}
```

Key ki asli samagri surakshit hardware se bahar jati hi nahi — aajkal ke zyadatar devices par koi TEE ya
alag suraksha wali chip — aur root kiye device se bhi nikali nahi ja sakti. Aapke code ko us key ko
*istemal* karne ko milta hai, padhne ko nahi.

Isiliye session ka token Keystore ki key se encrypt karke rakhna safe hai aur API ka raaz nahi: Keystore
us cheez ki hifazat karta hai jo usi device par bani thi, jabki API ka raaz APK mein aaya tha aur
Keystore ke dekhne se pehle hi ujagar ho chuka tha.

## Rakhe hue data ki hifazat

```kotlin title="Storage.kt" numbered
// Jetpack Security hatai ja chuki hai; apni Keystore ki key se encrypt kiya DataStore
val encrypted = cipher.doFinal(token.toByteArray())
dataStore.edit { it[TOKEN] = Base64.encodeToString(encrypted, Base64.NO_WRAP) }

// poore database ke liye SQLCipher, jiska passphrase Keystore se aata hai
Room.databaseBuilder(context, AppDatabase::class.java, "app.db")
    .openHelperFactory(SupportOpenHelperFactory(passphrase))
    .build()
```

`EncryptedSharedPreferences` aur `EncryptedFile` maanak jawab the aur ab hataye ja chuke hain, to naye
code ko seedhe Keystore ki key DataStore ke saath leni chahiye, ya jahan poora database chahiye wahan
SQLCipher.

Khatre ki tasveer saaf rakhna theek rahega: `filesDir` wali app ki apni storage doosre apps ke liye
pehle se hi padhi nahi ja sakti, aur jis device par screen lock hai wahan platform use pehle se hi
encrypt karke rakhta hai. Uske upar encrypt karna root kiye device, backup nikale jane, ya churaye hue
khule phone se bachata hai — asli khatre, par "koi meri file padh sakta hai" se kahin sankre.

<Detail summary="Backups, logs aur ittefaqan hone wale risav">
Teen tarike jinse raaz bina kisi ke hamla kiye nikal jate hain.

**Auto Backup.** Default se Android app ka data user ke cloud par sahejta hai, aapki files samet. Jo
samvedansheel hai use bahar rakhiye:

```xml title="AndroidManifest.xml" numbered
<application
    android:dataExtractionRules="@xml/data_extraction_rules"
    android:fullBackupContent="@xml/backup_rules">
```

**Logs.** `Log.d("api", "token=$token")` debuggable build par `adb` rakhne wale kisi ko bhi padha ja
sakta hai, aur crash ki reporton tatha analytics ki kadiyon mein aage bhi bacha rehta hai. Release mein
logging kisi R8 niyam se hataiye, aur request ki body kabhi log mat kijiye.

**Screenshots aur haal wali list.** Samvedansheel data dikhati screen app badalne wali list mein dikhti
hai aur pakdi ja sakti hai. `WindowManager.LayoutParams.FLAG_SECURE` us activity ke liye dono rok deta
hai.

Teenon mein tarika ek hi hai: raaz theek se sambhala gaya aur phir aisi jagah nakal ho gaya jahan ke
niyam alag hain. Ye kisi bhi decompiler se zyada aam risav hai.
</Detail>

## Aam galtiyan

<Pitfall title="Paanch, aur pehli hamlawaron ke bajaye bots ko milti hai">
**`BuildConfig` ya `strings.xml` mein koi niji key.** Scanners Play par theek isi ke liye ghoomte hain.

**NDK ko chhupne ki jagah manna.** Dhoondhna mushkil, aur istemal ke waqt memory mein khula.

**Client ki key seemit na karna.** Apne package se bandhi Maps ki key bhejna safe hai; bina bandhi kisi
aur ka bill hai.

**`google-services.json` ya keystore commit kar dena.** Sirf maujooda files nahi, itihas dekhiye.

**Tokens log karna.** Wo log ki line padhe jane ke bahut baad tak crash ki reporton aur analytics mein
bache rehte hain.
</Pitfall>

## Abhyaas

1. Apni hi release APK par `jadx` chalaiye aur har wo string dhoondhiye jo key jaisi lagti hai.
2. Jis `.so` mein jada hua raaz hai us par `strings` chalaiye.
3. `setUserAuthenticationRequired` wali Keystore ki key banaiye aur pakka kijiye ki aap use padh nahi
   sakte.
4. Kisi screen par `FLAG_SECURE` lagaiye aur uska screenshot lene ki koshish kijiye.
5. Apne backup ke niyam dekhiye aur ginaiye ki aaj kaun si files cloud par jatin.

## Doharav

| Cheez | Ek line |
| --- | --- |
| APK | Kisi aur ke computer par padi ek zip |
| Naam badalna aur NDK | Hamlawar ke liye zyada mehnat; deewar nahi |
| Client ki pehchan | Bhejna theek hai, agar server ki taraf se seemit ho |
| Niji raaz | Kabhi mat bhejiye; wo kaam aapke server ki jagah hai |
| Keystore | Hardware ka sahara; key nikali nahi ja sakti |
| Ye chalta kyun hai | Wo uski hifazat karta hai jo device ne banai, jo APK mein aayi uski nahi |
| `EncryptedSharedPreferences` | Hatai ja chuki; DataStore ke saath Keystore ki key lijiye |
| SQLCipher | Jab poora database encrypt karna ho |
| Auto Backup | Samvedansheel files bahar rakhiye, warna wo cloud par jati hain |
| `FLAG_SECURE` | Screenshots aur haal wali jhalak, dono rokta hai |

<Interview title="Ek sawal, jiska jawab do took hai">
"Android app mein API ki key safe tarike se kaise rakhoge?"

Rakhenge hi nahi — APK ki har cheez nikali ja sakti hai, aur `BuildConfig`, `strings.xml`, naam badalna
tatha NDK mein farak sirf itna hai ki kitni der lagti hai. NDK wahi hai jise log safe maante hain, aur wo
hai nahi: wo string us binary mein hai, aur uljhai hui hone par bhi istemal ke pal use memory mein khula
hona hi padta hai, aur wahin hooking wala framework use padh leta hai.

To main keys ko kism ke hisab se baantunga. Sarvajanik client ki pehchan — Maps ki key, koi OAuth client
id — bheji ja sakti hai, kyunki suraksha wo pabandi hai: use package ke naam aur hastakshar wale
certificate se baandh dijiye taki nikalne se kuch mile nahi. Jo sach mein raaz hai wo bheja hi nahi jata;
wo khaas kaam kisi server par chala jata hai jisse app har user ke apne, radd kiye ja sakne wale token se
pehchan batata hai. Keystore alag mushkil ke liye hai — us cheez ki hifazat, jo device ne banai, jaise
koi session ki key — aur wo theek isiliye chalta hai ki wo value APK mein aayi hi nahi thi.
</Interview>
