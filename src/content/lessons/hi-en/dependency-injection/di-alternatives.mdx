Aur haath se ki gayi DI, jo pehle lesson ne likhkar dikhai thi: ek container, koi library nahi, poora
akhtiyaar. Wo logon ki ummid se zyada der chalti hai aur scope wali umron tatha `ViewModel` ki
factories par ruk jati hai.

```kotlin title="KoinModule.kt" numbered
val appModule = module {
    single { OkHttpClient.Builder().addInterceptor(get<AuthInterceptor>()).build() }
    single { Retrofit.Builder().baseUrl(BASE_URL).client(get()).build() }
    single { get<Retrofit>().create(OrderApi::class.java) }
    single<OrderRepository> { OfflineFirstOrderRepository(get(), get()) }
    viewModel { OrderViewModel(get()) }
}
```

Use Hilt wale roop ke saamne rakhkar padhiye aur farak dikh jata hai: `single` hi `@Singleton` hai,
`factory` bina scope wala, aur `get()` wahi hai jo Hilt constructor ke parameters se khud nikal leta
tha. Wiring aam Kotlin hai jise aap debugger mein ek-ek kadam chala sakte ho — jo sach mein padhne
mein zyada achhi hai, aur yahi wajah bhi hai ki app chalne se pehle use kisi ne check nahi kiya.

## KMP wala sawal

Yahin ye chunaav pasand ki baat nahi reh jata.

Hilt, Dagger par bana hai, jo Java ka annotation processor hai aur JVM ka code banata hai. Share kiya
gaya Kotlin Multiplatform code iOS ke liye, aur aksar JS tatha native ke liye bhi compile hona padta
hai, to Hilt wahan chal hi nahi sakta — ye ghumakar paar karne wali pabandi nahi, banawat ki baat hai.

To share kiye gaye code ke liye teen asli raaste bachte hain:

| Tarika | Kaise chalta hai |
| --- | --- |
| Koin | Multiplatform hai, share kiye code mein jas ka tas chalta hai |
| Haath se DI | Common code mein ek share container; lamba hai, aur poori tarah portable |
| kotlin-inject / Metro | KSP se compile waqt wali DI, to ye multiplatform chalti hai |

Aam shakal ek mili-juli hai: share kiye module mein Koin ya haath se DI, aur uske ird-gird Android app
ko Hilt se wire karna. Ye samjhauta kam aur ye manna zyada hai ki dono hisson ki sharten alag hain.

<Note>
Agar Kotlin Multiplatform aage ki yojana mein kahin bhi hai, to ye jaldi tay kar lena theek rehta hai.
Baad mein DI badalna har us class ko chhoota hai jo koi dependency paati hai — aur agar aapne is phase
ko mana hai, to wo sab hain.
</Note>

<Detail summary="Build ka waqt jata kahan hai">
"Annotation processing dheemi hai" jitni baar dohrai jati hai usse kam baar naapi jati hai, aur bareeki
maayne rakhti hai.

Hilt ki keemat barabar bandhi hui nahi hai. Uska processor sab kuch ikattha karta hai, to kisi
`@Module` mein badlaav build ke bade hisse ko amanya kar sakta hai — yani dard wala maamla hai DI
badalne ke baad ka incremental build, na ki saaf build, aur na hi aam code badalna. Chhote app par ye
dikhta hi nahi; bade kai-module wale app par ye un wajahon mein hai jo log badalte waqt ginate hain.

Library badalne ki sochne se pehle do cheezein ise ghatati hain. Pakka kijiye ki aap kapt nahi balki
**KSP** par ho, jo usi kaam ke liye kaafi tez hai. Aur modules chhote rakhiye, taki ek badlaav kam
cheezein amanya kare.

Agar Koin ki sochne ki wajah build ki raftar hai, to pehle naapiye. `--scan` ya koi build profile bata
dega ki aapke build ka kitna hissa sach mein annotation processing hai, aur wo aksar jhunjhlahat ke
bataye se chhota nikalta hai.
</Detail>

## Chunna

| Haalat | Samajhdar chunaav |
| --- | --- |
| Sirf Android wala app, kisi bhi naap ka | Hilt |
| Chhota app, gini-chuni dependencies | Haath se DI — sach mein theek |
| Kotlin Multiplatform ka share kiya code | Koin, haath se, ya kotlin-inject |
| Jis build par DI ki processing naapne layak haavi ho | Koin, aur CI mein `checkModules()` |
| Aapki chhapi hui koi library | Constructor injection, aur koi framework nahi |

Aakhri pankti saaf-saaf kehne layak hai. Kisi library ko apna DI framework us app par kabhi nahi
thopna chahiye jo use leta hai. Constructors bahar dijiye, aur unhe jo bhi wo lete hain usse wire karne
dijiye.

## Aam galtiyan

<Pitfall title="Galat chunne ke chaar tarike">
**Bina `checkModules()` ke Koin apnana.** Aapne compile waqt wali guarantee chhod di aur use wapas
khareeda nahi, to kam khulne wali koi screen tooti hui bheji jati hai.

**Bina naape build ki raftar par chunna.** Dekhiye ki build ka kitna hissa annotation processing hai,
aur dekhiye ki aap kapt nahi, KSP par ho.

**Hilt apnane ke baad KMP wali shart pata chalna.** DI badalna har us class ko chhoota hai jo koi
dependency paati hai.

**Chhapi hui library mein koi framework.** Constructors bahar dijiye; wire karna app tay karega.
</Pitfall>

## Abhyaas

1. Ek screen Koin se aur wahi screen Hilt se wire kijiye, aur milaiye ki dono kya-kya dikhate hain.
2. `checkModules()` wala test likhiye aur ek paribhasha mitaiye. Pakka kijiye ki wo nakaam hota hai.
3. Kisi build ka profile nikaliye aur asli pratishat dhoondhiye jo annotation processing mein jata hai.
4. Pakka kijiye ki aapka project kapt nahi, KSP leta hai.
5. Koi chhoti suvidha constructor injection wali library ki tarah likhiye, bina kisi DI framework ke,
   phir use Hilt lete kisi app se wire kijiye.

<Interview title="Ek sawal, jo ye check kar raha hai ki aap apna default sahi thehra sakte ho ya nahi">
"Koin ke bajaye Hilt kyun?"

Sirf Android wale app ke liye, kyunki graph compile waqt check hota hai: gayab dependency us type ka
naam leti build ki error hai, na ki us screen ko pehli baar kholne par aaya crash jise uski zarurat
thi. Usmein Android ki umrein bani-banai hain, to `ViewModel` aur retained scopes khud wire karne ke
bajaye annotations hain.

Main ise seedhe-seedhe behtar kehkar nahi rakhunga. Koin mein koi code nahi banta, to builds tez rehte
hain, aur wiring saada Kotlin hai jise padha aur debug kiya ja sakta hai — aur sabse ahem, wo Kotlin
Multiplatform par chalta hai, jo Hilt nahi chal sakta, kyunki Dagger JVM ka code banata hai. Agar main
Koin chunun to compile waqt wali guarantee wapas pane ke liye CI mein `checkModules()` jodunga. Aur
chhote app ke liye ek container wali haath se ki gayi DI jayaz jawab hai, jise bhejne mein mujhe koi
sharm nahi hogi.
</Interview>
