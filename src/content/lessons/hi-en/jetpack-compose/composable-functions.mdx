<KeyIdea>
`@Composable` kisi function ko **wo yaaddasht deta hai jo is baat se bandhi hai ki use bulaya
kahan se gaya**. Compiler ek chhipa hua `Composer` parameter jodta hai, aur usi se runtime ko pata
rehta hai ki is call ne pichhli baar kya banaya tha aur is baar chalane ki zarurat bhi hai ya
nahi.
</KeyIdea>

## Ye kyun zaruri hai

Shuru mein teen baatein sabko uljhati hain: composables sirf doosre composables se bulaye ja
sakte hain, `remember` bina koi naam diye kaam kar jata hai, aur jis function ko aapne chhua tak
nahi wo chupchap chalna band kar deta hai. Teenon ek hi baat ke teen kone hain.

## Compiler likhta kya hai

```kotlin title="YouWrite.kt"
@Composable
fun Greeting(name: String) {
    Text("Hello, $name")
}
```

```kotlin title="RoughlyWhatItBecomes.kt"
fun Greeting(name: String, $composer: Composer, $changed: Int) {
    $composer.startRestartGroup(0x7f0a01)
    // ... Text chhodta hai ...
    $composer.endRestartGroup()?.updateScope { c, _ -> Greeting(name, c, $changed or 1) }
}
```

Is pherbadal se do cheezein aati hain. `$composer` is call wali jagah ke liye runtime ki copy hai.
`$changed` ek bitmask hai jo batata hai ki pichhli baar se asal mein kaun se parameters alag hain
— aur isi se function tay kar pata hai ki use apni body chalani bhi hai ya nahi.

<Note>
Isiliye composable ko `onClick` se ya kisi `ViewModel` se nahi bulaya ja sakta. Wahan bhejne ko
koi `Composer` hai hi nahi, to na call se jodne ko koi yaaddasht hai aur na dobara chalane ko koi
scope.
</Note>

## Chhodna, aur wo kisse mumkin hota hai

Composable ki koi call tabhi chhodi jati hai jab uska har argument **stable** ho aur **pichhli
baar jaisa hi** ho.

| Parameter ka type | Stable? | Kyun |
| --- | --- | --- |
| `String`, `Int`, `Boolean` | Haan | Badle nahi ja sakte, aur `equals` ka matlab hai |
| Stable types wala `data class` | Haan | Compiler khud samajh leta hai |
| `List<Order>` | Nahi | Interface ke peeche badla ja sakne wala roop ho sakta hai |
| `ImmutableList<Order>` | Haan | `kotlinx.collections.immutable` se |
| Aapka wahin likha lambda | Haan, agar pakdi cheezein stable hon | Compiler use aapke liye yaad rakh leta hai |
| `var` field wali koi class | Nahi | Uske andar ki cheez bina khabar badal sakti hai |

<Tip>
Kisi type par `@Immutable` ya `@Stable` lagana compiler se kiya gaya wada hai, koi guzarish nahi.
Wada karke phir badlenge to Compose wo recomposition chhod dega jo sach mein zaruri thi, aur
screen par baasi data dikhega.
</Tip>

## Jagah hi pehchan hai

```kotlin title="Positional.kt" numbered
@Composable
fun Panel(expanded: Boolean) {
    if (expanded) {
        Text("Open")          // slot A
    } else {
        Text("Closed")        // slot B
    }
}
```

Ye dono `Text` alag-alag jagahon se bulaye gaye hain, to runtime ki table mein unhe alag slots
milte hain. Ek mein `remember` ki gayi koi cheez doosre ko dikhti nahi, aur shakha badalte hi
pehli shakha ki yaaddasht phenk di jati hai.

<Detail summary="Slot table, ek paragraph mein">
Runtime ek sapaat array rakhta hai — slot table — jismein har call wali jagah ka ek group hota
hai, usi order mein jismein composition wahan gaya tha. Group mein wahan `remember` ki gayi values
aur chhode gaye nodes rehte hain. Recomposition par runtime usi array par chalta hai, saath-saath
milata jata hai, aur sirf wo groups dobara bante hain jinka input badla hai. Pehchan *jagah* se
hoti hai, isliye source mein call ko hilana, ya kisi loop mein `key` diye bina items ka order
badalna, runtime ko lagta hai ki wo kisi aur cheez ko dekh raha hai aur wo yaaddasht phenk deta
hai.
</Detail>

## Common galtiyan

<Pitfall title="Teen jo performance ya sachai ki keemat maangti hain">
**Body mein hisab kar dena.** Composable ki body mein `val sorted = orders.sortedBy { it.date }`
har recomposition par dobara chalta hai. Ise lapetiye:
`remember(orders) { orders.sortedBy { it.date } }`.

**State bahut upar padhna.** Tezi se badalti value kisi parent mein padhne se wo parent aur uske
neeche sab bekar ho jata hai. Use ped mein jitna neeche ho sake utna neeche padhiye — sabse achha,
usi composable mein jo use dikhata hai.

**Wahi state likhna jise wahi composable padhta hai.** Isse abhi-abhi chala dayra bekar ho jata
hai, to wo phir se tay hota hai, aur ye chalta rehta hai. Inmein se kuch Compose pakadkar phenk
deta hai; baaki antheen recomposition ka phanda ban jate hain.
</Pitfall>

## Practice

1. Kisi parent aur child dono mein `println` rakhiye, sirf child ke padhe hue state ko badliye,
   aur dekhiye kiska chhapta hai.
2. Us state ko parent se hatakar child mein padhiye aur parent ka recompose hona band hote
   dekhiye.
3. Ek `List` parameter bhejiye, phir wahi data `ImmutableList` ki tarah, aur Layout Inspector ki
   recomposition ginti se milaiye ki kya chhootta hai.
4. Composable ki body mein seedhe ek bhaari loop likhiye, phir use `remember` mein lapetiye, aur
   frame ka samay milaiye.

## Recap

| Cheez | Ek line |
| --- | --- |
| `@Composable` | Chhipa hua `Composer` aur `$changed` bitmask jodta hai |
| Bulane ki jagah | Sirf koi doosra composable hi bula sakta hai |
| Restart ka dayra | Sabse paas wala restartable composable, akeli call nahi |
| Chhodna | Har argument stable ho aur pichhli baar jaisa ho |
| Stability | Khud samjhi jati hai, ya `@Stable` / `@Immutable` se wada kiya jata hai |
| Pehchan | Source mein call ki jagah |
| State padhna | Maujooda dayre ko usse jod deta hai |
| `remember(key)` | Key badalne tak nikali hui value rakhta hai |

<Interview title="Wo sawal jiska galat jawab bahut aam hai">
"Ek value badalne par recompose hota asal mein kya hai?"

Sabse paas wala restartable composable dobara chalta hai, aur uske andar har call tab chhod di
jati hai jab uske arguments stable aur pehle jaise hon. Aam galat jawab hain 'poori screen' aur
'sirf wo ek `Text`', aur asli jawab ka matlab kaam ka hai: composable ki body mein yun hi pada
bhaari hisab usi dayre ke andar hai jo dobara chalta hai, to use koi chhodkar nahi jata.
</Interview>
