<KeyIdea>
Kotlin mein class ko tab tak badhaya nahi ja sakta jab tak aap `open` na likho. Inheritance ek
soch-samajh kar liya faisla hai, galti se mila hua default nahi.
</KeyIdea>

## Jo structure aap bana rahe ho

```kotlin title="Payment.kt" numbered runnable
open class Payment(val amount: Int) {
    open fun fee(): Int = 0
    fun receipt(): String = "Paid $amount, fee ${fee()}"
}

class Card(amount: Int) : Payment(amount) {
    override fun fee(): Int = amount / 50
}

class Upi(amount: Int) : Payment(amount) {
    override fun fee(): Int = 0
}

fun main() {
    val payments = listOf(Payment(100), Card(500), Upi(500))
    payments.forEach { println(it.receipt()) }
}
```

Dhyan do ki `receipt()` `open` nahi hai, phir bhi wo `fee()` ko bulata hai jo `open` hai. Ek
method pakka hai, dusra ek khaali jagah hai jise subclasses bharti hain. Poora idea yahi hai.

## Teen keywords, har ek ka ek niyam

| Keyword | Matlab |
| --- | --- |
| Class par `open` | Is class ko badhaya ja sakta hai |
| Member par `open` | Is member ko badla ja sakta hai |
| `override` | Ye member upar wale `open` member ki jagah leta hai |
| `final override` | Jagah leta hai, aur chain yahin rok deta hai |
| `super.x()` | Jise maine abhi badla, wahi wala chalao |

<Detail summary="Kotlin ne classes default se band kyun ki, Java ne kyun nahi">
Java mein har class badhayi ja sakti thi jab tak `final` na likho, isliye library likhne wale
ko har khatarnaak subclass pehle se soch kar rokni padti thi. Asal mein koi nahi rokta tha, aur
fragile base class ki samasya aati thi: superclass ka ek method badlo aur aisi subclasses toot
jaayein jinke hone ka pata bhi na ho. Kotlin ne default ulta kar diya. Ab wahi cheez badhayi ja
sakti hai jiske baare mein likhne wale ne socha ho.
</Detail>

## `super` — purana behaviour rakhkar usme jodna

```kotlin title="Super.kt" numbered runnable
open class Logger {
    open fun log(message: String) = println("LOG: $message")
}

class TimestampLogger : Logger() {
    override fun log(message: String) {
        super.log("[12:04] $message")     // dobara likho mat, use karo
    }
}

fun main() = TimestampLogger().log("saved")
```

## Common galtiyan

<Pitfall title="Do jo asli bug bunti hain">
**Constructor ya `init` se `open` method bulana.** Subclass ki apni properties tab tak assign
hui hi nahi hotin, isliye override aadhe-adhoore state par chalta hai aur `null` ya `0` padhta
hai. Construction ke dauraan overridable method kabhi mat bulao.

**Code baantne ke liye inheritance use karna.** Agar `Card` aur `Upi` ko sirf ek hi helper
chahiye, to wo `is-a` rishta nahi hai — wo ek shared function hai. Inheritance subclass ko base
ke har aane wale badlav se baandh deta hai. Composition behtar hai, ya default wala interface.
</Pitfall>

## Practice

1. Ek `Wallet` payment jodo jiski fee seedhi 5 ho. Dekho ki `receipt()` use bina `Payment` chhue
   utha leta hai.
2. `Card` mein `fee()` ko `final override` karo, phir `Card` ko badhakar use dobara override
   karne ki koshish karo. Compiler ki galti padho.
3. `Payment` ke `init` mein ek `println` daalo jo `fee()` bulaye, phir `Card` banao. Jo number
   mila use samjhao.
4. Poore structure ko aise likho ki `fee()` open class ki jagah interface se aaye. Paanchwa
   payment type jodne par kaun sa version zyada aaram se jhelta?

## Recap

| Situation | Kya uthao |
| --- | --- |
| Subtypes state aur behaviour dono baantein | `open class` + `override` |
| Subtypes sirf behaviour baantein | Default wala interface |
| Reuse chahiye, `is-a` nahi | Composition — doosre object ko rakho |
| Subtypes ka set fixed aur pata ho | `sealed` — aage ke lesson mein |
