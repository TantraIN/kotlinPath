<KeyIdea>
`sealed` hierarchy ko band kar deta hai, isliye uspar `when` ko `else` chahiye hi nahi — aur jis
din koi naya case jodta hai jo aapne handle nahi kiya, us din se compile hona band ho jata hai.
</KeyIdea>

## Wo screen state jo har app mein hai

```kotlin title="UiState.kt" numbered runnable
sealed interface UiState {
    object Loading : UiState
    data class Success(val items: List<String>) : UiState
    data class Error(val message: String) : UiState
}

fun render(state: UiState): String = when (state) {
    UiState.Loading    -> "spinner"
    is UiState.Success -> "${state.items.size} items"
    is UiState.Error   -> "error: ${state.message}"
    // koi else nahi — compiler har case check kar chuka hai
}

fun main() {
    listOf(UiState.Loading, UiState.Success(listOf("a", "b")), UiState.Error("timeout"))
        .forEach { println(render(it)) }
}
```

Dhyan do ki `else` hai hi nahi. Uska na hona hi poori khoobi hai.

## Sealed aur enum mein farq

| | `enum` | `sealed` |
| --- | --- | --- |
| Cases | **Values** ka fixed set | **Types** ka fixed set |
| Data rakh sakta hai | Har case mein wahi fields | Har case ki apni fields |
| Kai instances | Nahi, har constant ka ek | Haan, `Success` kai baar ho sakta hai |
| Kis liye | Tabs, sort order, status flags | Screen state, results, events |

<Tip bare>
Agar kisi ek case ko aisa data chahiye jo baakiyon ko nahi, to `sealed` chahiye. Agar har case
sirf ek naam hai, to `enum` chahiye.
</Tip>

<Detail summary="sealed interface ya sealed class">
`sealed interface` behtar hai. Koi subtype kai interfaces implement kar sakta hai par class sirf
ek badha sakta hai, isliye interface wala roop jodne-todne laayak rehta hai. `sealed class`
tabhi uthao jab cases sach mein shared stored state rakhte hon, jo kam hi hota hai.
</Detail>

## Common galtiyan

<Pitfall title="Do jo chupchap poora faayda kha jati hain">
**Sealed type par `when` mein `else` jodna.** Aaj bhi compile hoga aur hamesha hota rahega —
us din bhi jab naya case aayega aur bina handle hue `else` mein gir jayega. Har case alag se
likho.

**Bina data wale case ke liye `data class`.** `data class Loading : UiState()` har baar naya
object banata hai aur bewajah values milata hai. Bina state wala case `object` hona chahiye.
</Pitfall>

## Practice

1. `render` ko chhue bina `UiState` mein `Empty` case jodo. Compiler ki galti padho, phir theek
   karo.
2. `render` ko `else -> "unknown"` ke saath likho, ek aur case jodo, aur dekho ki koi warning
   nahi aati. Yahi cheez aap chhod rahe ho.
3. Payment result ko sealed interface se model karo — `Approved(txnId)`, `Declined(reason)` aur
   `Pending`. Teeno mein se kaun sa `object` hona chahiye?
4. Apne likhe kisi `enum` ko sealed interface mein badlo. Kya kisi case ko aisa field mila jo
   sirf usi ko chahiye tha?

## Recap

| Baat | Detail |
| --- | --- |
| `sealed` | Saare subtypes compile time par pata, usi module mein |
| Poora `when` | `else` chahiye nahi — aur kabhi jodo mat |
| Naya case jodna | Jahan-jahan maayne rakhta hai wahan compile error |
| Bina state ka case | `object`, `data class` nahi |
| Default chunav | `sealed class` se behtar `sealed interface` |
