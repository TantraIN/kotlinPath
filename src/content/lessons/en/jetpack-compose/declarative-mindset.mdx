<KeyIdea>
A composable is not a thing you build and then mutate. It is a **description of what the screen
looks like for one particular state** — a function the runtime calls again whenever that state
changes.
</KeyIdea>

## Why this matters

Here is a badge that should be visible only for unread orders, written the imperative way:

```kotlin title="Imperative.kt" numbered
fun bind(order: Order) {
    binding.title.text = order.title
    if (order.isUnread) {
        binding.badge.isVisible = true
    }
}
```

That code is wrong, and the reason is the same one you met in `RecyclerView`: it says what to do
when the badge should appear and says nothing about when it should go away. The next order to
land in that row inherits a badge it never asked for.

Every imperative UI bug has this shape. You changed the screen for one case and forgot the other.

## The same thing, described rather than commanded

```kotlin title="Declarative.kt" numbered
@Composable
fun OrderRow(order: Order) {
    Row {
        Text(order.title)
        if (order.isUnread) {
            Badge()
        }
    }
}
```

There is no branch that turns the badge off, because there is no badge to turn off. The function
says what a row *is* for this order. When `order` changes, the runtime calls it again and reaches
the new answer.

<Note>
`@Composable` is not a normal annotation. It changes what the function can do and who is allowed
to call it: only another `@Composable`. The next lesson is entirely about what the compiler does
with it.
</Note>

Composition builds a tree of nodes describing the screen. When state changes, only the
composables that read that state run again — this is **recomposition**, and it is the thing the
whole toolkit is built to make cheap.

## The rule that catches everyone

  question="You add `var runs = 0` outside a composable and do `runs++` inside it, to see how often it runs. The number is nonsense. Why?"

## Under the hood

<Timeline>
  <TimelineItem title="A composable returns nothing" meta="it emits">
    `OrderRow` has no return type. Calling it inside a composition *emits* nodes into the tree
    being built, which is why it can only be called from another composable.
  </TimelineItem>
  <TimelineItem title="Position is identity" meta="positional memoization">
    The runtime remembers values by where the call sits in the source, not by any name you give
    it. That is how `remember` can hold a value across recompositions without a key.
  </TimelineItem>
  <TimelineItem title="The tree is nodes, not Views" meta="no inflation">
    Composition produces lightweight layout nodes, not `View` objects, so there is no XML to
    inflate and nothing to recycle.
  </TimelineItem>
</Timeline>

<Detail summary="So what happened to state?">
State is not gone — it moved. A composable that needs to remember something across recompositions
asks the runtime to hold it:

```kotlin title="Preview.kt"
var expanded by remember { mutableStateOf(false) }
```

`mutableStateOf` creates a value the runtime watches, and `remember` keeps it alive across
recompositions. Reading it inside a composable subscribes that composable to it, so changing it
schedules exactly the recomposition needed. Two lessons from now this is the whole topic; for
now, know that the state has an owner and it is not a widget.
</Detail>

## Common mistakes

<Pitfall title="Three that come straight from the view system">
**Thinking of a composable as an object.** There is no `OrderRow` instance to keep, no reference
to hold and no method to call on it later. There is only the function and the state it reads.

**Doing work in the function body.** Network calls, logging, database writes — a composable can
run many times a frame, so anything with an effect must go through a side-effect API, never in
the body.

**Expecting an order.** Sibling composables have no guaranteed execution order and may run in
parallel. Code that depends on one running before another is already broken.
</Pitfall>

## Practice

1. Take the imperative `bind` above and write down every case it forgets. Then write the Compose
   version and count the branches.
2. Write a composable that shows a label only when a boolean is true, and drive that boolean from
   a button. Notice that you never wrote code to hide the label.
3. Add a `println` inside a composable and watch how often it appears while you interact.
4. Explain to somebody else why the count in the quiz above cannot work. That explanation is the
   whole mental shift.

## Recap

| Thing | One line |
| --- | --- |
| Composable | A description of the UI for one state, not an object |
| Emits | It returns nothing; it adds nodes to the composition |
| Recomposition | Re-running the composables that read changed state |
| Purity | No side effects in the body — ever |
| Order | Not guaranteed; siblings may run in parallel |
| Skipping | Unchanged inputs mean the function may not run at all |
| Identity | Position in the source, not a name you chose |

<Interview title="The question that opens every Compose interview">
"What does declarative UI actually mean here?"

That you write a function from state to a description of the screen, and never write the
transition between two screens. The line worth adding is the failure it removes: the classic
imperative bug is a branch that sets something and no matching branch that unsets it, and in a
declarative description that bug cannot be expressed.
</Interview>
