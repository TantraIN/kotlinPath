<KeyIdea>
Paging exists because a list is **unbounded and memory is not**. The library's real work is keeping
a sliding window of loaded pages, dropping what scrolled away, and doing it while the user is still
scrolling — which is why you cannot reasonably hand-roll it.
</KeyIdea>

## Why this matters

The version everyone writes first:

```kotlin title="Manual.kt" numbered
private var page = 0
private val all = mutableListOf<Order>()

fun loadMore() = viewModelScope.launch {
    val next = api.orders(page = page++)        // fires again on every scroll event
    all += next                                 // grows forever
    _state.value = OrderUiState(all.toList())   // copies the whole list each time
}
```

Every problem here appears only at scale. `page++` outside the coroutine means two fast scrolls load
page 3 twice and skip page 4. `all` never shrinks, so ten thousand orders is ten thousand objects in
memory. Each emission copies the entire list. And there is nowhere to put a retry, or a loading
spinner at the bottom, without another flag.

## The three pieces

```kotlin title="OrderPagingSource.kt" numbered
class OrderPagingSource(private val api: OrderApi) : PagingSource<Int, OrderDto>() {

    override suspend fun load(params: LoadParams<Int>): LoadResult<Int, OrderDto> = try {
        val page = params.key ?: 1
        val orders = api.orders(page = page, limit = params.loadSize)
        LoadResult.Page(
            data = orders,
            prevKey = if (page == 1) null else page - 1,
            nextKey = if (orders.isEmpty()) null else page + 1,   // null means: no more
        )
    } catch (e: IOException) {
        LoadResult.Error(e)                     // the UI can offer a retry
    }

    override fun getRefreshKey(state: PagingState<Int, OrderDto>): Int? =
        state.anchorPosition?.let { state.closestPageToPosition(it)?.nextKey?.minus(1) }
}
```

```kotlin title="OrderRepository.kt" numbered
fun orders(): Flow<PagingData<Order>> = Pager(
    config = PagingConfig(pageSize = 20, prefetchDistance = 5),
    pagingSourceFactory = { OrderPagingSource(api) },
).flow.map { paging -> paging.map(OrderDto::toDomain) }
```

```kotlin title="OrderScreen.kt" numbered
val orders = viewModel.orders.collectAsLazyPagingItems()

LazyColumn {
    items(orders.itemCount, key = orders.itemKey { it.id }) { index ->
        orders[index]?.let { OrderRow(it) }     // null while that page loads
    }
}
```

`orders[index]` returning null is not an error — it is the placeholder for a row whose page is still
loading. Treat it as a normal state and show a skeleton row.

<Note>
`getRefreshKey` is the one people leave as `null` and regret. It answers: after a refresh, which page
should reload so the user stays roughly where they were? Return `null` and every refresh jumps them
back to the top — which on a pull-to-refresh feels like the app lost their place, because it did.
</Note>

## Loading state comes with it

```kotlin title="LoadState.kt" numbered
when (val refresh = orders.loadState.refresh) {
    is LoadState.Loading -> FullScreenSpinner()
    is LoadState.Error   -> ErrorScreen(refresh.error) { orders.retry() }
    is LoadState.NotLoading -> if (orders.itemCount == 0) EmptyState()
}

if (orders.loadState.append is LoadState.Loading) item { BottomSpinner() }
```

`refresh` is the first load or a manual refresh; `append` is loading more at the bottom; `prepend` is
at the top. Separating them is what lets a failed page-five load show a small retry button at the
bottom instead of replacing a working screen with an error — a distinction the manual version had no
way to express.

This is the same identity rule as any LazyColumn, but paging makes it far more visible because invalidation happens constantly under a background sync. Note that a small pageSize does cause extra loads, but it would not produce the jumping — that symptom is specifically about identity."

## RemoteMediator, where paging meets offline-first

A `PagingSource` reads from one place. Real apps read from the database and fill it from the network,
which is a second job:

```kotlin title="OrderRemoteMediator.kt" numbered
@OptIn(ExperimentalPagingApi::class)
class OrderRemoteMediator(
    private val api: OrderApi,
    private val db: AppDatabase,
) : RemoteMediator<Int, OrderEntity>() {

    override suspend fun load(
        loadType: LoadType,
        state: PagingState<Int, OrderEntity>,
    ): MediatorResult = try {
        val page = when (loadType) {
            LoadType.REFRESH -> 1
            LoadType.PREPEND -> return MediatorResult.Success(endOfPaginationReached = true)
            LoadType.APPEND  -> db.keyDao().nextKey() ?: return MediatorResult.Success(true)
        }

        val orders = api.orders(page = page, limit = state.config.pageSize)

        db.withTransaction {                                   // one invalidation, not many
            if (loadType == LoadType.REFRESH) db.orderDao().clear()
            db.keyDao().setNextKey(if (orders.isEmpty()) null else page + 1)
            db.orderDao().upsert(orders.map(OrderDto::toEntity))
        }
        MediatorResult.Success(endOfPaginationReached = orders.isEmpty())
    } catch (e: IOException) {
        MediatorResult.Error(e)
    }
}
```

```kotlin title="Wiring.kt" numbered
Pager(
    config = PagingConfig(pageSize = 20),
    remoteMediator = OrderRemoteMediator(api, db),
    pagingSourceFactory = { db.orderDao().pagingSource() },   // reads always come from Room
).flow
```

Read that wiring against the repository lesson: the `PagingSource` is the database, the
`RemoteMediator` only writes into it, and the single source of truth holds. The app pages through
cached data offline and fills gaps when the network returns, with no separate offline code path.

The `withTransaction` is the same point as the Room lesson. Three DAO calls outside a transaction are
three invalidations, so Paging reloads three times for one page of data.

<Detail summary="Why the remote keys table exists">
`RemoteMediator` cannot ask the database "what page is this row from" — that is not something a row
knows. So paging state has to be stored, usually as a small table:

```kotlin title="RemoteKey.kt" numbered
@Entity(tableName = "remote_keys")
data class RemoteKeyEntity(
    @PrimaryKey val id: String = "orders",
    val nextKey: Int?,
)
```

It is written inside the same transaction as the rows it describes, which is what keeps the two
consistent if the process dies mid-write. Write them separately and you can end up with rows saved
and a key that never advanced, so the app re-fetches page 3 forever.

For a cursor-based API — one that returns an opaque `next` token rather than a page number — this
table is not an optimisation, it is the only place that token can live.
</Detail>

## Common mistakes

<Pitfall title="Five that only appear on a long list">
**No stable `key` in `items`.** Flicker and lost row state on every invalidation. See the quiz.

**Ignoring `getRefreshKey`.** Every refresh jumps the user back to the top.

**Multiple writes outside a transaction in `RemoteMediator`.** One page of data, several
invalidations, several reloads.

**Treating a null item as a bug.** It is the placeholder for a loading page — render a skeleton.

**Using `PagingData` like a list.** It has no `size` and cannot be filtered after collection. Filter
in the query or with `PagingData.filter` inside the flow.
</Pitfall>

## Practice

1. Page through a list, then log `itemCount` while scrolling far down and watch the window rather
   than the total.
2. Remove the `key` from `items`, run a background insert, and watch the list flicker.
3. Return `null` from `getRefreshKey`, pull to refresh halfway down, and see where you land.
4. Add a `RemoteMediator` and put the app in airplane mode after one scroll — the cached pages should
   still page.
5. Make the network fail on page three and confirm the bottom shows a retry rather than the whole
   screen erroring.

## Recap

| Thing | One line |
| --- | --- |
| Why | The list is unbounded, memory is not |
| `PagingSource` | Loads one page and names the next key |
| `nextKey = null` | There is no more data |
| `getRefreshKey` | Where to reload so the user keeps their place |
| `Pager` + `PagingConfig` | Page size and prefetch distance |
| `collectAsLazyPagingItems` | The Compose bridge; a null item means loading |
| `loadState` | `refresh`, `append`, `prepend` — handled separately |
| `RemoteMediator` | Fills the database; the `PagingSource` still reads it |
| Remote keys | Paging state, written in the same transaction as the rows |
| Stable `key` | Identity by id, not position — or the list flickers |

<Interview title="A question whose good answer starts with memory">
"Why use Paging instead of loading the whole list?"

Because the list is unbounded and memory is not. Paging keeps a window of loaded pages and drops what
has scrolled out of range, so a ten thousand row list costs the same as a hundred row one. It also
gives me the things a hand-rolled version always misses — deduplicated requests so a fast scroll does
not load the same page twice, and separate `refresh`, `append` and `prepend` load states, so a failed
page five shows a retry at the bottom instead of replacing a working screen.

The piece I would highlight is `RemoteMediator`, because it is what makes paging compatible with a
single source of truth: the `PagingSource` reads from Room and the mediator only writes into it, so
the app pages through cached data offline with no separate code path. The detail that matters there
is writing the rows and the remote key in one transaction — separately, a process death leaves saved
rows and a stale key, and the app re-fetches the same page forever.
</Interview>
