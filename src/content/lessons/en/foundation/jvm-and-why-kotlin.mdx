## Why this matters

Sooner or later a build fails with something like this:

```text no-glossary
Unsupported class file major version 65
> Task :app:compileDebugKotlin FAILED
```

Nothing in that message mentions Kotlin, Android, or your code. It is talking about
**bytecode** and **JDK versions** — the layer this lesson is about. Once you can see that
layer, errors like this stop being mysterious and become a one-line fix.

## The middle path

Last lesson gave you two options: compile everything ahead of time, or interpret it line
by line. Kotlin takes neither.

It compiles ahead of time — but not to machine code for your specific processor. It
compiles to **bytecode**: instructions for an imaginary computer. A program called the
**Java Virtual Machine** then runs that bytecode on the real machine it happens to be
installed on.

That split is the whole trick. The compiler does the expensive work once. The JVM handles
the part that differs between a Windows laptop, a Linux server and a phone.

<Tip bare>
This is what "write once, run anywhere" means. Not that the source is portable — that the
**compiled artefact** is.
</Tip>

Two names you will keep meeting:

- **JDK** — Java Development Kit. The tools *plus* a JVM. You need it to build.
- **JRE** — Java Runtime Environment. Just the JVM. Enough to run, not to build.

Android Studio bundles a JDK, which is why you rarely install one by hand — and also why
"which JDK is this build using?" is a question worth knowing how to answer.

## Under the hood: bytecode is readable

Bytecode is not magic. Here is an ordinary Kotlin function:

```kotlin title="Adder.kt" numbered runnable
fun add(a: Int, b: Int): Int {
    return a + b
}

fun main() {
    println(add(2, 3))
}
```

Compiled, `add` becomes roughly four bytecode instructions: load the first argument, load
the second, add them, return. The JVM executes those, and after a function has run enough
times the **JIT compiler** notices and translates it into real machine code so later calls
skip the interpretation entirely.

<Note>
This is why a JVM program is often slow for its first second and fast afterwards. On
Android the same idea appears as **Baseline Profiles**, which tell the runtime what to
compile ahead of time so your users never see the slow first second. You will meet those
again in Phase 12.
</Note>

## So why Kotlin and not Java?

Both compile to the same bytecode. The JVM cannot tell them apart. The difference is
entirely in what the language lets you express — and what it refuses to let you write.

The same idea in both languages:

```java title="User.java" numbered
public class User {
    private final String name;
    public User(String name) { this.name = name; }
    public String getName() { return name; }
    // plus equals, hashCode and toString by hand
}
```

```kotlin title="User.kt" numbered runnable
data class User(val name: String)
```

One line, and `equals`, `hashCode`, `toString` and `copy` come with it. That is not a party
trick — value equality is what makes list diffing and Compose recomposition work correctly,
as you will see in Phase 2.

## Common mistakes

<Pitfall title="The two that cost beginners a day each">
**Mixing JDK versions.** Your Gradle build, your Kotlin compiler and Android Studio must
agree. `Unsupported class file major version 65` means something compiled with a newer JDK
than the one reading it. Fix it in one place — the project's Java toolchain — not by
reinstalling things at random.

**Trusting a value that came from Java.** The compiler cannot know whether a Java method
returns null, so it marks the result a *platform type* and steps out of the way. Null
safety silently stops protecting you at that boundary. Assign it to an explicitly nullable
type (`String?`) the moment it enters your Kotlin code.
</Pitfall>

## Recap

| Term | What it is | When you meet it |
| --- | --- | --- |
| Bytecode | Instructions for an imaginary machine | `.class` files, build errors |
| JVM | The program that runs bytecode | Every `java` command |
| JDK | Tools + JVM, needed to build | Gradle toolchain settings |
| JIT | Compiles hot code to machine code at run time | Slow first run, fast after |
| Platform type | A Java value Kotlin cannot check for null | Interop crashes |

<Interview title="A very common opening question">
"Kotlin and Java both run on the JVM. What does Kotlin actually add?"

A strong answer separates the two layers: nothing at the bytecode level — the JVM sees the
same instructions — and a great deal at the language level, where the compiler enforces
null safety, generates data-class members, and turns `suspend` functions into state
machines before any bytecode exists.
</Interview>
