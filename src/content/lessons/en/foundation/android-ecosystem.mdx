## Why this matters

Android asks you to make decisions on day one that only make sense if you know what is
underneath: which `minSdk` to support, why your app cannot read another app's files, why
`targetSdk` changes behaviour you never wrote.

None of those are arbitrary. Each falls out of the architecture. Fifteen minutes here saves
you from cargo-culting settings you do not understand.

## ART is not the JVM

The last lesson ended with a question: why can Android not just ship the JVM?

Because a phone is not a server. It has a small battery, limited RAM, and a user watching a
spinner. Android replaced the JVM with the **Android Runtime**, which makes different
trade-offs.

## The sandbox

Here is the single most consequential design decision in Android: **every app gets its own
Linux user ID.**

Not a metaphor — an actual user, the way `root` and `www-data` are users on a server. Your
app's files are owned by that user, and Linux file permissions do the rest.

```bash title="Terminal" no-glossary
# Two apps, two completely separate identities
adb shell ps -A | grep -E "com.example|com.android.chrome"

u0_a142  ...  com.example.myapp
u0_a201  ...  com.android.chrome
```

Everything else follows from this:

- Another app cannot read your database, because the file is not readable by its user.
- A permission is the system granting your user ID access to something outside your
  sandbox — the camera, the network, the user's contacts.
- Each app runs in its own process with its own runtime instance, so one app crashing
  cannot take down another.

<Note>
This is why "just write the file to the SD card and read it from my other app" stopped
working years ago, and why every storage question on Android eventually becomes a question
about which sandbox the file lives in. Phase 8 covers scoped storage in detail.
</Note>

## API levels: the number that actually matters

Users talk about "Android 15". The platform talks about **API level 35**. They are two
names for the same release, and the API level is the one your build uses.

| Setting | What it means | Set it to |
| --- | --- | --- |
| `compileSdk` | Which API your code is compiled against | Always the latest stable |
| `minSdk` | The oldest device that can install your app | As low as your users need |
| `targetSdk` | The behaviour your app is tested against | Latest, and raise it deliberately |

`targetSdk` is the subtle one. The system reads it and decides how strictly to treat you.
Raise it and behaviours change — background limits tighten, permissions become stricter —
without you editing a single line. Google Play also requires it to stay recent, so it is
not optional.

<Pitfall title="Two assumptions that break real apps">
**Assuming a class exists because it compiles.** `compileSdk 35` lets you call an API added
in level 33. On a `minSdk 24` device that class is simply not there, and the app crashes
with `NoSuchMethodError`. Guard it: `if (Build.VERSION.SDK_INT >= Build.VERSION_CODES.TIRAMISU)`.

**Raising `targetSdk` to silence a warning.** It is a declaration that you have tested
against that version's behaviour changes. Raise it, then actually run the app — do not raise
it the evening before a release.
</Pitfall>

## What you actually ship

You do not upload an APK to Google Play any more. You upload an **AAB** — an Android App
Bundle — and Play generates a right-sized APK for each device.

## Practice

1. For each of these, name the layer it belongs to: `SQLite`, `Activity`, the camera
   driver, `PackageManager`, DEX execution.
2. Your app crashes with `NoSuchMethodError` only on older phones. Which of the three SDK
   settings is wrong, and what is the fix?
3. Explain, using the sandbox, why a to-do app cannot read a banking app's saved session —
   without using the word "security".
4. Your APK is 40 MB. Give two reasons an AAB would make the actual download smaller.

## Recap

| Term | One line |
| --- | --- |
| Linux kernel | The bottom layer; source of the user-ID sandbox |
| HAL | Stable interface to hardware from many manufacturers |
| ART | Android's runtime — runs DEX, compiles ahead of time |
| DEX | Android's bytecode format, produced by R8 |
| Sandbox | One Linux user per app; permissions are grants outside it |
| API level | The number your build targets, e.g. 35 for Android 15 |
| AAB | What you upload; Play turns it into per-device APKs |

<Interview title="Asked to check you understand the platform, not just the SDK">
"What is the difference between `minSdk`, `targetSdk` and `compileSdk`?"

The answer that lands: `compileSdk` is compile time, `minSdk` is install time, `targetSdk`
is run time. Then give the consequence of each being wrong — code that will not compile,
users who cannot install, and behaviour changes you never tested.
</Interview>
