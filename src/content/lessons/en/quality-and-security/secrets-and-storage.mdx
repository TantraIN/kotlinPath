<KeyIdea>
An APK is a zip file on someone else's computer. Obfuscation, `BuildConfig`, native code and clever
encoding all raise the effort and none of them change the outcome — so a secret that must stay secret
**cannot ship with the app**.
</KeyIdea>

## What "hidden" actually buys

```kotlin title="NotHidden.kt" numbered
// visible in the decompiled class file
private const val API_SECRET = "sk_live_9f2a..."

// visible in BuildConfig, which is a normal class
buildConfigField("String", "API_SECRET", "\"sk_live_9f2a...\"")

// visible in strings.xml, and even easier
<string name="api_secret">sk_live_9f2a...</string>

// visible in the .so with `strings`, and to anyone who hooks the JNI call
external fun getSecret(): String
```

Each row is a little more work for an attacker and none is a barrier. `apktool` and `jadx` take
seconds; the NDK version takes a few minutes with `strings` or Frida. Automated scanners crawl Play
for exactly these patterns, which is how leaked keys usually get found — not by a targeted attacker
but by a bot.

The distinction that matters:

| Kind of key | Can it ship? |
| --- | --- |
| A public client identifier — Maps key, OAuth client id, Firebase config | Yes; restrict it server-side |
| A signing secret, private API key, admin token | No, ever |

For the first kind, restriction is the security: lock a Maps key to your package name and signing
certificate, so extracting it gains nothing. For the second, the operation belongs on your server, and
the app calls your endpoint instead of the third party's.

## The Keystore, for secrets the device generates

What the device generates and never sends is a different problem, and Android has real hardware for it:

```kotlin title="Keystore.kt" numbered
val spec = KeyGenParameterSpec.Builder("token_key", PURPOSE_ENCRYPT or PURPOSE_DECRYPT)
    .setBlockModes(BLOCK_MODE_GCM)
    .setEncryptionPaddings(ENCRYPTION_PADDING_NONE)
    .setUserAuthenticationRequired(true)          // only after a biometric or PIN
    .build()

KeyGenerator.getInstance(KEY_ALGORITHM_AES, "AndroidKeyStore").apply {
    init(spec); generateKey()
}
```

The key material never leaves the secure hardware — on most modern devices a TEE or a dedicated
security chip — and cannot be extracted even from a rooted device. Your code gets to *use* the key, not
to read it.

That is why a session token is safe to store encrypted with a Keystore key and an API secret is not:
the Keystore protects something that was created on that device, while an API secret arrived in the
APK and was already compromised before the Keystore saw it.

## Storing data at rest

```kotlin title="Storage.kt" numbered
// Jetpack Security is deprecated; DataStore encrypted with your own Keystore key
val encrypted = cipher.doFinal(token.toByteArray())
dataStore.edit { it[TOKEN] = Base64.encodeToString(encrypted, Base64.NO_WRAP) }

// SQLCipher for a whole database, with the passphrase from the Keystore
Room.databaseBuilder(context, AppDatabase::class.java, "app.db")
    .openHelperFactory(SupportOpenHelperFactory(passphrase))
    .build()
```

`EncryptedSharedPreferences` and `EncryptedFile` were the standard answer and are now deprecated, so
new code should use a Keystore key directly with DataStore, or SQLCipher when a whole database needs
it.

Worth being clear about the threat model: app-private storage in `filesDir` is already unreadable by
other apps, and on a device with a screen lock it is encrypted at rest by the platform. Encrypting on
top of that protects against a rooted device, a backup extraction, or a stolen unlocked phone — real
threats, but narrower than "someone might read my file".

<Detail summary="Backups, logs and the accidental leaks">
Three ways secrets escape without anyone attacking anything.

**Auto Backup.** By default Android backs up app data to the user's cloud, including your files.
Exclude anything sensitive:

```xml title="AndroidManifest.xml" numbered
<application
    android:dataExtractionRules="@xml/data_extraction_rules"
    android:fullBackupContent="@xml/backup_rules">
```

**Logs.** `Log.d("api", "token=$token")` is readable by anyone with `adb` on a debuggable build, and
survives into crash reports and analytics breadcrumbs. Strip logging in release with an R8 rule, and
never log a request body.

**Screenshots and the recents list.** A screen showing sensitive data appears in the app switcher and
can be captured. `WindowManager.LayoutParams.FLAG_SECURE` blocks both for that activity.

The pattern across all three is that the secret was handled correctly and then copied somewhere with
different rules. That is a more common leak than any decompiler.
</Detail>

## Common mistakes

<Pitfall title="Five, and the first is found by bots rather than attackers">
**A private key in `BuildConfig` or `strings.xml`.** Scanners crawl Play for exactly this.

**Treating the NDK as a hiding place.** Harder to find, and plaintext in memory when used.

**Not restricting a client key.** A Maps key locked to your package is safe to ship; an unlocked one
is someone else's bill.

**Committing `google-services.json` or a keystore.** Check history, not just the working tree.

**Logging tokens.** They survive into crash reports and analytics long after the log line is read.
</Pitfall>

## Practice

1. Run `jadx` on your own release APK and find every string that looks like a key.
2. Run `strings` on a `.so` containing a hardcoded secret.
3. Generate a Keystore key with `setUserAuthenticationRequired` and confirm you cannot read the key.
4. Add `FLAG_SECURE` to a screen and try to screenshot it.
5. Check your backup rules and list which files would be uploaded to the cloud today.

## Recap

| Thing | One line |
| --- | --- |
| An APK | A zip on someone else's computer |
| Obfuscation and NDK | More effort for an attacker; not a barrier |
| Client identifiers | Fine to ship, if restricted server-side |
| Private secrets | Never ship; the call belongs on your server |
| Keystore | Hardware-backed; the key cannot be extracted |
| Why it works | It protects what the device generated, not what arrived in the APK |
| `EncryptedSharedPreferences` | Deprecated; use a Keystore key with DataStore |
| SQLCipher | When a whole database needs encrypting |
| Auto Backup | Exclude sensitive files, or they go to the cloud |
| `FLAG_SECURE` | Blocks screenshots and the recents thumbnail |

<Interview title="A question with a firm answer">
"How do you store an API key securely in an Android app?"

You do not — anything in the APK can be extracted, and `BuildConfig`, `strings.xml`, obfuscation and
the NDK differ only in how long it takes. The NDK is the one people expect to be safe, and it is not:
the string is in the binary, and even obfuscated it has to be plaintext in memory at the moment it is
used, which is where a hooking framework reads it.

So I would split the keys by kind. A public client identifier — a Maps key, an OAuth client id — can
ship, because the security is the restriction: lock it to the package name and signing certificate so
extracting it gains nothing. Anything genuinely secret does not ship at all; the privileged call moves
to a server the app authenticates to with a per-user token that can be revoked. The Keystore is for a
different problem — protecting something the device generated, like a session key — and it works
precisely because that value never arrived in the APK.
</Interview>
