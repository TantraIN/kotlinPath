<KeyIdea>
A route is an **address, not a payload**. Pass the id of the thing; let the destination
load it. A route carrying the object looks convenient and breaks the first time the
data changes while the screen is open — or the process is restored from disk.
</KeyIdea>

## Type-safe routes

```kotlin title="ui/Routes.kt" numbered
@Serializable data object ListsRoute
@Serializable data class ListRoute(val listId: String)
@Serializable data class EditItemRoute(val listId: String, val itemId: String)
```

Three declarations and one plugin — `kotlinx-serialization` — replace the string
routes that Navigation used to need. The difference is not aesthetic: with strings,
`"list/{listId}"` and a typo in the argument name compile fine and fail at run time
with a null argument. With these, a missing or misnamed argument is a compile error.

```kotlin title="ui/SaathiNavHost.kt" numbered
NavHost(navController = navController, startDestination = ListsRoute) {

    composable<ListsRoute> {
        ListsScreen(onOpen = { listId -> navController.navigate(ListRoute(listId)) })
    }

    composable<ListRoute> {
        ListScreen(
            onEdit = { itemId -> navController.navigate(EditItemRoute(listId, itemId)) },
            onBack = { navController.navigateUp() },
        )
    }

    composable<EditItemRoute> {
        EditItemScreen(onDone = { navController.popBackStack() })
    }
}
```

`navigate(ListRoute(listId))` takes an instance, not a formatted string. The route
object is serialised into the back stack entry, and `savedStateHandle.toRoute<ListRoute>()`
in the ViewModel reads it back — which is the line you already wrote in the previous
step.

## Managing the back stack

Navigating is easy; deciding what the user can come back to is the part with rules.

```kotlin title="Clearing the login screen" numbered
navController.navigate(ListsRoute) {
    popUpTo<LoginRoute> { inclusive = true }   // remove login, including itself
    launchSingleTop = true                     // do not stack a second copy
}
```

Without `popUpTo`, pressing back after signing in returns the user to the login
screen of an app they are already signed into. It is the single most common
navigation bug in an app with auth, and one option fixes it.

`launchSingleTop` matters wherever a destination can be reached from itself — a
notification opening a list the user is already viewing, or a double tap on a row.
Without it, back has to be pressed twice to leave one screen.

| Option | Use when |
| --- | --- |
| `popUpTo(route)` | The screens behind should not be returned to |
| `inclusive = true` | The target itself should also go — login, onboarding |
| `launchSingleTop` | The destination may be re-entered from itself |
| `restoreState` | Bottom-nav tabs that should keep their scroll position |

<Detail summary="`navigateUp` and `popBackStack` are not the same call">
They behave identically most of the time, which is why the difference only shows up in
the case that matters.

`popBackStack()` removes the top entry of *your* back stack. If it is empty, nothing
happens and the user is stuck.

`navigateUp()` asks the host — which may be another app. When your screen was opened
from a deep link, or from a share sheet in someone else's app, `navigateUp` returns
the user there. That is the behaviour a person expects from the toolbar arrow, and it
is why toolbar Up should call `navigateUp()` while an in-screen "Done" button should
call `popBackStack()`.

This becomes concrete in the sharing step, when a link from WhatsApp opens the app
directly onto a list with no back stack behind it.
</Detail>

## Where the ViewModel lives

```kotlin title="Scoped to the destination" numbered
composable<ListRoute> {
    val viewModel: ListViewModel = hiltViewModel()   // scoped to this back stack entry
    ListScreen(viewModel)
}
```

`hiltViewModel()` inside a `composable` block scopes the ViewModel to that navigation
entry, not to the Activity. Two different lists on the stack therefore get two
ViewModels with two `listId`s, and popping a screen clears its ViewModel.

That is almost always what you want. The exception is state genuinely shared across
screens — a multi-step form — where you scope to the parent graph entry instead, and
say so explicitly rather than reaching for an Activity-scoped ViewModel.

<Pitfall title="Four, and the first two are visible to any tester in a minute">
**Passing objects as route arguments.** Stale data after any delay, and after process
death.

**No `popUpTo` after sign-in.** Back returns to the login screen of a signed-in app.

**Missing `launchSingleTop`.** A duplicate screen stacks up and back must be pressed
twice.

**`popBackStack()` on the toolbar arrow.** A deep-linked screen has nothing to pop, and
Up does nothing.
</Pitfall>

## Checkpoint

| Check | How you know |
| --- | --- |
| Routes are type-safe | Arguments are constructor parameters, not strings |
| Only ids travel | No route holds a domain object |
| Login is not in the stack | Back after sign-in leaves the app, not to login |
| ViewModels are per-destination | Two lists on the stack keep separate state |
| Up and back are distinguished | The toolbar arrow calls `navigateUp()` |
